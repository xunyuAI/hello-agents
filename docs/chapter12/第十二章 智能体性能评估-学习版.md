# 第十二章 智能体性能评估

前几章我们已经把 HelloAgents 的「手脚」和「记性」装好了：多种 Agent 范式、工具系统、记忆与检索、上下文工程，甚至强化学习训练。但真正上线前，还差一个更冷、也更关键的问题：

**这个智能体到底好不好？换了提示词或模型之后，是真进步了，还是只是感觉变好了？**

本章要给框架补上 **性能评估系统（Evaluation System）**。你可以把评估理解成「用同一套考卷和同一套评分规则，给不同智能体打分」——没有它，优化就像蒙眼调参。

## 读这一章之前，先建立心智模型

### 一个生活比喻

| 现实场景 | Agent 对应 | 本章组件 |
|---------|-----------|---------|
| 科目二专项（倒车入库） | 工具调用是否正确 | **BFCL** + AST 匹配 |
| 城市综合路考 | 真实任务综合能力 | **GAIA** + 准精确匹配 |
| 出题质量评审会 | 生成数据靠不靠谱 | **LLM Judge / Win Rate / 人工** |

传统软件测试像「断言返回码是 200」；智能体评估更像「作文评分」——同一题可以有多种正确写法，还要看结构、语义和成本。

### 几个关键词，先抓牢

- **Benchmark（评估基准）**：统一的数据集 + 指标 + 评分方法，保证横向可比。
- **AST Match**：把函数调用解析成抽象语法树再比较——允许参数顺序不同、等价表达式。
- **Quasi Exact Match（准精确匹配）**：先归一化答案（去 `$`、去冠词、列表排序），再精确比对。
- **LLM Judge**：用大模型当评委，多维度打绝对分。
- **Win Rate**：生成样本 vs 参考样本成对对比，理想值约 50%（质量相当）。
- **分层评估**：小样本冒烟 → 中等规模 → 全量，控制 API 成本。

### 建议怎么读

1. **先装环境**（12.1.4）：`hello-agents[evaluation]==0.2.7`，并处理 `bfcl-eval` / `numpy` 冲突。
2. **先跑通 BFCL 5 条样本**：确认评估链路通了，再读 AST 细节。
3. **GAIA 先申请 HF 权限**：受限数据集没 Token 会卡死。
4. **数据质量三条线一起理解**：Judge 看绝对水平，Win Rate 看相对差距，人工做最终把关。
5. **习题当复盘**：12.5 后的 5 大题覆盖对比、动手与系统设计。

## 12.1 智能体评估基础

### 12.1.1 为何需要智能体评估

看一个「看起来能用」的 SimpleAgent：

```python
from hello_agents import SimpleAgent, HelloAgentsLLM
from hello_agents.tools import SearchTool

llm = HelloAgentsLLM()
system_prompt = """你是一个AI助手，可以使用搜索工具来获取最新信息。
当需要搜索信息时，请使用：
[TOOL_CALL:search:搜索关键词]
请在回答问题前先使用搜索工具获取最新信息。"""

agent = SimpleAgent(name="AI助手", llm=llm, system_prompt=system_prompt)
agent.add_tool(SearchTool())
response = agent.run("最新的AI技术发展趋势是什么？")
print(response)
```

它能跑——但你无法客观回答：

1. 它是否具备预期能力？
2. 不同任务上表现如何？
3. 和其他智能体比处于什么水平？

**评估的核心价值**：用数字量化表现 → 客观比较方案 → 发现弱点 → 向用户证明可靠性。

#### 三大独特挑战（新手必记）

| 挑战 | 表现 | 常见应对 |
|------|------|----------|
| 输出不确定性 | 同一题多种正解 | AST / 语义匹配 / 归一化 / LLM Judge |
| 标准多样性 | 工具调用 ≠ 开放问答 | 按任务选基准与指标族 |
| 成本高昂 | 大量 API 调用 | 分层抽样、缓存、CI 门禁策略 |

学术界与工业界用标准化 **Benchmark** 应对：同一套题、同一套分，才谈得上「排行榜」。

### 12.1.2 主流评估基准概览

#### （1）工具调用能力

- **BFCL**（UC Berkeley）：1120+ 样本；simple / multiple / parallel / irrelevance；**AST 匹配**；规模适中、社区活跃——本章主战场之一。
- **ToolBench**（清华）：16000+ 真实 API 场景。
- **API-Bank**（微软）：53 个常用 API，侧重文档理解与调用。

#### （2）通用能力

- **GAIA**（Meta + HF）：466 个真实世界问题，Level 1/2/3；多步推理、工具、文件、浏览；**准精确匹配**——本章主战场之二。
- **AgentBench**（清华）：8 领域通用能力。
- **WebArena**（CMU）：真实网页环境任务。

#### （3）多智能体协作

ChatEval、SOTOPIA，以及业务自定义协作场景。

#### （4）常用指标族

- **准确性**：Accuracy、Exact Match、F1
- **效率**：Response Time、Token Usage
- **鲁棒性**：Error Rate、Failure Recovery
- **协作**：Communication Efficiency、Task Completion

### 12.1.3 HelloAgents 评估体系设计

本章聚焦三条线：

1. **BFCL**：函数调用准确性（数据集适中、指标清晰）
2. **GAIA**：综合问题解决（任务真实、难度分级）
3. **数据生成质量**：LLM Judge、Win Rate、人工验证（完整体验「用 Agent 造数据再评数据」）

架构上是经典三层：**Dataset（数据）→ Evaluator（执行）→ Metrics（指标）**，再封装成 Tool。图 12.1（原书）给出了整体构建思路。

## 12.2 BFCL：工具调用能力评估

### 12.2.1 BFCL 基准介绍

工具调用四步：理解需求 → 选工具 → 填参数 → 处理复杂场景（多函数 / 并行 / 无关）。

#### 四个类别（难度递增）

| 类别 | 测什么 |
|------|--------|
| Simple | 单函数正确调用 |
| Multiple | 多函数规划与调用 |
| Parallel | 可并行的多调用（集合匹配，顺序可不同） |
| Irrelevance | **该不该**调用工具 |

评估流程：加载数据 → 跑 Agent 得预测 → 解析为 AST → AST 匹配 → 汇总准确率（见图 12.2）。

#### 样本结构

关键字段：`question`（用户请求）、`function`（可用函数签名）、`ground_truth`（期望调用）。

#### AST 匹配：为什么比字符串强

$$\text{AST\_Match}(P,G)=\begin{cases}1 & \text{if AST}(P)\equiv\text{AST}(G)\\0 & \text{otherwise}\end{cases}$$

等价条件直觉：

1. **函数名**必须精确一致
2. **参数键值集合**相等（忽略顺序）
3. **参数值语义等价**（如 `2+3` ≡ `5`，引号风格可不同）

```text
✅ get_weather(city="Beijing", unit="celsius")
   vs get_weather(unit="celsius", city="Beijing")

✅ calculate(x=2+3) vs calculate(x=5)

❌ get_temperature(...) vs get_weather(...)
❌ city="Shanghai" vs city="Beijing"
```

#### 指标怎么读

- **Accuracy / AST Match Rate**：匹配成功比例
- **Category-wise Accuracy**：各类别准确率
- **Weighted Accuracy**：按难度加权
- **Error Rate**：1 − Accuracy

读数：`0.8` ≈ 80% 样本正确。先看总体，再拆类别找薄弱点。

官方 CLI（`bfcl evaluate`）使用官方 AST 算法，结果可与排行榜对齐。

### 12.2.4 BFCL 官方评估工具集成

四步对齐排行榜（图 12.3）：

1. 加载 BFCL v4 数据
2. HelloAgents 跑预测
3. 导出 JSONL 到 `evaluation_results/bfcl_official/`，并复制到 `result/{model_name}/`
4. `bfcl evaluate --partial-eval` 出权威分

默认 `run_official_eval=True`。需要手动控制时设 `False`，再自行调用 CLI / `generate_report`。

### 12.2.5 核心组件实现细节

| 组件 | 职责 | 关键点 |
|------|------|--------|
| BFCLDataset | 加载数据 | 本地优先，否则 HF |
| BFCLEvaluator | 执行评估 | 构 Prompt → run → 提取调用 → AST 对比 |
| BFCLMetrics | 算指标 | accuracy / 参数准确率 / 分类统计 |
| BFCLEvaluationTool | Tool 封装 | 参数校验 + JSON 结果 |

提取函数调用要兼容 **JSON、代码块、纯文本**——这是工程上最容易踩坑的地方。AST 匹配实现上常把参数字典拼成虚拟 `func(...)` 再 `ast.parse` 比较。

### 12.2.6 扩展与优化建议

**当前局限**：教学用 SimpleAgent 的 `[TOOL_CALL:...]` 格式，复杂场景往往不如原生 Function Calling。

**提分方向**：原生函数调用模型 / 更好提示词；按数据集预置常用工具；针对 multiple/parallel/irrelevance 设计策略。

**实践节奏**：

```python
# 渐进式
r1 = bfcl_tool.run(agent, category="simple_python", max_samples=5)
if r1["overall_accuracy"] > 0.8:
    r2 = bfcl_tool.run(agent, category="simple_python", max_samples=50)
# 多类别 / 对比提示词配置同理
```

成绩好可按 Gorilla `CONTRIBUTING.md` 准备材料提交官方排行榜。

## 12.3 GAIA：通用 AI 助手能力评估

### 12.3.1 GAIA 基准介绍

**设计理念**：真实世界问题需要多种能力综合——多步推理、知识、多模态、网页浏览、文件操作。BFCL 像专项；GAIA 像综合路考。

样本关键字段：`Question`、`Level`(1–3)、`Final answer`、附件路径、`Annotator Metadata`（步骤、工具等）。

#### 准精确匹配（Quasi Exact Match）

先归一化 \(\mathcal{N}(\cdot)\)，再精确相等：

| 类型 | 规则示例 |
|------|----------|
| 数字 | `$1,234.56` → `1234.56`（去单位与千分位） |
| 字符串 | 小写、去 the/a/an、去多余空格与末尾标点 |
| 列表 | 拆分 → 单元素归一化 → **字母序排序** 再拼接 |

#### 指标

- **Exact Match Rate**：准精确匹配成功比例
- **Level-wise Accuracy**：各级准确率
- **Drop Rate**：\((\text{Acc}_\ell-\text{Acc}_{\ell+1})/\text{Acc}_\ell\) —— 难度升高时掉多少
- **Avg Steps**：正确样本平均推理步数

示例直觉：整体 70%；L1=100%、L2=67%、L3=50% → Drop 1→2 约 33%。下降率大 = 复杂任务能力衰减明显。

#### 官方 System Prompt（必须）

要求以 `FINAL ANSWER: [YOUR FINAL ANSWER]` 结束；数字勿加千分位与单位；字符串少冠词与缩写；列表逗号分隔。

### 12.3.2 获取 GAIA 数据集

**重要**：GAIA 是 **Gated Dataset**。

1. 在 HF 申请 `gaia-benchmark/GAIA` 访问
2. `.env` 写 `HF_TOKEN=hf_...`
3. `GAIADataset(level=1, split="validation").load()` 自动缓存到 `./data/gaia/`

validation 约 165 题（级别分布约 L1:53 / L2:62 / L3:50），含图片/PDF 等附件。也可 `snapshot_download` 手动下载。

### 12.3.3 在 HelloAgents 中实现 GAIA 评估

#### 方式 2：GAIADataset + GAIAEvaluator

### 12.3.5 核心组件实现细节

## 12.4 数据生成质量评估

高质量训练/测试数据是系统上限。本节以 **AIME 风格数学题** 为例（答案为 0–999 整数、多步推理、难度中等），参考数据集如 `TianHongZXY/aime-1983-2025`（900+ 真题）。

### 12.4.1 评估方法概述

三种互补方法（图 12.5）：

| 方法 | 角色 | 典型输出 |
|------|------|----------|
| LLM Judge | 绝对多维打分 | 均分 / 通过率 / 优秀率 |
| Win Rate | 相对真题对比 | Win / Loss / Tie |
| 人工验证 | 最终质量把关 | approved / rejected / needs_revision |

#### LLM Judge 四维（1–5）

正确性 · 清晰度 · 难度匹配 · 完整性。

- **Average Score**：样本四维均值再平均
- **Pass Rate**：均分 ≥ 3.5
- **Excellent Rate**：均分 ≥ 4.5

#### Win Rate

成对比较生成题 vs 真题（图 12.6）。**理想 Win Rate ≈ 50%**。显著偏低 → 优化生成；显著偏高 → 警惕评委偏差或「看起来更花哨」。

#### 人工验证

阅读题目/答案/解答 → 四维打分 → 标状态 → 写评论。数学逻辑严密性上，自动化评委仍可能漏判。

### 12.4.3 AIME 题目生成器实现

要点：

- 从 900+ 真题随机抽参考样例（风格参考，要求生成完全不同题）
- **英文生成**：与真题一致、评估公平、国际化、避免翻译误差
- 输出 JSON：`problem` / `answer`(0–999) / `solution` / `topic`
- 批量生成：tqdm + API 延迟；检查点清理
- **LaTeX 坑**：`\frac` 等反斜杠在 JSON 非法，需正则转成合法转义后再 `json.loads`

### 12.4.4 LLM Judge 评估工具

流程：加载生成数据 → 加载参考年真题 → `LLMJudgeEvaluator.evaluate_batch` → 导出结果与报告。

评委 Prompt 要求输出四维分数 + comments 的 JSON。报告示例常见：均分 4.2、通过率 85%、优秀率 40%。

### 12.4.5 Win Rate 评估工具

`AIDataset` 支持 `generated`（本地 JSON）与 `real`（如 `math-ai/aime25`）。选择 AIME 2025 的原因：时效、维护简单、格式统一、30 题足够做相对评估。

对比 Prompt 输出 `winner: A|B|Tie` + reason。报告解读：差距 <10% 可视为接近参考水平。

### 12.4.8 综合评估报告与实践建议

综合报告通常包含：主题分布、Judge 各维、Win Rate 表、结论与下一步（人工验证）。

**建议门槛（可按项目调整）**：

- LLM Judge 均分 ≥ 4.0
- Win Rate ≥ 45%（接近 50%）
- 通过率 ≥ 80%
- 人工验证通过率 ≥ 90%

**工程经验**：生成间隔 2–3 秒防限流；先 10 条试跑再批量；低分题聚类分析后改 Prompt；Judge 与 Win Rate 结合使用，人工做最终闸门。
