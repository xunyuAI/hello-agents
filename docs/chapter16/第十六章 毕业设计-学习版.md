### 几个关键词，先抓牢

- **Co-creation-projects**：官方仓库里放学员毕业作品的目录。
- **命名规范**：`{GitHub用户名}-{项目名称}`，如 `jjyaoao-CodeReviewAgent`。
- **必须交付**：可运行 Notebook/脚本 + `requirements.txt` + `README.md`。
- **PR 标题**：`[毕业设计] 项目名称 - 简短描述`。
- **大文件规范**：主仓建议总大小 ≤ 5MB；视频/大数据/模型走外链或独立资源仓。
- **MVP**：最小可演示版本——先跑通一条主路径，再谈扩展。
- **工具 + LLM 分工**：确定性、可验证的事交给工具；语义理解与建议交给 LLM（见 16.6）。

## 16.1 毕业设计的意义

### 16.1.1 为什么要做毕业设计

学习技术最好的方式不是再看一遍教程，而是**动手实践**。真正的挑战是：

- 如何把知识应用到**实际问题**？
- 如何设计一个**完整系统**？
- 如何处理**边界与异常**？

毕业设计的核心价值：培养**综合应用能力**——把智能体范式、工具系统、记忆机制、通信协议等，**有选择地**整合进一个完整项目（不必章章用满）。

**期望收获：**

| 能力 | 具体表现 |
|------|---------|
| 独立设计 | 能从痛点推到架构与 MVP 范围 |
| 框架熟练 | 会用 HelloAgents 搭 Agent + 工具 |
| 工程协作 | 掌握 Git / Fork / PR / Review |
| 文档表达 | README 让陌生人能跑通 |
| 作品沉淀 | `Co-creation-projects` 里有可展示条目 |

### 16.1.2 毕业设计的形式

以**开源项目**形式提交到 Hello-Agents 的 `Co-creation-projects/`。

| 项 | 要求 |
|----|------|
| 命名 | `{GitHub用户名}-{项目名称}` |
| 必须 | 可运行 `.ipynb` 或脚本 · `requirements.txt` · `README.md` |
| 可选 | 演示视频、截图、小规模数据 |
| 提交 | GitHub Pull Request |
| 评审 | 社区 review → 修改 → 合并 |

**小作品也值得提交。** 创意不必宏大——自己动手、能跑通、文档清楚，就符合共创精神。

### 16.1.3 成功标准（心里有数）

Reviewer 大致会看：

1. **能不能跑**：按 README 操作，主路径无致命报错。  
2. **是不是 Agent 应用**：有工具 / 多步推理 / 明确系统角色，而非「调一次 LLM」。  
3. **仓库是否干净**：命名对、体积可控、依赖可复现。  
4. **文档是否诚实**：写清限制、密钥配置、已知问题。

## 16.2 项目选题指南

### 16.2.1 选题原则

1. **实用性**：解决真实问题，不为技术而技术。  
2. **可完成性**：有限时间资源内可交付（先 MVP）。  
3. **可展示性**：清晰体现能力，别人能跑通、看懂。

三原则可记成一句话：**真痛点 × 两周能做完 × 别人看得懂。**

### 16.2.2 推荐选题方向（五类）

**（1）生产力工具**：代码审查、文档生成、会议助手、邮件助手  

**（2）学习辅助**：学习伙伴、论文助手、编程导师、语言学习助手  

**（3）创意娱乐**：故事生成、游戏 NPC、音乐推荐、菜谱助手  

**（4）数据分析**：数据分析师、股票/舆情（注意合规）、竞品分析  

**（5）生活服务**：健康、理财、购物、智能家居（可用模拟设备起步）

选方向时问自己：我最熟悉哪类用户故事？手头有没有可公开的小样例数据？

### 16.2.3 选题示例：CodeReviewAgent

- **问题**：人工审查慢且易漏；静态分析难懂语义。  
- **功能（可裁剪）**：质量分析、潜在 bug、性能建议、安全扫描、最佳实践。  
- **成果**：可运行 Notebook、主流语言样例、Markdown 审查报告与改进建议。

**迁移公式**：真问题 → 哪些步骤适合「确定性工具」→ 哪些适合 LLM → 一条可演示主路径。

### 16.2.4 选题反例（尽量避开）

| 反例 | 为什么难过审 |
|------|-------------|
| 「做一个通用超级 Agent」 | 范围无限，两周做不完 |
| 必须上传未授权爬虫数据 | 合规与版权风险 |
| 主仓塞进完整大模型权重 | 体积爆炸，违反大文件规范 |
| 单次 `llm.chat()` 无工具 | 更像 Demo 调用，不像 Agent 应用 |
| 医疗诊断结论 / 投资承诺 | 强合规，教学项目易踩雷 |

### 选题自检（开工前 1 分钟）

- [ ] 解决我或身边人的真实痛点  
- [ ] 两周内能做出可演示 MVP  
- [ ] 确实需要 Agent/工具/多步推理（不是单次问答）  
- [ ] 不依赖未公开超大数据/权重进主仓  
- [ ] 不涉及未授权爬取或强合规风险场景

## 16.3 开发环境准备

### 16.3.1 安装必要工具

```bash
pip install "hello-agents[all]"

git --version
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"

# 推荐 SSH
ssh-keygen -t ed25519 -C "你的邮箱"
# 公钥加到 GitHub → Settings → SSH and GPG keys
ssh -T git@github.com

pip install jupyterlab
jupyter lab
```

**提示**：密钥不要写进仓库；用 `.env` + `.env.example`，并把 `.env` 放进 `.gitignore`。

### 16.3.2 Fork · 克隆 · 分支

1. 打开 [datawhalechina/hello-agents](https://github.com/datawhalechina/hello-agents) → **Fork**（图 16.1）。  
2. 克隆自己的 Fork，并加 `upstream`（图 16.2）：

```bash
git clone git@github.com:你的用户名/hello-agents.git
cd hello-agents   # 以实际目录名为准
git remote add upstream https://github.com/datawhalechina/hello-agents.git
git remote -v

git checkout -b feature/你的项目名称
# 例：git checkout -b feature/code-review-agent
```

| 远程名 | 指向 | 用途 |
|--------|------|------|
| `origin` | 你的 Fork | 日常 push |
| `upstream` | 官方仓 | 同步主线更新 |

### 16.3.3 项目目录结构

```bash
cd Co-creation-projects
mkdir 你的用户名-项目名称
```

推荐结构：

```
jjyaoao-CodeReviewAgent/
├── README.md
├── requirements.txt
├── main.ipynb
├── .env.example          # 推荐：密钥占位说明
├── .gitignore            # 推荐：忽略 .env / 大文件
├── data/                 # 可选：小样例（建议 <1MB）
├── outputs/              # 可选：报告/截图
└── src/                  # 可选：agents / tools / utils
```

**原则**：别人打开 README 就能装依赖、跑通主 Notebook，并看懂「解决了什么问题」。

## 16.4 项目开发指南（施工核心）

> 本节对应原书 16.4，也是互动教程侧栏 **「16.4 项目开发指南」** 专节的细读版。  
> 建议按：**开发步骤 → README → 依赖 → Notebook → 测试清单 → 大文件** 顺序推进。

### 16.4.0 端到端开发步骤（建议节奏）

不要一上来就写复杂 Agent。按下面六步走，返工最少：

```
① 定 MVP 一句话
    ↓
② 建目录 + README 骨架 + requirements 占位
    ↓
③ 写 1～2 个确定性工具（可单测）
    ↓
④ 接 HelloAgents：LLM + Agent + system prompt
    ↓
⑤ 主路径演示（样例 in → 结果 out）
    ↓
⑥ 对照测试清单 + 处理大文件 → 准备 PR
```

**两周节奏参考（可压缩）：**

| 阶段 | 做什么 | 完成标志 |
|------|--------|---------|
| D1–D2 | 选题定界、Fork、目录、README 空壳 | 目录命名正确，README 有「怎么跑」标题 |
| D3–D5 | 工具 + Agent 主路径 | `agent.run` 对样例有合理输出 |
| D6–D8 | 第二场景、异常处理、注释 | Notebook 七段齐，输出可复现 |
| D9–D10 | 清单自检、大文件外置、开 PR | 按 README 在干净环境能跑 |

### 16.4.1 编写 README

README 是项目门面。建议至少包含：

| 区块 | 写什么 |
|------|--------|
| 简介 | 解决什么问题、特色、适用场景 |
| 核心功能 | 勾选列表（已实现打 ✅） |
| 技术栈 | HelloAgents 范式、工具、外部 API |
| 快速开始 | 环境要求 · 安装 · `.env` · 运行命令 |
| 使用示例 | 最短可复制路径 + 预期结果 |
| 亮点 / 评估 / 计划 | 可选但加分 |
| 贡献 · 许可证 · 作者 · 致谢 | 规范收尾 |

**门面原则**：Reviewer 通常先读 README；写不清「怎么跑」，代码再好也难合并。

**骨架模板（可直接粘贴改写）：**

```markdown
# 项目名称

> 一句话描述你的项目

## 项目简介
- 解决什么问题？
- 有什么特色功能？
- 适用于什么场景？

## 核心功能
- [x] 功能1
- [ ] 功能2（计划中）

## 技术栈
- HelloAgents（如 SimpleAgent + ToolRegistry）
- 其他依赖 / API

## 快速开始
### 环境要求
- Python 3.10+

### 安装依赖
pip install -r requirements.txt

### 配置 API 密钥
cp .env.example .env
# 编辑 .env，填入密钥

### 运行
jupyter lab
# 打开 main.ipynb 并运行

## 使用示例
（最短步骤 + 预期输出位置，如 outputs/xxx.md）

## 项目亮点 / 未来计划 / 作者 / 致谢
```

完整加长模板见原书 16.4.1。

### 16.4.2 requirements.txt

只列真实依赖，尽量给版本下界：

```txt
# 核心
hello-agents[all]>=0.2.7

# 按需
matplotlib>=3.7.0
plotly>=5.14.0
fastapi>=0.109.0
uvicorn>=0.27.0
python-dotenv>=1.0.0
```

**易错点：**

- 漏掉你 Notebook 里 `import` 过的包。  
- 写「全世界所有包」——反而难装、难审。  
- 不写版本 → 三个月后依赖漂移，别人复现失败。

### 16.4.3 Jupyter Notebook 七段式

| # | 部分 | 要点 |
|---|------|------|
| 1 | 项目介绍 | 目标、作者、日期 |
| 2 | 环境配置 | 安装、import、密钥 |
| 3 | 工具定义 | 自定义 Tool：name / description / run |
| 4 | 智能体构建 | LLM + Agent + 注册工具 + system prompt |
| 5 | 功能演示 | 基础 + 稍复杂场景 |
| 6 | 性能评估 | 可选：准确率 / 耗时 / 抽检 |
| 7 | 总结与展望 | 已完成、踩坑、下一步 |

**最小代码骨架（示意）：**

```python
# 2. 环境
from hello_agents import SimpleAgent, HelloAgentsLLM
from hello_agents.tools import BaseTool  # 或项目所用 Tool API
from dotenv import load_dotenv
load_dotenv()

# 3. 工具：确定性逻辑放这里
class CustomTool(BaseTool):
    name = "tool_name"
    description = "工具描述"
    def run(self, query: str) -> str:
        # TODO: 可验证的计算 / 解析 / 检查
        return "结果"

# 4. Agent：语义理解与组织报告放这里
llm = HelloAgentsLLM()
agent = SimpleAgent(
    name="智能体名称",
    llm=llm,
    system_prompt="说明：先调工具，再基于结果给建议"
)
agent.add_tool(CustomTool())

# 5. 演示
print(agent.run("用户输入 / 样例任务"))
```

完整七段注释版见原书 16.4.3；实战对照见 16.6 的 CodeReviewAgent。

### 16.4.4 提交前测试清单

提交前请逐项确认：

- [ ] 能跑无报错  
- [ ] README 完整（尤其「快速开始」）  
- [ ] 依赖齐全且可安装  
- [ ] 有使用示例（输入 → 输出路径清晰）  
- [ ] 适当注释（关键逻辑有说明）  
- [ ] 输出符合预期  
- [ ] 常见异常有处理（空输入、语法错、缺密钥）  
- [ ] 结构与命名规范（`{user}-{Project}`）  
- [ ] 大文件已妥善处理  

**为什么每项都重要（速记）：**

| 清单项 | Reviewer 视角 |
|--------|----------------|
| 能跑 | 合并不该变成「帮你调试环境」 |
| README | 决定别人愿不愿花时间试 |
| requirements | 决定能不能复现 |
| 示例 | 决定「功能是否可信」 |
| 异常 | 决定像不像完整应用 |
| 大文件 | 决定会不会拖垮主仓 |

### 16.4.5 大文件处理

**限制**：项目总大小建议不超过 **5MB**；禁止直接提交视频、大型数据集、模型文件。

| 方案 | 做法 |
|------|------|
| 外链（推荐） | 网盘/Drive/Kaggle/HF；视频放 B 站/YouTube；README 写清步骤 |
| 独立资源仓 | 另建 `*-resources`，主仓只放代码与说明 |
| 小样例 | 主仓仅保留 &lt;1MB 样例，完整集外链 |

推荐平台速查：

- **数据集**：百度网盘、Google Drive、Kaggle、HuggingFace Datasets  
- **视频**：B 站、YouTube、腾讯视频  
- **模型**：HuggingFace Models、ModelScope  

配合 `.gitignore`，至少忽略：

```gitignore
.env
__pycache__/
*.pyc
.ipynb_checkpoints/
data/large/
*.pt
*.bin
*.mp4
```

README 中应写清：示例数据在哪、完整数据怎么下、下完放到哪个目录。

### 16.4.6 常见翻车点（开发期避坑）

1. **先写一堆 Prompt，后补工具** → 主路径不稳；应先工具可测，再接 Agent。  
2. **README 最后才写** → 容易漏步骤；建议第一天就写「快速开始」空壳。  
3. **密钥写进 Notebook 并 push** → 立即轮换密钥；改用 `.env`。  
4. **演示依赖私有数据** → 换成可公开小样例，否则 reviewer 无法复现。  
5. **功能贪多** → MVP 一条主路径胜过五个半成品。  

### 16.4.7 开发期总检查清单（开 PR 前再过一遍）

- [ ] 目录名 = `{GitHub用户名}-{项目名称}`  
- [ ] 有 `README.md` / `requirements.txt` / 可运行入口  
- [ ] `.env.example` 有字段说明，`.env` 未入库  
- [ ] Notebook/脚本按七段或等价结构可读  
- [ ] 至少一条端到端演示（样例 → 输出文件或打印）  
- [ ] `git status` 无意外大文件  
- [ ] 本地按 README 从零走通一遍

## 16.5 提交 Pull Request

### 16.5.1 提交到 GitHub

```bash
git status
git add Co-creation-projects/你的用户名-项目名称/
git commit -m "feat: 添加XXX毕业设计项目"
git push origin feature/你的项目名称
```

常用 type：`feat`（毕业设计用这个）· `fix` · `docs` · `style` · `refactor` · `test` · `chore`。

**建议**：`git add` 指定项目目录，避免把无关本地文件带进 PR。

### 16.5.2 创建 PR

- **Base**：`datawhalechina/hello-agents` · `main`  
- **Compare**：你的 Fork · `feature/…`  
- **标题（强制）**：`[毕业设计] 项目名称 - 简短描述`

示例：

- `[毕业设计] CodeReviewAgent - 智能代码审查助手`

### 16.5.3 响应 Review

看评论 → 改代码 → 同分支再 push → 在 PR 下回复说明。不要丢弃讨论另开无关 PR。

```bash
git add .
git commit -m "fix: 根据review意见修改XXX"
git push origin feature/你的项目名称
```

协作心态：Review 是帮你把作品变好，不是考试打分。每条意见尽量「改完 + 回复」。

## 16.6 示例项目展示：CodeReviewAgent

- **作者**：@jjyaoao  
- **路径**：`Co-creation-projects/jjyaoao-CodeReviewAgent/`  

**结构要点**：`README.md` · `requirements.txt` · `main.ipynb` · `.env.example` · `.gitignore` · `data/sample_code.py` · `outputs/review_report.md`

**设计要点：**

| 组件 | 职责 | 为何不交给「纯 LLM」 |
|------|------|----------------------|
| `CodeAnalysisTool` | AST 统计函数/类/行数，语法错误友好返回 | 结构统计应精确、可复现 |
| `StyleCheckTool` | 行宽与缩进等 PEP 8 启发式 | 规则检查稳定、便宜 |
| `SimpleAgent` + `ToolRegistry` | 先调工具再写 Markdown 报告 | LLM 负责语义与建议组织 |

主路径：读样例 → `agent.run` → 写入 `outputs/review_report.md`。

**可迁移一句话**：工具做可计算、可验证的事；LLM 做语义理解与建议。

把「代码」换成「会议记录 / 论文摘要 / 菜谱食材」，工具与 Agent 的分工模式仍然成立。

完整代码与 README 模板见原书 `docs/chapter16/第十六章 毕业设计.md` 第 16.6 节。
