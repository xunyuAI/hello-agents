为何智能体需要记忆与 RAG

8.1.2 · 两大根本局限

局限一 · 无状态遗忘

  • 每次 API 调用彼此独立
  • 上下文窗口挤掉早期信息
  • 无法记住偏好与习惯
  • 难从成败经验中学习
  • 多轮可能前后矛盾

局限二 · 知识静态

  • 训练数据有截止时间
  • 专业领域深度不足
  • 幻觉：编造看似合理的内容
  • 缺来源 → 可信度弱
记忆解决「上次聊过啥」；RAG解决「书里写了啥」。一个管对话经历，一个管外部知识库。

无状态有多尴尬？

8.1.2 · 代码演示

from hello_agents import SimpleAgent, HelloAgentsLLM agent = SimpleAgent(name="学习助手", llm=HelloAgentsLLM()) agent.run("我叫张三，正在学习Python，目前掌握了基础语法") # → 「很好！Python基础语法是编程的重要基础...」 agent.run("你还记得我的学习进度吗？") # → 「抱歉，我不知道您的学习进度...」

模型本身不会自动记住上次对话。要解决：引入记忆系统（外挂存储 + 检索回填）。

把整段历史塞进 Prompt 也能「假装有记忆」，但窗口有限、贵、且难做个性化持久化——故需要专门 Memory。

RAG：开卷考试

8.1.2 · 定义

生成前先从外部知识库查出相关段落，塞进提示词，再让 LLM 作答——更准、可溯源。

检索 Retrieval

从文档/库中找相关片段

增强 Augmented

把片段写进 Prompt 当依据

生成 Generation

LLM 基于依据写答案

收益

时效、专业深度、减幻觉、可解释

闭卷靠背训练语料；RAG 是开卷——先翻书再答题。

为何与 Memory 共享嵌入？
同一套向量空间便于「检索结果写入记忆」时语义一致；也减少重复依赖。

MemoryTool：统一入口

8.2.3 · execute(action)

「统一入口，分发处理」——Agent 只记工具名 memory。

addsearchsummary statsupdateremove forgetconsolidateclear_all
def execute(self, action: str, **kwargs) -> str: if action == "add": return self._add_memory(**kwargs) elif action == "search": return self._search_memory(**kwargs) # ...

add：编码一条记忆

8.2.3 (1)

关键参数：content、memory_type（默认 working）、importance（0–1，默认 0.5）、感知可用 file_path/modality。

  • 自动 session_id（session_YYYYMMDD_HHMMSS）
  • perceptual + file_path → 推断 modality
  • 写入 timestamp / importance
memory_tool.execute("add", content="...", memory_type="episodic", importance=0.9, event_type="document_loaded")

四种类型怎么 add？

元数据示例

working
临时问答上下文，importance 可偏低（如 0.5–0.6）。
episodic
event_type、location、session_id —— 事件相册。
semantic
knowledge_type="factual" 或偏好规则。
perceptual
modality="image" + file_path。

search：按需提取

8.2.3 (2)

参数：query、limit、memory_type(s)、min_importance。底层 retrieve_memories。

展示常带类型中文标签 + 内容预览约 80 字 + importance，方便 Agent/人阅读。

forget：三种遗忘策略

8.2.3 (3)

strategy含义关键参数
importance_based删低于阈值threshold 如 0.2
time_based删超过天数max_age_days 如 30
capacity_based超限删最不重要threshold 如 0.3
遗忘不是缺陷，是资源管理——大脑也在持续清理。

consolidate：短期→长期

8.2.3 (4)

默认：working → episodic，importance ≥ 0.7；也可 episodic → semantic（阈值可更高，如 0.8）。

模拟记忆固化：重要的短期痕迹在「睡眠/复盘」后进入长期库。
memory_tool.execute("consolidate", from_type="working", to_type="episodic", importance_threshold=0.7)

完整生命周期

创建→…→清理

add → search → summary/stats → update/remove → forget → consolidate → clear_all

另有 summary / stats / update / remove / clear_all，构成运维闭环。

WorkingMemory · 短期便签

8.2.5 (1)

  • 纯内存 · 容量默认 50 · TTL 默认约 60 分钟
  • 重启即丢——符合「临时」
  • 检索：TF-IDF + 关键词混合（向量 0.7 + 关键词 0.3）
(相似度 × 时间衰减) × (0.8 + 重要性 × 0.4)
像浏览器标签：关了就没；重要页请收藏（consolidate）。

WorkingMemory.add / retrieve

实现要点

add: 先 _expire_old_memories；满则 _remove_lowest_priority_memory retrieve: TF-IDF 向量分 + 关键词分 → 时间衰减 → 重要性权重

无向量时退回纯关键词，保证极简环境也能用。

EpisodicMemory · 事件相册

8.2.5 (2)

  • SQLite：结构化与复杂查询
  • Qdrant：语义向量
  • sessions 索引：按会话回顾
(向量×0.8 + 近因性×0.2) × (0.8 + 重要性×0.4)

流程：结构化预过滤 → 向量检索 → 综合评分。

情景记忆为何要近因性？

设计意图

「昨天刚发生的事」往往比三年前更相关——情景像日记，越近越热。

对象 Episode：episode_id, session_id, timestamp, content, context。

SemanticMemory · 知识图谱

8.2.5 (3)

添加：嵌入 → 抽实体/关系（spaCy）→ Neo4j → Qdrant。

检索：向量 + 图搜索 → 混合排序。

(向量×0.7 + 图×0.3) × (0.8 + 重要性×0.4)
重要性权重落在 [0.8, 1.2]，避免「重要」压过「相关」。

向量 0.7 · 图 0.3 的意图

必理解

向量主通道

先保证「说的是一回事」——语义相关

图补关系

挖隐含关联、多跳路径——纯向量难做

向量像全文搜索；图像「张三→就职→某公司→位于→某城」的推理链。

PerceptualMemory · 多模态

8.2.5 (4)

  • 文本 / 图像(CLIP) / 音频(CLAP) 分集合，避免维度错配
  • 同模态精确匹配；跨模态靠统一语义空间
  • 评分形同情景：向量 0.8 + 近因 0.2，再乘重要性
recency = exp(-0.1 * age_hours / 24) # 最低约 0.1，模拟遗忘曲线

update / remove / clear_all

  • remove：按 id 精确删除
  • clear_all：清空——危险操作，多用户场景慎用
remove 是点杀；forget 是策略批量清理；clear_all 是整库重置。

维度陷阱

文本向量、CLIP 图像向量、CLAP 音频向量维度与空间不同。硬塞同一集合会导致检索错乱。

perceptual_text / perceptual_image / perceptual_audio

RAGTool action

rag_tool.execute("ask", question=..., limit=5, enable_advanced_search=True, enable_mqe=True, enable_hyde=True)

search_vectors_expanded

分块重叠防什么？

工程直觉

若在句子中间硬切，检索到的块会缺主语/结论。overlap_tokens 让相邻块共享边界上下文。

块太大

噪声多、塞满上下文

块太小

语义破碎、难回答

_prompt_mqe 在干什么？

8.3.5 代码

system: 你是检索查询扩展助手。生成语义等价或互补的多样化查询。 user: 原始查询：{query} · 请给出 n 个不同表述，每行一个。

失败则回退为原查询——保证检索链路不因 LLM 故障中断。

_prompt_hyde 在干什么？

8.3.5 代码

system: 根据用户问题，先写一段可能的答案性段落，用于向量检索。 user: 问题：{query} · 请直接写中等长度、客观、含关键术语的段落。
