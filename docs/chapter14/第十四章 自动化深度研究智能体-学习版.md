在第十三章的旅行助手项目中，我们体验了如何把 HelloAgents 做成一个「能用的多智能体产品」。本章换赛道，聚焦**知识密集型应用**：构建一个能自动化执行深度研究任务的智能体助手。

旅行规划关心「路线是否可行」；深度研究关心「事实是否可核验」。信息会不断发散、事实会快速更新，用户还特别在意引用来源。所以本章要交付的不是「搜一下给个答案」，而是一份**可追溯的研究报告**。

为了做到这一点，系统需要三项核心能力：

1. **问题剖析**：把用户的开放主题拆成可检索的查询语句。
2. **多轮信息采集**：结合不同搜索 API 持续挖掘，并去重整合。
3. **反思与总结**：依据阶段结果识别知识空白，决定是否继续检索，并生成结构化总结。

## 读这一章之前，先建立心智模型

### 一个生活比喻

把深度研究助手想成「带助理的论文写作流程」：

| 人类做法 | 系统对应 |
|---------|---------|
| 先列提纲，决定要搞清哪几块 | TODO Planner |
| 按提纲逐节搜资料、做笔记 | Search + Summarizer + NoteTool |
| 最后统稿、加参考文献 | Report Writer |
| 写作过程随时告诉你进展 | SSE 推送到前端 |

传统搜索像「打开浏览器漫无目地点链接」；TODO 驱动像「先提纲后执行」，每一步都有输入输出，出了问题也知道卡在哪一环。

### 几个关键词，先抓牢

- **TODO 驱动研究**：把复杂主题拆成 3–5 个子任务，再规划→执行→整合。
- **子任务三字段**：`title`（标题）、`intent`（为何研究）、`query`（搜索查询，可用英文提高召回）。
- **三 Agent**：Planner / Summarizer / Report Writer，专而简单。
- **ToolAwareSimpleAgent**：在 `SimpleAgent` 上加工具调用监听，方便日志与前端进度。
- **服务层**：Planning / Summarization / Reporting / Search —— 连接 Agent 与工具的业务胶水。
- **SSE**：服务器单向推送事件流，用于实时进度，而不是整页刷新。

### 新手易混点（读前先扫一眼）

| 容易混淆 | 正确理解 |
|---------|---------|
| 「深度研究 = 一次大 Prompt 让模型写长文」 | 深度研究是流水线：拆题 → 搜证 → 笔记 → 统稿，证据来自网页 |
| 「Agent 直接调搜索就行，何必 SearchService」 | 中间层负责选引擎、去重、截断、降级、缓存；Agent 专心读材料 |
| 「ToolAware 让模型更聪明」 | 它不改推理能力，只加**可观测钩子**（谁调了什么工具） |
| 「SSE = WebSocket」 | SSE 是**单向**服务器推送；WebSocket 双向。本章用 SSE 够用 |
| 「NoteTool 只是记笔记好玩」 | 落盘是为了可恢复、可审计、可复盘质量 |

## 14.1 项目概述与架构设计

> **本节目标**：弄清「为什么做深度研究助手」、四层怎么叠、一次请求怎么走，并先跑通项目建立产品直觉。

### 14.1.1 为什么需要深度研究助手

信息爆炸时代，了解新技术/概念/事件时，传统方式常见三个痛点：

1. **信息过载**：搜索结果成千上万，人工点开成本极高。  
2. **缺少结构**：即使找到相关内容，也往往是碎片，难成系统。  
3. **重复劳动**：每次都要「搜索→阅读→总结→整理」，流程无法沉淀。

深度研究助手的目标不是替代你思考，而是把重复劳动自动化，并留下可验证痕迹。它不只是「再包一层搜索框」，而是能**自主规划、执行、总结**的研究助手。

**核心价值（对照原书）：**

1. **省时间**：1–2 小时压缩到约 5–10 分钟（视主题与引擎而定）。  
2. **提质量**：系统化流程，减少遗漏。  
3. **可追溯**：保留搜索结果与来源，方便核验引用。  
4. **可扩展**：可继续加搜索引擎、数据源、分析工具。

**和旅行助手比一眼：**

| 维度 | 第十三章旅行助手 | 本章深度研究 |
|------|------------------|--------------|
| 核心交付 | 可执行行程 JSON | 带引用的研究报告 |
| 外部依赖 | 地图 / 天气 / 酒店 | 多搜索引擎 |
| 质量标准 | 路线合理、字段完整 | 事实可核验、来源可点开 |
| 用户体验重点 | 地图与预算可视化 | 实时进度 + Markdown 报告 |

## 14.2 TODO 驱动的研究范式

> **本节目标**：把「研究」从模糊目标，变成「规划→执行→整合」的可调试流水线；掌握子任务三字段与三阶段 I/O。

### 14.2.1 什么是 TODO 驱动的研究

一句话：**把「研究」这个模糊目标，变成「规划→执行→整合」的可调试流水线。**

传统路径：

```
主题 → 搜索引擎甩一堆链接 → 人逐个点开记笔记 → 碎片信息
```

问题：每个链接只覆盖一面；缺系统结构；整理全靠人手。

TODO 驱动路径（对应图 14.5）：

```
主题
 → 规划：TODO1 基本信息 / TODO2 项目 / TODO3 文化 / TODO4 影响力
 → 执行：每个 TODO 搜 → 总结 → 记来源
 → 整合：结构化报告 + 参考文献
```

**三大核心要素：**

1. **智能规划器（TODO Planner）**：拆出 3–5 个子任务，并为每个写好 query。太少易漏，太多易冗余。  
2. **任务执行器（Task Executor）**：搜、提炼、去冗余、保引用（工程上由搜索服务 + 总结 Agent + 笔记工具协作）。  
3. **报告生成器（Report Writer）**：按逻辑组织、合并重复、挂来源。

整条流程是**线性**的，但每阶段 I/O 清晰——这正是易于理解与调试的原因。

**范式优势（原书归纳）：**

1. **可控**：每个子任务有明确目标与范围。  
2. **质量**：专门 Agent 守住各环节。  
3. **易调试**：可单任务复现失败。  
4. **可扩展**：增删 TODO 或调顺序成本低。

### 14.2.2 三阶段研究流程

#### （1）规划 Planning

- **输入**：研究主题 + 当前日期（利于「最新」检索）。  
- **输出**：JSON 子任务列表，每项含 `title` / `intent` / `query`。  
- **质量标准**：覆盖全面、逻辑清晰、查询精准、数量适中。

常见分解策略：基础概念 → 技术/组织现状 → 应用/项目 → 趋势/影响；必要时加对比。

示例（节选）：

```json
[
  {
    "title": "Datawhale的基本信息",
    "intent": "了解组织定位、成立时间、发展历程",
    "query": "Datawhale organization introduction history 2024"
  },
  {
    "title": "Datawhale的主要项目",
    "intent": "了解核心开源项目和教程",
    "query": "Datawhale projects tutorials open source 2024"
  }
]
```

**三字段为什么缺一不可？**

| 字段 | 给谁看 | 不做会怎样 |
|------|--------|------------|
| `title` | 人与报告标题 | 任务列表难以阅读 |
| `intent` | Summarizer / Writer | 总结偏题，只堆关键词 |
| `query` | SearchTool | 搜不到证据，后面全空转 |

`query` 常用英文，是因为不少网页与学术资料英文召回更好；`title`/`intent` 仍可用中文方便人读。

#### （2）执行 Execution

对每个子任务：

1. `SearchTool.run({input, backend, mode:"structured", max_results:5})`  
2. 取出 title / url / snippet  
3. 调用总结 Agent 生成带 `[1][2]` 引用的 Markdown  
4. `NoteTool` 落盘  

同时向前端推送 `status` / `task` 等 SSE 事件，让用户看见「正在搜索… / 任务已完成」。

总结质量要点（原书强调）：

- 提取核心观点，合并相似信息  
- 保留数字、日期、名称等关键数据  
- **每个观点挂来源引用**  

示例总结形态：

```markdown
## Datawhale的基本信息

Datawhale是一个专注于数据科学与AI领域的开源组织，成立于2018年[1]。
核心使命是「for the learner，和学习者一起成长」[2]。

## 来源
[1] https://github.com/datawhalechina
[2] https://datawhale.club/about
```

#### （3）报告 Reporting

- **输入**：全部子任务总结 + 主题  
- **输出**：Markdown 报告  

推荐骨架：

1. 标题  
2. 概述（2–3 段）  
3. 各子任务详细分析（二级标题）  
4. 总结（1–2 段）  
5. 参考文献（可按任务分组）  

报告 Agent 的职责是：按逻辑排序、消冗、统一格式、把引用汇总到参考文献区。

## 14.3 智能体系统设计（重点）

> **本节目标**：理解「为何要三 Agent」、各自 Prompt 与 I/O、ToolAware 监听钩子如何服务 SSE、DeepResearchAgent 如何顺序调度。

### 14.3.1 Agent 职责划分

第七章的 `SimpleAgent` 适合「单次问答 + 可选工具」。深度研究太长、太分叉：若塞进一个巨型 Prompt，会出现职责混乱、难调试、难单独优化某一环。因此本章采用**多智能体分工**（见表 14.1）。

设计原则一句话：**专而简单**——每个 Agent 只做一件事，Prompt 可以写得很「硬」。

| Agent | 角色隐喻 | 输入 | 输出 |
|-------|---------|------|------|
| TODO Planner | 开题前的头脑风暴 | 主题 + 日期 | JSON 子任务列表 |
| Task Summarizer | 读文献做笔记 | 任务元数据 + 搜索结果 | 带引用 Markdown |
| Report Writer | 统稿写报告 | 主题 + 多份总结 | 完整研究报告 |

#### Agent 1：TODO Planner（研究规划专家）

- **职责**：主题 → 3–5 个子任务 JSON。  
- **设计理念**：模拟人类开题前的 brainstorm：先看主题有哪些面，再落到可搜索的问题。  
- **Prompt 关键点**：  
  - 注入 `{current_date}` 与 `{research_topic}`  
  - 强调可搜索、有目标、彼此有逻辑（基础→应用→趋势）  
  - **只返回 JSON**（工程上仍要防夹带自然语言）  
  - 给出示例输出，降低格式漂移  

Prompt 骨架（对照原书，学习时抓住约束即可）：

```python
todo_planner_instructions = """
你是一个研究规划专家。将研究主题分解为3-5个子任务。
当前日期：{current_date}
研究主题：{research_topic}
每个子任务包含 title / intent / query。
请确保：数量3-5；彼此有逻辑；query 可检索；只返回JSON。
"""
```

**工程点**：`_extract_tasks` 用正则抽出 `[...]` 再 `json.loads`。模型常在 JSON 前后写「好的，我将…」，正则抽数组是标配。

```python
def _extract_tasks(self, response: str) -> List[dict]:
    json_match = re.search(r'\[.*\]', response, re.DOTALL)
    if json_match:
        return json.loads(json_match.group(0))
    raise ValueError("无法从响应中提取JSON")
```

创建 `TodoItem` 时再校验字段：

```python
for idx, item in enumerate(tasks_payload, start=1):
    if not all(k in item for k in ("title", "intent", "query")):
        raise ValueError(f"任务{idx}缺少必需字段")
    todo_items.append(TodoItem(id=idx, title=item["title"], ...))
```

#### Agent 2：Task Summarizer（任务总结专家）

- **职责**：搜索结果 → 结构化笔记。  
- **设计理念**：像人读完网页后写文献笔记，而不是复读 snippet。  
- **输出要求**：核心观点、关键数据（数字/日期/名称）、来源引用 `[1][2]`。  

实现上先 `_format_sources`，把每条结果编成：

```text
[1] 标题
URL: ...
摘要: ...
```

再填入 Prompt。这样模型引用编号时能对齐真实 URL。

```python
def _format_sources(self, search_results: List[dict]) -> str:
    parts = []
    for idx, r in enumerate(search_results, start=1):
        parts.append(
            f"[{idx}] {r['title']}\nURL: {r['url']}\n摘要: {r['snippet']}\n"
        )
    return "\n".join(parts)
```

> **质量直觉**：Summarizer 决定报告有没有「证据感」。若这里不强制引用，后面参考文献就会空心。

#### Agent 3：Report Writer（报告撰写专家）

- **职责**：多份总结 → 一篇完整报告。  
- **设计理念**：统稿官，不是再搜一遍。  
- **结构钉在 Prompt 里**：标题 / 概述 / 分节 / 总结 / 参考文献，比事后「修报告」稳得多。  

喂给 Writer 前，服务层会格式化：

```python
formatted.append(
    f"## 任务{idx}：{task.title}\n"
    f"意图：{task.intent}\n\n"
    f"{summary}\n"
)
```

Writer 再负责：逻辑排序、消冗、统一 Markdown、参考文献分组。

#### 为何不做成「一个超级 Agent」？

| 单 Agent 硬扛 | 三 Agent 分工 |
|--------------|---------------|
| Prompt 又长又脆 | 每环 Prompt 短而硬 |
| 失败难定位 | 可单环复现（规划失败 vs 总结失败） |
| 改一处牵全身 | 改 Planner 不影响 Writer |
| 难单独调温/模型 | 可为不同环选不同模型（进阶） |

### 14.3.2 ToolAwareSimpleAgent 的设计

深度研究需要**可观测性**：

1. **调试**：谁调了什么工具、参数是什么  
2. **日志**：全过程可回放  
3. **分析**：行为模式  
4. **进度**：前端实时显示「正在搜索 / 正在写笔记」

`SimpleAgent` 没有监听钩子，因此扩展为 `ToolAwareSimpleAgent`：在 `_execute_tool_call` 里，调用父类执行后，若存在 `tool_call_listener`，就把 `agent_name / tool_name / parsed_parameters / result` 回调出去。

**类比**：给每个扳手装上传感器——谁、何时、用了什么参数、结果如何，全部可观测。它**不改变**工具本身能力。

核心实现（对照原书）：

```python
class ToolAwareSimpleAgent(SimpleAgent):
    def __init__(self, name, system_prompt, llm,
                 tool_registry=None, tool_call_listener=None):
        super().__init__(name=name, system_prompt=system_prompt,
                         llm=llm, tool_registry=tool_registry)
        self._tool_call_listener = tool_call_listener

    def _execute_tool_call(self, tool_name: str, parameters: str) -> str:
        parsed_parameters = self._parse_parameters(parameters)
        result = super()._execute_tool_call(tool_name, parameters)
        if self._tool_call_listener:
            self._tool_call_listener({
                "agent_name": self.name,
                "tool_name": tool_name,
                "parsed_parameters": parsed_parameters,
                "result": result,
            })
        return result
```

使用示例：

```python
def tool_listener(call_info):
    print(call_info["agent_name"], call_info["tool_name"],
          call_info["parsed_parameters"])

agent = ToolAwareSimpleAgent(
    name="研究助手",
    system_prompt="你是一个研究助手",
    llm=llm,
    tool_call_listener=tool_listener,
)
```

在 `DeepResearchAgent` 里，三个服务共用同一个 listener，把工具事件转成 SSE：

```python
def tool_listener(call_info):
    self._emit_event({
        "type": "tool_call",
        "agent": call_info["agent_name"],
        "tool": call_info["tool_name"],
        "parameters": call_info["parsed_parameters"],

self.reporter = ReportingService(self.llm, tool_listener)
```

**同一套钩子，同时服务调试与产品体验**——这是本章很「工程味」的设计点。

### 14.3.3 Agent 协作模式

三个 Agent 是**顺序协作**（图 14.6）：

1. **线性**：固定顺序  
2. **明确 I/O**：上一环输出 = 下一环输入  
3. **无并发**：同时只跑一个 Agent（易调试；后续若要加速，再考虑并行搜多个 TODO）

协调器心智模型：

```text
plan → emit tasks
for task in todo_list:
    search → summarize → record → emit task_completed
report → emit report
```

`DeepResearchAgent.run` 伪代码（对照原书）：

```python
class DeepResearchAgent:
    def run(self, research_topic: str) -> str:
        self._emit_event({"type": "status", "message": "正在规划研究任务..."})
        todo_list = self.planner.plan_todo_list(research_topic)
        self._emit_event({"type": "tasks", "tasks": todo_list})

        task_summaries = []
        for task in todo_list:
            self._emit_event({"type": "status",
                              "message": f"正在研究：{task.title}"})
            search_results = self.search_service.search(task.query)
            summary = self.summarizer.summarize_task(task, search_results)
            task_summaries.append((task, summary))
            self._emit_event({"type": "task_completed", "task_id": task.id})

        self._emit_event({"type": "status", "message": "正在生成报告..."})
        report = self.reporter.generate_report(research_topic, task_summaries)
        self._emit_event({"type": "report", "content": report})
        return report
```

**顺序 vs 并行（学习笔记）：**

| | 顺序协作（本章） | 并行执行 TODO（进阶） |
|--|------------------|------------------------|
| 优点 | 易调试、进度语义清晰 | 总耗时更短 |
| 代价 | 总时长 ≈ 各任务之和 | 竞态、限速、日志更乱 |
| 建议 | 先跑通再优化 | 先保证 SearchService 幂等与缓存 |

统一返回字段记住：

| 字段 | 含义 |
|------|------|
| `results` | 列表：title / url / snippet |
| `backend` | 实际使用的引擎 |
| `answer` | 可选，Perplexity 等会给 AI 答案 |

**两道清洗关卡（强烈建议动手实现时不要省）：**

1. **URL 去重**：同一链接只留一条，避免 Summarizer 重复读。  
2. **Token/长度限制**：长 snippet 截断（教材用「约 4 字符 ≈ 1 token」粗估），避免撑爆 Summarizer 上下文。

```python
def deduplicate_sources(sources: List[dict]) -> List[dict]:
    seen, out = set(), []
    for s in sources:
        if s["url"] not in seen:
            seen.add(s["url"])
            out.append(s)
    return out

def limit_source_tokens(source: dict, max_tokens: int = 2000) -> dict:
    max_chars = max_tokens * 4
    snip = source["snippet"]
    if len(snip) > max_chars:
        snip = snip[:max_chars] + "..."
    return {**source, "snippet": snip}
```

> **为什么清洗放在工具/服务层，而不是 Prompt 里说「请忽略重复」？**  
> 因为重复与超长是**确定性工程问题**，用代码处理更稳、更省 token，也避免模型「装作忽略」却仍被噪声带偏。

## 14.5 服务层实现（重点）

> **本节目标**：理解服务层为何存在；吃透 Planning 的 JSON 健壮解析与质量评估；Summarization / Reporting 的格式化职责；SearchService 中间层、降级与缓存。

服务层是「业务逻辑容器」：Agent 负责语言智能，服务负责流程、校验、降级与缓存。

**Agent vs 服务（对照表）：**

| | Agent | Service |
|--|-------|---------|
| 擅长 | 理解、生成、结构化语言 | 编排、校验、I/O、容错 |
| 脆弱点 | 格式漂移、幻觉 | 若把「写总结」塞进服务会变笨重 |
| 本章分工 | Planner / Summarizer / Writer | 调 Agent、解析、清洗、推事件 |

### 14.5.1 任务规划服务 PlanningService

四职责：

1. 构建规划 Prompt（主题 + 日期）  
2. 调用 Planner Agent  
3. 提取 JSON  
4. 校验字段并生成 `TodoItem`  

核心骨架：

```python
class PlanningService:
    def plan_todo_list(self, state: SummaryState) -> List[TodoItem]:
        prompt = todo_planner_instructions.format(
            current_date=self._get_current_date(),  # 如「2026年07月23日」
            research_topic=state.research_topic,
        )
        response = self._agent.run(prompt)
        tasks_payload = self._extract_tasks(response)
        # 校验 title/intent/query → TodoItem
        ...
```

**健壮解析策略（工程硬菜）：**

真实 LLM 不会永远只吐纯 JSON。常见坑：

1. **额外文本**：前后有「好的，我将…」  
2. **格式错误**：缺引号/逗号 → `JSONDecodeError`  
3. **字段缺失**：少 `query` 等  

对策：

1. 先正则找 JSON 数组 `re.search(r'\[.*\]', ..., DOTALL)`  
2. 再尝试整段 `json.loads`  
3. 对每个 item 检查必需键  

```python
def _extract_tasks(self, response: str) -> List[dict]:
    json_match = re.search(r'\[.*\]', response, re.DOTALL)
    if json_match:
        try:
            return json.loads(json_match.group(0))
        except json.JSONDecodeError as e:
            raise ValueError(f"JSON解析失败：{e}")
    try:
        return json.loads(response)
    except json.JSONDecodeError:
        raise ValueError("无法从响应中提取JSON")
```

**规划质量评估（可选但很有教学价值）：**

好规划的标准：覆盖全面、逻辑清晰、查询精准、数量 3–5。

```python
def evaluate_plan(self, todo_items: List[TodoItem]) -> dict:
    score, suggestions = 100, []
    if len(todo_items) < 3:
        score -= 20
        suggestions.append("子任务过少，可能遗漏重要信息")
    elif len(todo_items) > 5:
        score -= 10
        suggestions.append("子任务过多，可能冗余")
    for task in todo_items:
        if len(task.query.split()) < 2:
            score -= 10
            suggestions.append(f"「{task.title}」查询过于简单")
    return {"score": score, "suggestions": suggestions}
```

练习方向：分数过低自动重规划一次（见文末练习）。

### 14.5.2 总结服务 SummarizationService

把搜索结果格式化后交给 Summarizer，返回带引用的 Markdown（以及来源 URL 列表）。这一步决定报告「有没有证据感」。

职责清单：

1. 格式化搜索结果  
2. 构建总结 Prompt（带上 title / intent / query）  
3. 调用 Task Summarizer  
4. 提取来源 URL 供报告阶段使用  

```python
def summarize_task(self, task, search_results):
    formatted = self._format_sources(search_results)
    prompt = task_summarizer_instructions.format(
        task_title=task.title,
        task_intent=task.intent,
        task_query=task.query,
        search_results=formatted,
    )
    summary = self._agent.run(prompt)
    source_urls = [r["url"] for r in search_results]
    return summary, source_urls
```

**为什么要把 intent 也塞进 Prompt？**  
因为同样十个搜索结果，意图不同，笔记焦点不同。例如「了解成立时间」vs「了解社区文化」，应强调不同字段。

### 14.5.3 报告生成服务 ReportingService

把 `List[(TodoItem, summary, source_urls)]` 格式化为「任务 i + 意图 + 正文 + 来源」块，再交给 Report Writer。Prompt 里把报告五段结构钉死。

```python
def _format_summaries(self, task_summaries) -> str:
    formatted = []
    for idx, (task, summary, source_urls) in enumerate(task_summaries, start=1):
        formatted.append(
            f"## 任务{idx}：{task.title}\n\n"
            f"**意图**：{task.intent}\n\n"
            f"{summary}\n\n**来源**：\n"
        )
        for url in source_urls:
            formatted.append(f"- {url}\n")
        formatted.append("\n")
    return "".join(formatted)
```

报告结构（与 14.2 呼应）：

```markdown
# 主题
## 概述
## 1. 子任务A
## 2. 子任务B
## 总结
## 参考文献
### 任务1：...
### 任务2：...
```

> **产品分水岭**：聊天机器人给结论；深度研究给「结论 + 可点开的来源」。ReportingService 要把来源一路传到参考文献区。

### 14.5.4 搜索调度服务 SearchService

本章刻意**不让 SimpleAgent 直接摸搜索引擎**，而是经 SearchService：

1. 按配置选引擎  
2. 调 SearchTool  
3. 去重 + 截断  
4. 失败记日志并返回空列表（不拖垮全流程）  

动机：让 Agent **更专注处理已得到的信息**；搜索侧可独立做降级、缓存、限速、清洗（图 14.8）。

```python
class SearchService:
    def search(self, query: str, max_results: int = 5) -> List[dict]:
        try:
            raw = self.search_tool.run({
                "input": query,
                "backend": self.config.search_api.value,
                "mode": "structured",
                "max_results": max_results,
            })
            results = raw.get("results", [])
            results = self._deduplicate_sources(results)
            results = self._limit_source_tokens(results)
            return results
        except Exception as e:
            logger.error(f"搜索失败：{query}，错误：{e}")
            return []  # 降级：空列表，流水线可继续（总结会变薄）
```

**调度逻辑五步：** 读 `SEARCH_API` → 选引擎 → 执行 → 去重截断 → 返回。

**进阶：磁盘缓存**（降成本、加速重复实验）：

```python
# cache_key = MD5(query + max_results + engine)
content = f"{query}_{max_results}_{self.config.search_api.value}"
cache_key = hashlib.md5(content.encode()).hexdigest()
# 命中则读 ./cache/search/{key}.json，否则搜索后写入
```

**为何失败返回 `[]` 而不是抛死？**

| 策略 | 效果 |
|------|------|
| 抛异常中断全流程 | 一个引擎抖动，整份报告作废 |
| 返回空列表 + 日志 | 该 TODO 总结变空/变弱，其它 TODO 仍可完成 |

教学上要意识到：降级会牺牲该任务质量，生产环境可再加「重试 / 换引擎 / 标红警告」。

### 14.6.2 实时进度展示（SSE）

SSE = Server-Sent Events，服务器单向推送（图 14.10；第十章协议也有铺垫）。

流程：

1. 客户端发起研究请求  
2. 服务器返回 `text/event-stream`  
3. 持续推送 `progress` / `plan` / `task_summary` / `report` / `error`  
4. 完成后关闭连接  

**后端（FastAPI）要点：**

```python
async def research_stream(topic: str) -> AsyncGenerator[str, None]:
    yield f"data: {json.dumps({'type':'progress','stage':'planning',...})}\n\n"
    todo_items = await planning_service.plan_todo_list(topic)
    yield f"data: {json.dumps({'type':'plan','data':[...]})}\n\n"
    # 循环：progress → search → summarize → task_summary
    yield f"data: {json.dumps({'type':'report','data': report})}\n\n"
    yield f"data: {json.dumps({'type':'progress','stage':'completed',...})}\n\n"

return StreamingResponse(
    research_stream(topic),
    media_type="text/event-stream",
    headers={"Cache-Control": "no-cache", "Connection": "keep-alive"},
)
```

记住 SSE 行格式：`data: {json}\n\n`（两个换行结束一帧）。

进度百分比常见分配（教材思路）：

| 阶段 | 大致进度 |
|------|----------|
| 规划完成 | ~10% |
| 执行中按任务推进 | 10% → 80% |
| 生成报告 | ~90% |
| 完成 | 100% |

**前端 `useResearch.ts` 心智模型：**

```typescript
eventSource.onmessage = (event) => {
  const data = JSON.parse(event.data)
  switch (data.type) {
    case 'progress':
      progressPercentage.value = data.percentage
      progressText.value = data.text
      break
    case 'plan': /* 展示任务列表 */ break
    case 'task_summary':
      markdownContent.value += `\n\n## 任务${data.task_id}\n\n${data.summary}`
      break
    case 'report':
      markdownContent.value = data.data
      break
    case 'error':
      error.value = data.message
      eventSource.close()
      break
  }
}
```

**SSE vs 轮询 vs WebSocket：**

| 方案 | 适合本章？ | 说明 |
|------|-----------|------|
| 轮询 | 勉强 | 延迟高、浪费请求 |
| SSE | **推荐** | 单向进度流，实现简单 |
| WebSocket | 可 | 若还要双向「取消/追问」再上 |

练习：前端「取消研究」= `eventSource.close()` + 后端协作取消（见文末练习）。

## 14.7 本章小结

回顾六条主线：

1. **TODO 驱动范式**：规划 / 执行 / 报告，可控、可调试、可扩展。  
2. **三 Agent 协作**：Planner、Summarizer、Writer 专而清晰；Prompt 可分别优化。  
3. **ToolAwareSimpleAgent**：工具调用可观测，同一钩子服务调试与 SSE。  
4. **工具集成**：Search 多引擎配置化 + 去重截断；Note 持久化；Registry 统一调度。  
5. **四服务层**：规划解析与评估、总结、报告、搜索调度（含清洗/缓存/降级）。  
6. **前端产品化**：全屏模态 + SSE 事件协议 + Markdown/参考文献可视化。

这些模式可迁移到竞品调研、学术综述、政策追踪等场景。下一章将进入赛博小镇，看游戏引擎场景下更复杂的多 Agent 交互。

### 一张图收束全章数据流

```
用户主题
  → PlanningService + Planner → TodoItem[]
  → 对每个 Todo：
        SearchService(+清洗/缓存) → sources
        SummarizationService + Summarizer → 笔记(+引用)
        NoteTool → workspace/notes/*.md
  → ReportingService + Writer → final Markdown
  → SSE 全程推送 → ResearchModal 渲染
```
