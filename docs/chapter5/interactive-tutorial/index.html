章首导读

不是放弃代码，是多一条工程路线

如果你的目标不是研究底层细节，而是更快把想法做出来——低代码平台把常见工程动作抽象成节点、模块与工作流。

手写代码

  • 控制力强、自由度高
  • 打地基到走线都自己来
  • 适合深度定制与研究
  • 慢：连工具、管状态、排链路

低代码平台

  • 标准化构件 + 预制模块
  • 可视化、可观测、协作友好
  • 适合快速验证与业务编排
  • 自由度受平台边界限制
搭房子：手写像从打地基开始；低代码像用预制构件。不是谁高级谁低级，而是阶段不同、工具不同。

纠偏

低代码既不「不专业」，也不「万能」

极端 A

觉得不用写代码就不专业，平台是「玩具」。

错在哪：专业开发者也大量用平台做原型、联调与标准化流程。效率本身就是专业能力。

极端 B

觉得平台什么都能解决，以后不用管底层。

错在哪：持久化、高并发、深度定制、原理理解仍要你自己。平台不替你思考任务设计。

帮你建立现实判断：低代码是 Agent 工具箱里的一种选择。学完应能回答——什么时候适合用平台，什么时候该回到代码。

先抓主线

读这一章前先对齐词汇

低代码平台

不是零门槛魔法盒；把 API、状态、流程等工程动作抽象成可拖拽节点与模块。

工作流

把任务拆成有序节点，数据按预定路线流动——看得见的流水线。

可观测性

能否看清每一步发生了什么：耗时、失败点、数据流。平台通常比终端日志更直观。

原型验证

先尽快验证「值不值得做」，再决定是否下沉代码或上生产加固。

边界感

抽象重复劳动，不取消思考

§ 5.1

平台化构建的兴起

既然会写代码了，为什么还要看低代码？因为真正耗时的往往不是「模型调用」，而是连工具、管状态、搭流程、排查链路。

类比网站演进：从手写 HTML/CSS/JS → WordPress / Wix；智能体也迎来图形化、模块化的平台浪潮。重心从「实现细节」转向「业务逻辑」。

本节两问：① 为何需要低代码？② Coze / Dify / n8n 怎么选？

5.1.1 · 动机

「重复造轮子」与工程效率的张力

「重复造轮子」对深入学习至关重要；但在追求工程效率与创新的实战中，我们往往需要站在巨人肩膀上。

尽管第四章封装了可复用的 ReActAgent、PlanAndSolveAgent 等类，当业务逻辑变复杂时：

  • 维护成本急剧上升（分支、异常、鉴权、重试……）
  • 开发周期拉长（从想法到可演示原型可能要数天）
  • 非开发角色难以直接参与流程设计
低代码像「预制厨房」：灶具、水槽已经装好，你负责决定做什么菜、按什么顺序出锅。

5.1.1 · 四大价值

把复杂细节封装成「节点」

低代码平台将 API 调用、状态管理、并发控制等封装成易于理解的节点或模块。用户无需精通编程，通过拖拽与连接就能构建工作流。

谁因此受益？

产品经理、设计师、业务专家等非技术人员也能参与智能体设计与创造，拓宽创新边界。开发者则少写样板代码。

新手注意

「低门槛」≠「零思考」。节点连错、Prompt 写糊、知识库没喂对，结果一样会跑偏。门槛降低的是工程操作，不是产品判断。

5.1.1

原型从「数天」压到「数小时」

对专业开发者而言，平台同样能带来巨大效率提升。项目初期需要快速验证想法或搭建 Prototype 时，低代码可在数小时甚至数分钟内完成原本需要数天编码的工作。

把时间从底层工程实现，挪到业务逻辑梳理与提示工程优化——这通常才是 Agent 效果差异的来源。

实战节奏：先用平台验证「用户是否需要」；确认价值后再决定是否用代码做加固、私有化与性能优化。

5.1.1

端到端看见数据怎么流

相比在终端打印日志，图形化平台天然提供智能体运行轨迹的端到端可视化：

  • 数据在每个节点之间如何流动
  • 哪一个环节耗时最长
  • 哪一次工具调用失败、失败原因是什么
像给流水线装上透明罩：堵在哪一站、哪一箱货掉了，一眼能看见——调试体验是纯代码难以比拟的。

5.1.1

内置模板与统一协作语言

优秀低代码平台通常内置行业最佳实践，例如：

  • 预设的 ReAct 模板
  • 优化过的知识库检索引擎
  • 标准化的工具接入规范

这不仅避免开发者「踩坑」，也让团队协作更顺畅——所有人基于同一套标准和组件开发。

低代码并非要取代代码，而是更高层次抽象：从繁琐底层实现解放出来，更专注智能体「思考」与「行动」的逻辑本身。

5.1.1 · 收束

从「实现细节」转向「业务逻辑」

简而言之：低代码让我们从繁琐底层实现解放出来，更专注智能体「思考」与「行动」的逻辑本身，从而更快、更好地把创意变为现实。

还要学第四章吗？

点击

要。不懂范式，平台上的 ReAct/工作流只是黑盒；懂了才能设计得更好、排错更快。

什么时候必须回代码？

点击

深度定制、极限性能、特殊协议、精细状态机、平台能力天花板——以及你要沉淀可版本控制的核心资产时。

5.1.1 · 深挖

调试时你想看见的三件事

数据

每个节点输入/输出 JSON 或文本是什么

时间

哪一步最慢：模型、检索还是外部 API

失败

鉴权失败、超时、格式错误、空结果

纯代码也能做观测，但要自己埋点；平台把「看见」变成默认能力。

5.1.2

百花齐放：看需求、背景与目标

智能体与 LLM 应用的低代码市场很热闹。选哪个，往往取决于核心需求、技术背景以及项目最终目标。

本章重点介绍并实操三个代表性平台：

Coze · 应用搭建与上线 Dify · Agent 产品组织 n8n · 系统集成自动化

5.1.2 · Coze

零代码/低代码 Agent 体验

  • 核心定位：由字节跳动推出，主打让不具备编程背景的用户也能轻松创造 Agent。
  • 特点：可视化界面友好，像搭乐高——拖拽插件、配置知识库、设定工作流；插件库丰富；支持一键发布到抖音、飞书、微信公众号等。
  • 适用人群：AI 应用入门用户、产品经理、运营人员，以及希望快速把创意变成可交互产品的个人创作者。
记忆钩子：Coze ≈ 「做出来并上线给人用」最快的那条路。

5.1.2 · Dify

开源 LLM 应用开发与运营平台

  • 核心定位：为开发者提供从原型构建到生产部署的一站式方案，融合后端服务与模型运营理念。
  • 特点：支持 Agent 工作流、RAG Pipeline、数据标注与微调等；追求专业、稳定、可扩展的企业级应用时，Dify 提供坚实基础。
  • 适用人群：有一定技术背景的开发者、需要构建可扩展企业级 AI 应用的团队。
记忆钩子：Dify ≈ 「把 Agent 当产品来组织」：角色、技能、规则、工作流、知识库、部署一体。

5.1.2 · n8n

开源工作流自动化（非纯 LLM 平台）

  • 核心定位：本质是通用工作流自动化工具；近年来积极集成 AI 能力。
  • 特点：强项在「连接」——数百预置节点串联 SaaS、数据库、API；可在流程中嵌入 LLM 节点。学习曲线相对陡峭。
  • 适用人群：需要把 AI 深度整合进现有业务流程、实现高度定制化自动化的开发者与企业。
记忆钩子：n8n ≈ 「让 AI 成为整条业务自动化里的一环」，而不是只做一个聊天 Bot。

§ 5.2

平台一：Coze（扣子）

上手门槛低、交互直观：用较少工程成本，快速搭一个能跑、能调、能发布的 Agent。

带着问题读：如果我刚开始做 AI 应用，Coze 帮我省掉了哪些麻烦？

生态亮点：一键发布到微信、飞书、豆包等；企业可用 API 把能力嵌进现有业务——「搭积木式」构建。

5.2 开场

市面上应用很广的智能体制作工具

扣子（Coze）以直观可视化界面和丰富功能模块，让用户轻松创建各类智能体：陪聊机器人、自动写故事、甚至把故事做成电影 MV。

  • 生态集成：开发完成可一键发布到微信、飞书、豆包等主流平台
  • 企业能力：灵活 API，支持把智能体能力集成到现有业务系统
  • 构建方式：「搭积木式」——插件 + 知识库 + 工作流 + 提示词

5.2.2 · 设计选择

插件生态降低「取数工程」

简报案例用 RSS/GitHub/arXiv 插件，而不是让你从零写爬虫与解析器。这正是低代码价值：把取数工程变成配置。

  • GitHub：结构化仓库搜索
  • arXiv：学术更新接口化
若源站无 RSS 或反爬严格，才需要自定义插件/API——边界就出现了。

5.2.2 · Step 2

资深且权威的科技媒体编辑

角色设定与提示词是定义行为与输出质量的核心。把抽象指令变成智能体可理解并执行的具体任务。

我们将智能体设定为资深且权威的科技媒体编辑——赋予专业定位，使其在内容创作中模仿专业编辑：筛选、整合、概括。

没有角色，模型容易「什么都会一点、什么都不专业」。角色像给输出定「人格与标准」。

5.2.2 · Step 2

系统提示：长期准则与格式规范

System Prompt 核心条款（展开）
  • 角色：资深科技媒体编辑，擅 AI 动态 / 学术 / 开源整合
  • 日报开头标注「AI日报」、作者与当天日期
  • 每条标题加独有 Emoji（<!!!important!!!>）
  • 内容必须高度相关 AI/LLM/AIGC，排除广告营销
  • 每条提供原始链接 + 短概况
设计意图：System 管「怎么当这个编辑」；不要把一次性任务细节全塞进 System。

5.2.2 · Step 2

用户提示：具体任务与数据源

  • 从 articles* 筛选 AI 相关 →「AI技术新闻」
  • 从 arxiv 按 title/link 整理 →「AI学术论文」
  • 从 GitHub 筛最受瞩目的 5 个项目 →「AI开源项目」

输出总量：10 条新闻 + 5 篇论文 + 5 个开源项目。硬性数量能显著提高版式稳定性。

工作流像流水线：前一节点数据流入下一节点——与第四章范式比，这里更强调「画出来、连起来、观察起来」。

5.2.2 · Prompt 深挖

把「可检查」写进提示词

好 Prompt 不是文学，是验收标准：

  1. 开头格式是否可正则检查（日期、作者）
  2. Emoji 是否「每条独有」
  3. 是否强制带原始链接
  4. 模块数量是否硬约束（10/5/5）
  5. 是否明确排除广告营销
像给实习生写 checklist：你不写清楚，对方只能「凭感觉写漂亮话」。

5.2.2 · Step 3

运行预览：检查结构与风格

在预览界面运行，观察简报。期望结构类似：

# AI日报 by@jasonhuang 2025-09-24 ## 🚀 AI技术新闻 🤖 **某开源基座模型全面开源** · 链接 · 概况…… ## 📚 AI学术论文 🧪 **某生成式 3D 重建论文** · 链接 · 概况…… ## 💻 AI开源项目 🤖 **某多智能体框架** · 链接 · 概况……

仔细检查：内容准确性、格式完整性、语言风格。不符预期则回改 Prompt 或插件参数。

  • 不支持 MCP：作者认为这是最致命限制之一；插件市场虽丰富，缺 MCP 可能锁住生态扩展。若放开将是杀手锏。（注：路线图曾出现相关讨论，以平台最新能力为准。）

§ 5.4

平台三：n8n

n8n 的核心身份是通用工作流自动化平台，而非纯粹的 LLM 应用构建工具。理解这一点，是掌握 n8n 的关键。

在 n8n 里构建智能应用，实质是设计更宏大的自动化流程；大模型只是流程中的一个（或多个）强大「处理节点」。

5.4 开场

先改心态：不是「做 Bot」，是「串业务」

如果你把 n8n 当 Coze/Dify 的换皮版，会很难受——它的强项是把 CRM、邮件、数据库、Webhook、LLM 串成端到端自动化。

传统自动化

  • 线性：收到 → 规则 → 动作
  • 路径基本写死

AI Agent 工作流

  • 接收 → 思考 → 决策 → 工具调用 → 回复
  • Agent 在多个工具中自主选择

5.4.1

Node = 有特定功能的积木块

n8n 提供数百种预置节点：发邮件、读写数据库、调 API、处理文件……每个节点有输入输出与图形化配置。

触发节点 Trigger

工作流起点：新邮件、定时、Webhook 等。一个工作流必须有且仅有一个触发节点。

常规节点 Regular

处理数据与逻辑：读表格、调 OpenAI、写库等。

5.4.1

数据以 JSON 在节点间传递

工作流由多个节点连接而成，定义数据从触发节点开始如何被传递、处理并完成任务。结构化 JSON 传递让你可以精确控制每环输入输出。

像快递分拣线：每个工位只干一件事，包裹（JSON）带着标签往下传。你要盯的是「这一站吃什么字段、吐什么字段」。
真正威力：把孤立的应用与服务串联，实现过去要复杂编码才能完成的端到端业务自动化。

5.4.4 · Prompt 细节

为什么要 shouldReply / subject / body

下游 Gmail Send 需要稳定字段。若模型自由散文输出，表达式映射会碎。

{ "shouldReply": true, "subject": "Re: [原始邮件主题]", "body": "完整正文，换行用 <br>" }

规则还包括：永远优先尝试用 SerpAPI 回答；非工作时间必须声明状态并附准确工时；工时以 Vector Store 为准，不编造。

5.4.5

调试 · 非持久化 · 协作 · 性能

  • 调试相对繁琐：复杂流出错时常需逐节点查输入输出
  • 内置存储非持久：Simple Memory / Simple Vector Store 基于内存，重启即丢——生产必须换 Redis、Pinecone 等
  • 版本协作不如 Git 成熟：可导出 JSON，但 diff/多人同编易冲突
  • 性能：中低频自动化足够；超高并发下节点调度开销可能逊于纯代码服务

演示可以内存；上线必须持久化。否则「昨晚好好的，重启全没了」。

  • Simple Memory → Redis 等会话存储
  • 单机调试 → 可观测与告警、密钥与权限管理
  • 手动执行知识加载 → 变更时的受控流水线

5.5 预告

快速决策口诀

  • 快速原型验证、非技术用户 → 优先 Coze
  • 企业级应用、复杂业务逻辑 → 优先 Dify
  • 深度业务集成、自动化流程 → 优先 n8n
混合开发：用平台快速验证想法，用代码实现精细化控制；用平台处理标准化流程，用代码处理特殊逻辑。

工程哲学

平台与代码是光谱，不是阵营

值得强调：低代码并非要取代代码开发，而是互补选择。实际项目中可按阶段灵活切换：

  • 用低代码快速验证想法
  • 用代码实现精细化控制
  • 用平台处理标准化流程
  • 用代码处理特殊逻辑与性能关键路径

这种「混合开发」思维，才是智能体工程化的最佳实践。

习题 5 热身

结构不同，因为平台职责不同

  • Coze 简报：强格式媒体编辑 + 多源变量抽取
  • Dify 模块：Role/Skills/Rules 或五段式，服务「专长子智能体」
  • n8n 邮件：工具清单 + 并行步骤 + 强制 JSON，服务「自动化下游节点」

差异与平台特性相关：越靠近业务自动化，越强调结构化输出与工具契约。

习题延伸

工具调用的「新标准」视角

相对传统 REST 与散落的 Tool Calling 定义，MCP 试图提供更统一的工具发现与调用协议，让「模型侧」和「工具侧」解耦。

  • 对平台：可插拔接入大量 Hosted 工具（如高德）
  • 对生态：减少每个平台各写一套插件适配
  • 对 Coze：书中认为缺 MCP 是关键局限之一

§ 5.5

从手写代码到平台化开发

本章系统介绍了基于低代码平台构建智能体应用的理念、方法与实践。

5.1 回顾

四大价值：门槛、效率、可观测、标准化。平台是更高层抽象，不取代代码。

Coze 回顾

每日AI简报：多源插件→Prompt→多渠道发布。适合快验；注意 MCP 与导出形态。

Dify 回顾

超级个人助手：分类器+多模块+MCP。开源企业级；注意学习曲线与并发。

n8n 回顾

智能邮件：知识库加载 + AI Agent 主流程。连接力强；生产须持久化。

纠偏

别把平台用歪了

坑1 · 以为零思考

节点拖完就完事。其实 Prompt、路由规则、知识质量决定上限。

坑2 · 演示当生产

内存向量/记忆直接上线。重启丢数据是典型事故。

坑3 · 平台原教旨

非要用一个平台打天下。该混合就混合，该下沉代码就下沉。

应用 A：C 端 AI 写作小程序
