# 第一章 初识智能体

很多人第一次听到“智能体”这个词，会下意识把它理解成“更聪明一点的聊天机器人”。这个理解不能说完全错，但确实只摸到了表面。聊天机器人更像“你问一句，我答一句”；而智能体更像“你交给它一个目标，它会想办法一步一步把事情推进下去”。它不只是会说，还会看、会想、会做、会根据结果继续调整。

所以，这一章最重要的任务，不是让你一下子背会很多术语，而是先把脑子里的地图搭起来。后面你会不断接触 ReAct、工具调用、记忆、RAG、工作流编排、多智能体协作。如果第一章没把地基打稳，后面每学一个新词，都容易像在沙地上堆积木。

你可以带着三个问题读这一章：

1. 智能体和普通程序、普通聊天模型到底差在哪？
2. 一个智能体是靠什么机制运转起来的？
3. 为什么今天大家都在谈 Agent，而不是只谈大模型？

如果这三个问题在你脑中越来越清楚，那这一章就学对了。

### 开始前：先丢掉五个常见误解

1. **有了大模型 ≠ 有了智能体。** 大模型提供推理与语言能力；智能体还要工具、状态、循环、终止条件与护栏。
2. **智能体 ≠ 自动化脚本。** 脚本通常把路径写死；智能体在边界内自主决定下一步。真实系统常常二者混合。
3. **自主性不是越高越好。** 自主上升往往伴随风险、成本与不可复现性上升。成熟设计追求「刚刚好的自主性」。
4. **智能体不是 LLM 时代才有的新词。** 传统 AI 已研究数十年；现代 LLM Agent 是老思想在新技术上的重组。
5. **提示词写好就能稳定上线。** 提示词很重要，但解析器、重试、最大轮次、工具错误处理同样决定可用性。

## 1.1 什么是智能体？

先记一句最朴素、也最实用的话：<strong>智能体不是一个只会回答问题的模型，而是一个会围绕目标持续行动的系统。</strong>

为什么这里强调“系统”而不是“模型”？因为模型只是大脑，智能体还需要眼睛、耳朵、手脚，甚至还需要短期记忆、任务进度、规则边界和反馈机制。一个系统如果只能生成一段看起来很聪明的话，但不能感知环境、不能调用工具、不能根据结果继续往下推进，那它更像“会说话”，还谈不上“会做事”。

在人工智能领域，一个更正式的定义是：智能体是能够通过<strong>传感器（Sensors）</strong>感知环境，通过<strong>执行器（Actuators）</strong>采取行动，并依靠一定程度的<strong>自主性（Autonomy）</strong>来达成目标的实体。

这个定义初看有点像教材，但它非常有用，因为它把“智能体”这个容易被讲得很玄的概念拆成了几个特别好检查的部分。

- <strong>环境（Environment）</strong>：智能体面对的外部世界。自动驾驶面对的是道路和交通；代码助手面对的是代码库、终端、测试日志和你的需求。
- <strong>传感器（Sensors）</strong>：智能体用来获取信息的通道。机器人可能用摄像头、麦克风、雷达；软件智能体更常用 API 返回、网页内容、数据库结果、用户输入。
- <strong>执行器（Actuators）</strong>：智能体影响世界的方式。机器人用机械臂和轮子，软件智能体则可能调用函数、改文件、发消息、执行命令、点网页按钮。
- <strong>自主性（Autonomy）</strong>：它是不是只能机械执行预设步骤，还是能根据当前情况自己决定下一步查什么、做什么、改什么。

如果你愿意，也可以把这四件事翻译成更生活化的说法：它看见了什么、它能动什么、它想去哪里、它能不能自己决定怎么走。

这也是为什么“智能体”和“自动化脚本”不能简单画等号。自动化脚本通常是人把路线提前写死，系统照着跑；智能体则更像你给它一个目标，它自己边走边判断路线。当然，真实系统里两者经常混合存在，后面你会看到这一点。

### 1.1.1 传统视角下的智能体

#### 开始前铺垫：这一节在解决什么问题？

很多人一上来就想学「怎么写 Agent Prompt」，却不知道 Agent 思想其实有一条很长的演进链。本节按「能力逐步加码」讲五种传统架构。你可以把它当成升级打怪：

| 级别 | 名字 | 多出来的能力 | 一句话例子 |
|------|------|--------------|------------|
| L1 | 简单反射 | 条件-动作 | 恒温器 |
| L2 | 基于模型 | 内部状态/记忆雏形 | 隧道里仍估计前车位置 |
| L3 | 基于目标 | 规划到目标状态 | GPS 导航 |
| L4 | 基于效用 | 多目标权衡 | 又快又省油又少过路费 |
| L5 | 学习型 | 从反馈改进策略 | AlphaGo Zero |

**记忆口诀**：先反应 → 再建模 → 再奔目标 → 再算划算 → 最后会自学。


#### 概念拆解：为什么要先看「反射智能体」这张图？

原版用图 1.2 把「条件 → 动作」画成最简决策链。你先把它记成：

> **当前感知** 进系统 → **规则表匹配** → **立刻行动**。中间没有「回忆昨天」也没有「预测明天」。

**生活例子**：电梯里的开门按钮——按下就开门，不会记得你上次是不是误触。  
**对应到软件**：`if error_code == 503: retry()` 这种告警脚本，本质也是反射规则。  
**何时够用**：规则少、状态可直接观测、错了也不致命。  
**何时不够**：需要上下文（「用户刚才拒绝过酒店」）、需要规划（「先查天气再推景点」）。


很多人以为智能体是大语言模型火了之后才出现的新东西，其实不是。早在今天的 LLM 热潮之前，人工智能研究者就已经研究智能体几十年了。只不过那时候的智能体不是“用自然语言对话”的样子，而是沿着一条很清晰的路线，逐步从简单反应走向复杂决策。

理解这段历史很重要，因为它会帮你形成一个非常稳的判断：<strong>现代 Agent 并不是凭空诞生的，它是很多老思想在新技术条件下重新组合的结果。</strong>

最早的一类是<strong>反射智能体（Simple Reflex Agent）</strong>。这种系统非常像条件反射，逻辑可以概括成一句话：如果发生某种情况，就执行某个动作。比如恒温器监测到温度太高就制冷，太低就制热。它的优点是简单、稳定、响应快，特别适合那些规则清晰、变化有限、容错要求低的场景。

但它的问题也很明显。它只看“现在”，不理解“之前”，也不考虑“之后”。如果一个任务需要记住过去发生了什么，或者需要推测未来可能怎样，那它就不够用了。

于是研究者提出了<strong>基于模型的反射智能体（Model-Based Reflex Agent）</strong>。你可以把它理解成：系统开始在内部保留一份“世界当前大概长什么样”的状态图。哪怕眼前信息不完整，它也能根据之前看到的内容继续做出判断。比如自动驾驶汽车短时间失去前车画面，不代表它就认为前车不存在了，它会结合内部模型继续估计前车的位置和速度。

再往前一步，研究者发现，很多任务不是“看到什么就反应什么”，而是“为了一个目标往前走”。这就发展出了<strong>基于目标的智能体（Goal-Based Agent）</strong>。导航系统是最典型的例子。它不会只告诉你当前在哪，而是会基于“我要去公司”这个目标，规划下一步怎么走、转哪条路、怎么避堵。

再进一步，目标往往还不止一个。你不仅想去公司，还想快一点、省油一点、少交过路费、尽量避开堵车。于是出现了<strong>基于效用的智能体（Utility-Based Agent）</strong>。它不只是问“能不能达成目标”，而是问“哪一种方案最划算、最满意”。换句话说，它开始会做权衡。

但前面这些智能体还有一个共同点：核心逻辑基本还是人类先设计好的。规则是人给的，模型是人建的，目标和效用函数也大多是人定的。于是一个更深的问题出现了：系统能不能不靠我们把规则一条条写出来，而是自己在和环境互动中学会更好的策略？

这就引出了<strong>学习型智能体（Learning Agent）</strong>。其中最有代表性的路径，就是<strong>强化学习（Reinforcement Learning, RL）</strong>。强化学习可以先粗略理解成“试一试，看结果好不好，再慢慢学”。系统采取行动，环境给出奖励或惩罚，它就在不断试错中学会什么做法更有效。

比如下棋 AI，一开始可能只是乱下，但通过海量对弈，它会逐渐发现哪些棋路更容易赢。AlphaGo Zero 之所以震撼，是因为它不只是照抄人类经验，而是在不断自我博弈中学出了很强的策略。

如果把这条历史线压缩成一句话，那就是：智能体的发展，是一条从“只会当场反应”，走向“会记忆、会规划、会权衡、会学习”的路线。后面你看到的很多现代 Agent 能力，其实都能在这条路线里找到祖先。

### 1.1.2 大语言模型驱动的新范式

#### 概念拆解：LLM 到底「换」了智能体的哪一块？

传统智能体的「大脑」多半是人写的规则/搜索算法；LLM 智能体的「大脑」变成了一个能理解自然语言、能拆解模糊目标的通用推理接口。

**具体对照（旅行例子再拆一层）**：

1. 用户说「帮我规划厦门三日游」——这句话本身就不是 API 参数，传统程序要先做表单；LLM 可以直接接住。
2. 模型在内部可能拆成：确认偏好 → 查天气 → 排行程 → 订住宿。
3. 缺数据时调用工具（天气 API、搜索），而不是瞎编。
4. 用户说「预算超了」→ 把这句话当成新约束，动态改计划。

**务必记住的边界**：LLM 让「接模糊任务」变容易，但**不自动等于**工具可靠、状态正确、不会死循环。工程上仍要：解析器、最大轮次、工具错误处理、权限边界。


到了大语言模型时代，智能体发生了一次非常大的跃迁。以前很多系统都要求我们把规则写得很清楚：什么情况走什么分支，什么输入触发什么动作。可现实里的任务往往不是规规矩矩的流程图，而是模糊、开放、充满上下文的。

比如：

- “帮我规划一趟厦门三日游。”
- “帮我看看这段代码为什么老报错。”
- “帮我整理这周最重要的 AI 新闻，并按重要程度排序。”

这些任务共同的难点在于：你很难提前把全部规则写死。因为真实世界的信息太杂，用户表达也不标准，任务推进过程中还会不断出现新情况。

以<strong>GPT（Generative Pre-trained Transformer）</strong>为代表的大语言模型，改变的正是这件事。它不是靠工程师把每条规则一行行写进去，而是先在大量数据上学会语言理解、知识关联、模式概括和任务分解的能力。于是，系统面对高层目标时，不再只能执行固定脚本，而是能先理解需求，再规划步骤，再按需要调工具。

你可以继续用“智能旅行助手”来理解。以前你自己要打开天气 App、地图 App、酒店 App、点评网站，一步一步手动拼起来。现在，如果一个 LLM 智能体足够成熟，它可以接住一句很模糊的话：“帮我规划一次厦门旅行。”

接下来它可能会做这些事：

- 先判断任务里缺了哪些关键信息，比如出行时间、预算、偏好、同行人数。
- 把大目标拆成几个小目标，比如查天气、看交通、找酒店、排景点。
- 发现自己缺数据时，主动调用工具去补信息。
- 在拿到结果之后，不是机械往下跑，而是根据新信息动态调整。

比如它发现预报有雨，那么接下来推荐的景点就该偏室内；如果你说“预算超了”，它就要重新搜索更便宜的方案；如果你说“我不喜欢网红打卡，更想看人文历史”，它的行程逻辑也要跟着变。

这里最值得你抓住的，不是“旅行”这个例子，而是背后的变化：<strong>软件正在从“按预设流程执行”，转向“围绕目标动态求解”。</strong>

当然，也不要因此误会为“有了 LLM，一切就自动智能了”。不是的。大模型确实让智能体获得了强大的语言理解和推理接口，但它依然需要工具、上下文、状态管理、约束机制和工程控制。否则它很容易说得头头是道，却做不成事。

### 1.1.3 智能体的类型

<!-- W3-CH1 -->
#### 学习检查：读完 1.1 你应能口头回答

1. 用四要素检查「空调」是不是智能体（是弱反射智能体）。  
2. 说明 LLM Agent 相对传统规则 Agent 的最大变化（接模糊目标的能力）。  
3. 举一个必须用混合式（快反应+慢规划）的产品例子。  
4. 说明神经符号在现代 Agent 里分别体现在哪（模型 vs Thought/Action 结构）。


#### 学习地图：三种分类怎么交叉使用？

分类不是为了背名词，而是给你一张「选型清单」。遇到一个真实系统，建议按这个顺序问：

1. **决策架构**：它有没有内部模型？有没有明确目标？会不会学习？
2. **时间特性**：它必须毫秒级反应，还是可以花几秒规划？
3. **知识表示**：关键决策靠规则（可审计），还是靠神经网络（模式强但黑箱），还是混合？

**交叉例子**：自动驾驶高速避障——反应式为主（安全气囊/紧急制动），但路径规划层是审议式；感知多用神经网络（亚符号），交规与红线多用规则（符号）。这就是混合 + 神经符号的现实形态。


理解完智能体的基本定义和发展路线之后，接下来要学会一件更有工程价值的事：<strong>分类</strong>。因为以后你遇到一个系统，不能只说“它是 Agent”，这太粗了。更重要的是能继续往下判断：它偏即时反应，还是偏规划推理？它更像规则系统，还是更像数据驱动系统？它是单层结构，还是混合结构？

把类型分清楚，最大的好处不是为了考试，而是为了设计系统时少走弯路。你会更知道什么任务该用什么方法，为什么某种方案适合这个场景而不适合另一个场景。

（1）<strong>基于内部决策架构的分类</strong>

这是最经典的一种分法，也是《Artificial Intelligence: A Modern Approach》中系统化整理过的视角<sup>[1]</sup>。如果你回头看前面 1.1.1 节，其实已经把这条线走过一遍了：从简单反应，到基于模型，再到基于目标、基于效用，最后加入学习能力。

你可以把这条线理解成“智能体脑子越来越复杂”的过程。

- 简单反射：像膝跳反射，看到什么立刻做什么。
- 基于模型：脑中开始有一张简化地图，不再只看眼前。
- 基于目标：开始知道自己到底想去哪。
- 基于效用：不只想“到”，还想“更优地到”。
- 学习型：不只会执行，还会边做边学。

这个分类的意义在于，它告诉我们：不是所有智能体都需要最复杂的架构。任务简单时，简单反射可能最稳；任务复杂时，才需要规划、效用和学习。

（2）<strong>基于时间与反应性的分类</strong>

另一个很重要的分类维度，是看它到底是“快反应型”还是“慢思考型”。这背后反映的是一个经典权衡：<strong>速度</strong>和<strong>规划深度</strong>很难同时无限拉满。

- <strong>反应式智能体（Reactive Agents）</strong>

这类智能体的特点是快。外界一有变化，它就迅速作出响应。它的优势在于延迟低、实现直接、计算开销小。像汽车安全气囊系统、一些实时监控告警系统、高频交易中的部分策略，都非常依赖这种快反应。

但快也有代价。它通常不擅长长远规划，不善于处理多步推理，很容易只顾眼前、不顾后面。你可以把它想成一个反应很快的人，但不一定擅长布局。

- <strong>规划式智能体（Deliberative Agents）</strong>

这种智能体不急着立刻动作，而是会先想一想：我现在面对的是什么局面？有哪些可能路径？每条路径的后果是什么？这类智能体更适合做长期任务、复杂任务、需要多步骤协调的任务。

它很像下棋的人。好的棋手不会只看这一步吃不吃子，而是会连着往后想好几步。问题是，这种思考需要时间和算力。如果环境变化太快，它还没想完，局面可能已经变了。

- <strong>混合式智能体（Hybrid Agents）</strong>

现实世界里，很多任务既需要快反应，也需要慢规划。比如智能旅行助手，用户一句“这家酒店太贵了”进来，它要快速调整；但整趟旅行的安排又需要整体规划。这时，最实用的往往是混合式结构。

一种经典思路是分层：低层负责快速响应，高层负责长远规划。而现代 LLM 智能体则常常采用另一种更灵活的方式，把整个大任务拆成很多小循环：

- 在“思考”阶段做局部规划。
- 在“行动”阶段调用工具。
- 在“观察”阶段读取结果。
- 然后再根据新情况继续思考。

这就像一个人不是先把整件事从头到尾一次想完，而是每走一步都重新校准方向。它既保持了灵活性，又能逐步推进长期目标。

<strong>（3）基于知识表示的分类</strong>

还有一个更底层、更“哲学”的分类角度：智能体脑中的知识到底是怎么存在的？这就牵涉到人工智能历史上很重要的一场争论，也就是<strong>符号主义</strong>和<strong>亚符号主义</strong>。

- <strong>符号主义 AI（Symbolic AI）</strong>

符号主义相信，智能来自对“明确符号”和“逻辑规则”的操作。比如“如果用户是 VIP，并且在 7 天内申请退款，那么优先人工审核”这种就很符号化。它像一个极度讲条理的图书管理员，把知识按规则分类存放。

它最大的优点是透明。你能追溯它为什么做这个判断，也能审查它是不是遵守规则。所以在医疗、法律、金融风控这类高风险场景里，可解释性特别重要。

但它也有明显短板：现实世界太复杂，规则很难写全。一旦碰到规则之外的新情况，系统就容易发懵。这也被叫作“知识获取瓶颈”。

- <strong>亚符号主义 AI（Sub-symbolic AI）</strong>

亚符号主义走的是另一条路。它不要求把规则明明白白写出来，而是通过大量数据训练，让知识分布在神经网络参数里。深度学习就是这条路线的代表。

如果说符号主义像图书管理员，那么亚符号主义更像一个通过大量观察学会识别模式的孩子。孩子不一定能准确说出“猫的定义”，但看多了之后，往往一眼就能认出猫。

这种方法在图像、语音、文本等非结构化数据上特别强，因为它擅长从海量样本中抓模式。但它的问题是黑箱。很多时候它能答对，却说不清自己为什么这么答。更麻烦的是，它有时还会一本正经地“编错”。

- <strong>神经符号主义 AI（Neuro-Symbolic AI）</strong>

于是研究者开始尝试把这两条路线结合起来，形成神经符号主义，也就是既要神经网络的感知和泛化能力，又要符号系统的规则推理和可解释性。

这时候，丹尼尔·卡尼曼在《思考，快与慢》中提出的“双系统理论”就很好理解了<sup>[2]</sup>：

- <strong>系统 1</strong>：快、直觉、并行，像人一眼认出熟悉的脸。
- <strong>系统 2</strong>：慢、审慎、逻辑化，像人做一道复杂数学题。

现代 LLM 智能体正好很像这两种能力的结合体。模型本身是大规模神经网络，擅长模式识别、语言理解和生成；但它工作时又会吐出计划、步骤、工具调用、结构化参数，这些又是典型的“符号化中间产物”。

所以，从某种意义上说，今天的 Agent 之所以迷人，正是因为它开始让“直觉”和“规则”在同一个系统里合作。

## 1.2 智能体的构成与运行原理

上一节回答的是“智能体是什么”。这一节要回答的是另一个更落地的问题：<strong>它到底怎么运转？</strong>

很多人学 Agent 容易停在概念层，知道它好像会调用工具、会做任务分解、会自己推进流程。但一旦追问“具体是怎么一步步转起来的”，脑中就只剩一句模糊的话：好像是模型在想、工具在做、结果再喂回去。

其实，这件事完全可以讲清楚。你可以把智能体想成一个正在工作的助手。它先看当前情况，再想下一步，再动手做，然后看结果对不对，再继续决定下一步。这种循环，就是智能体真正的生命线。

### 1.2.1 任务环境定义

#### 动手模板：给你一个空白 PEAS 表

以后每设计一个 Agent，先填这张表（先别写代码）：

1. **P（成功标准）**：什么叫做好？例如「行程可执行、预算不超、用户满意度 ≥ 4/5」。
2. **E（环境）**：信息从哪来？会不会变？有没有别的行动者？
3. **A（执行器）**：能调哪些 API/写哪些文件/发哪些消息？**权限边界写清楚**。
4. **S（传感器）**：能读用户输入、工具返回、日志、数据库的哪一部分？

**环境四特性速记（配旅行助手）**：

- 部分可观察：航班 API 只返回一页结果。
- 随机性：票价下一分钟就变。
- 多智能体：别的用户可能抢票。
- 序贯+动态：你查完酒店再查机票时，酒店可能已满。

填完 PEAS 再写 Prompt，通常比「先写一堆提示词再补锅」稳得多。


想理解一个智能体，最容易忽略、却最该先看的一点，不是它用了哪个模型，而是：<strong>它到底在什么环境里工作。</strong>

在人工智能里，一个很经典的分析框架叫<strong>PEAS 模型</strong>，分别对应：

- <strong>Performance</strong>：怎样才算做得好
- <strong>Environment</strong>：它身处什么世界
- <strong>Actuators</strong>：它能做什么动作
- <strong>Sensors</strong>：它能获取什么信息

这个框架的价值非常大，因为它逼着你先把系统边界想清楚。很多 Agent 项目做不稳，不是模型不够强，而是一开始就没定义清楚“成功标准是什么”“它能看到什么”“它能动什么”。

你如果认真看这个例子，会发现一个关键事实：数字世界里的环境，一点也不比物理世界简单。

首先，它通常是<strong>部分可观察的</strong>。比如旅行助手查航班时，不可能一次性看到整个互联网里所有可用座位。它看到的只是某个接口当下返回的一部分数据。也就是说，它永远是在“信息不完整”的条件下做决策。

其次，它经常是<strong>随机的</strong>，也就是不确定的。你刚刚查出来的机票价格，五分钟后可能就变了；你看到的空房数，也可能下一秒就被别人订走。于是，智能体就不能假设世界静止不动，它得学会面对变化。

再次，它很可能是<strong>多参与者环境</strong>。你不是唯一行动者，别的用户、别的程序、别的平台策略也在同时改变局面。你可以把这些都看作“环境中的其他智能体”。它们不需要长得像人，也不需要会聊天，只要它们会行动并改变状态，就会影响你的智能体。

最后，很多任务还具有<strong>序贯性</strong>和<strong>动态性</strong>。序贯意味着现在这一步会影响后面；动态意味着你在想的时候，世界自己也在变。这就是为什么真正有价值的 Agent 几乎都离不开状态管理、持续循环和错误恢复。因为现实任务不是做一锤子买卖，而是在变化中不断往前推进。

### 1.2.2 智能体的运行机制

#### 步骤走读：把 Agent Loop 画成四格漫画

1. **感知**：拿到用户请求或上一步 Observation。  
2. **思考**：规划 + 选工具（对 LLM 来说常写成 Thought）。  
3. **行动**：真正调用函数/API（Action）。  
4. **观察**：把工具结果清洗成 Observation，塞回下一轮。

**为何需要循环而不是一次生成？**  
因为真实任务的信息是「边做边解锁」的：不查天气，就不知道该推室内还是室外景点。一次生成等于在信息不全时硬猜。

**护栏三件套（后面代码会用到）**：最大循环次数、Finish 终止协议、解析失败时的 Observation 纠错提示。


当任务环境定义清楚后，我们终于可以进入智能体最核心的部分了：<strong>智能体循环（Agent Loop）</strong>。

这个概念你务必要牢牢记住。因为往后你学 ReAct、Function Calling、Planning、Memory、Multi-Agent，本质上都还在这个循环上加东西，而不是另起炉灶。

这个循环可以拆成四个动作：

1. <strong>感知（Perception）</strong>
2. <strong>思考（Thought）</strong>
3. <strong>行动（Action）</strong>
4. <strong>观察结果并进入下一轮（Observation -> Next Loop）</strong>

你可以把它翻译成一句极其口语化的话：<strong>先看，再想，再做，再根据结果继续看。</strong>

这里最容易被初学者忽略的是，行动不是终点。很多人一看到系统调用了一次工具，就下意识觉得任务结束了。其实恰恰相反，真正的 Agent 味道，是它做完动作之后还能继续接收反馈，并根据反馈改变下一步。

比如旅行助手接到任务“帮我查北京天气，再推荐景点”。它不会一口气凭空把答案全说完，而应该是：

- 先意识到第一步缺少天气信息。
- 调天气工具去查。
- 拿到结果后发现今天晴天。
- 再根据“晴天”这个新观察去调用景点推荐工具。
- 最后把天气和景点合成一个完整回答。

也就是说，它不是“一次完成”，而是“一轮一轮推进”。

对于 LLM 智能体来说，“思考”阶段通常又可以细分成两个子过程：

- <strong>规划（Planning）</strong>：当前局面是什么？我离目标还有多远？下一步最合理的子任务是什么？
- <strong>工具选择（Tool Selection）</strong>：如果需要行动，该用哪个工具？参数该怎么填？

这就是为什么一个好用的 Agent，不只是模型会说话而已，而是模型在持续承担“局势判断”和“下一步决策”的角色。

### 1.2.3 智能体的感知与行动

#### 交互协议为什么长成 Thought / Action / Observation？

可以把它想成「人机交接单」：

- `Thought`：给人类看的推理痕迹（也给模型自己当短期草稿）。
- `Action`：给程序解析的可执行指令。
- `Observation`：给模型下一轮用的环境反馈（尽量短、干净、自然语言化）。

**常见翻车点**：

1. 模型一次输出两对 Thought-Action → 需要截断/只取第一对。  
2. Action 格式漂移（少引号、多换行）→ 正则解析失败。  
3. 把原始巨型 JSON 直接当 Observation → 浪费上下文且干扰推理。

后面 1.3 的旅行助手，就是把这套协议落到 Python 里。


理论上说“感知-思考-行动”很顺，但真正落到工程里，必须回答一个非常实际的问题：<strong>模型到底怎么和外部世界对接？</strong>

总不能让模型自由发挥一大段自然语言，然后程序员再靠猜测去判断它到底是想调用工具，还是已经给了最终答案。这样系统会非常脆弱。

所以，在很多现代 Agent 框架里，都会给模型约定一种相对结构化的输出协议。一个最常见的结构就是：

- <strong>Thought</strong>：说明它现在怎么理解问题，下一步打算干什么。
- <strong>Action</strong>：明确告诉系统，它要执行哪个动作。

例如：

```Bash
Thought: 用户想知道北京的天气。我需要调用天气查询工具。
Action: get_weather("北京")
```

这两行非常重要。第一行让人类和系统都知道模型当前的思路，第二行则能被程序精确解析。于是，程序看到 `Action` 后，就可以真的去调用 `get_weather` 这个函数。

调用完以后，环境会返回原始结果。这个结果有时可能是 JSON，有时可能是一长串接口数据。但模型下一轮更适合接收的是结构清晰、信息干净的文本，所以系统通常还会把工具输出包装成 `Observation`：

```Bash
Observation: 北京当前天气为晴，气温25摄氏度，微风。
```

然后把它喂回模型，进入下一轮。

这时候你就能看明白一个很关键的工程事实：<strong>Thought、Action、Observation 不只是提示词格式，它们是把“语言世界”和“真实执行世界”接起来的接口层。</strong>

没有这层接口，模型就只是会说；有了这层接口，模型才开始真的能做。

## 1.3 动手体验：5 分钟实现第一个智能体

前面讲了不少概念，现在要把这些概念压缩进一段可以运行的代码里。你在看这一节时，不要只想着“能不能跑通”，更重要的是看懂每一段代码各自负责什么。

你可以把一个最小可运行 Agent 拆成四层：

1. <strong>角色层</strong>：它是谁，要解决什么任务
2. <strong>工具层</strong>：它拥有哪些能力
3. <strong>循环层</strong>：它怎么一轮轮推进任务
4. <strong>终止层</strong>：它什么时候该停

只要把这四层看清楚，你以后看到更复杂的 Agent 框架，也不会被表面代码吓到。

这一节里，我们要做的是一个最小旅行助手。用户说：“帮我查询今天北京的天气，然后根据天气推荐一个合适的旅游景点。”这件事不算大，但特别适合拿来做教学样例，因为它刚好包含了完整 Agent 闭环：

- 先获取外部信息
- 再基于新信息决策
- 最后给出综合结果

### 1.3.1 准备工作

#### 代码导读：这一节三块东西各自干什么？

1. **`AGENT_SYSTEM_PROMPT`**：角色说明书。它规定「有哪些工具」「输出必须长什么样」「何时 Finish」。没有它，模型会自由聊天，程序无法稳定解析。  
2. **`get_weather`**：真实环境传感器+执行器的最小例子——发 HTTP、解析 JSON、返回一句人话。  
3. **`get_attraction`**：依赖外部搜索（Tavily）。它演示「模型知识不够时，用工具补实时信息」。

**为何工具返回值要写成自然语言？**  
因为下一轮要把 Observation 拼进 Prompt；模型更擅长读「北京晴，26℃」，而不是嵌套 JSON。

**依赖提醒**：`TAVILY_API_KEY` 没配时，工具应返回明确错误字符串，让 Agent 在 Observation 里看见失败原因，而不是静默崩溃。


为了让 Python 程序能访问外部世界，我们先安装几个依赖：

- `requests`：负责发 HTTP 请求
- `tavily-python`：负责搜索网络信息
- `openai`：负责调用兼容 OpenAI 接口的大语言模型

安装命令如下：

```bash
pip install requests tavily-python openai
```

先别急着记包名，更重要的是理解：<strong>智能体之所以能“做事”，本质上是因为它背后接了真实工具。</strong> 没有工具，模型再聪明，也只能靠已有知识猜；接上工具，它才开始能查实时天气、读网页、发请求、改文件、执行命令。

（1）指令模板

接下来是这个案例里最关键的一部分之一：给模型写“说明书”。你可以把它理解成这个智能体的岗位说明、行为规则和输出协议。

这里不是随便写一句“你是一个旅行助手”就够了。我们还需要告诉它：

- 你有哪些工具可以用
- 你每次输出应该长什么样
- 什么时候该继续行动
- 什么时候该结束任务

也就是说，这段 `system prompt` 其实就在帮我们塑造一个能被程序接住的“半结构化智能体”。

```
AGENT_SYSTEM_PROMPT = """
你是一个智能旅行助手。你的任务是分析用户的请求，并使用可用工具一步步地解决问题。

# 可用工具:
- `get_weather(city: str)`: 查询指定城市的实时天气。
- `get_attraction(city: str, weather: str)`: 根据城市和天气搜索推荐的旅游景点。

# 输出格式要求:
你的每次回复必须严格遵循以下格式，包含一对Thought和Action：

Thought: [你的思考过程和下一步计划]
Action: [你要执行的具体行动]

Action的格式必须是以下之一：
1. 调用工具：function_name(arg_name="arg_value")
2. 结束任务：Finish[最终答案]

# 重要提示:
- 每次只输出一对Thought-Action
- Action必须在同一行，不要换行
- 当收集到足够信息可以回答用户问题时，必须使用 Action: Finish[最终答案] 格式结束

请开始吧！
"""
```

如果你第一次看这段代码，可能会觉得它只是“写给模型看的提示词”。但从工程角度看，它干了三件非常重要的事：

1. 限定角色，避免模型跑偏
2. 暴露工具，让模型知道自己有哪些手段
3. 强制输出格式，方便后续程序解析

这三件事少任何一件，系统稳定性都会明显下降。

（2）工具 1：查询真实天气

下面我们先给智能体接一个最简单也最直观的工具：查天气。这里使用的是免费的 `wttr.in` 服务。

你在读这个函数时，可以重点看三件事：

- 它如何向外部 API 发起请求
- 它如何从返回结果中提取关键信息
- 它如何把机器数据整理成模型更容易理解的自然语言

```python
import requests

def get_weather(city: str) -> str:
    """
    通过调用 wttr.in API 查询真实的天气信息。
    """
    # API端点，我们请求JSON格式的数据
    url = f"https://wttr.in/{city}?format=j1"
    
    try:
        # 发起网络请求
        response = requests.get(url)
        # 检查响应状态码是否为200 (成功)
        # 自动检查 HTTP 响应状态码，非成功状态直接抛出异常。
        response.raise_for_status() 
        # 解析返回的JSON数据
        data = response.json()
        
        # 提取当前天气状况
        current_condition = data['current_condition'][0]
        weather_desc = current_condition['weatherDesc'][0]['value']
        temp_c = current_condition['temp_C']
        
        # 格式化成自然语言返回
        return f"{city}当前天气:{weather_desc}，气温{temp_c}摄氏度"
        
    except requests.exceptions.RequestException as e:
        # 处理网络错误
        return f"错误:查询天气时遇到网络问题 - {e}"
    except (KeyError, IndexError) as e:
        # 处理数据解析错误
        return f"错误:解析天气数据失败，可能是城市名称无效 - {e}"
```

这个函数虽然短，但很有代表性。它说明了工具函数在 Agent 里通常不需要特别花哨，关键是：

- 输入明确
- 输出清晰
- 出错时也能返回可读结果

为什么错误信息也要返回字符串，而不是直接让程序崩掉？因为智能体拿到错误信息后，理论上还可以继续思考，比如换个参数、提示用户补充信息，或者结束任务并解释原因。

（3）工具 2：搜索并推荐旅游景点

现在只有天气还不够，我们还要接第二个工具，让它能根据天气继续推荐景点。这里用的是 Tavily 搜索服务。

这个工具比前一个稍微复杂一点，因为它做的不只是“拿到一条数据”，而是“根据查询词，从互联网上汇总较适合的结果”。

```python
import os
from tavily import TavilyClient

def get_attraction(city: str, weather: str) -> str:
    """
    根据城市和天气，使用Tavily Search API搜索并返回优化后的景点推荐。
    """
    # 1. 从环境变量中读取API密钥
    api_key = os.environ.get("TAVILY_API_KEY")
    if not api_key:
        return "错误:未配置TAVILY_API_KEY环境变量。"

    # 2. 初始化Tavily客户端
    tavily = TavilyClient(api_key=api_key)
    
    # 3. 构造一个精确的查询
    query = f"'{city}' 在'{weather}'天气下最值得去的旅游景点推荐及理由"
    
    try:
        # 4. 调用API，include_answer=True会返回一个综合性的回答
        response = tavily.search(query=query, search_depth="basic", include_answer=True)
        
        # 5. Tavily返回的结果已经非常干净，可以直接使用
        # response['answer'] 是一个基于所有搜索结果的总结性回答
        if response.get("answer"):
            return response["answer"]
        
        # 如果没有综合性回答，则格式化原始结果
        formatted_results = []
        for result in response.get("results", []):
            formatted_results.append(f"- {result['title']}: {result['content']}")
        
        if not formatted_results:
             return "抱歉，没有找到相关的旅游景点推荐。"

        return "根据搜索，为您找到以下信息:\n" + "\n".join(formatted_results)

    except Exception as e:
        return f"错误:执行Tavily搜索时出现问题 - {e}"
```

这里你要特别注意一点：这个函数接收的不是“城市”一个参数，而是“城市 + 天气”。这意味着智能体不是在孤立地调用工具，而是在把前一轮的结果带进下一轮。这就是多步任务的雏形。

最后，我们把工具统一放进字典里，便于后面主循环按名字调用：

```python
# 将所有工具函数放入一个字典，方便后续调用
available_tools = {
    "get_weather": get_weather,
    "get_attraction": get_attraction,
}
```

这看起来只是个小细节，但它其实很重要。因为一旦工具都被标准化地挂进同一个表，主循环就能变得通用：模型只要输出工具名，系统就能去表里找对应函数执行。

### 1.3.2 接入大语言模型

#### 概念铺垫：什么叫「OpenAI 兼容接口」？

很多云厂商和本地推理框架（Ollama、vLLM 等）都提供与 OpenAI Chat Completions 类似的 HTTP API。于是我们只写一个客户端类，换 `base_url` / `api_key` / `model` 就能切换后端。

**`OpenAICompatibleClient.generate` 在干什么？**

- 组装 `system` + `user` 两条消息；
- 调用 `chat.completions.create`；
- 取出 `message.content` 作为模型本轮输出。

对 Agent 来说，这一步就是「大脑思考一次」。循环外层负责把历史拼进 `prompt`，并把 Thought/Action 解析出来去干活。


有了工具之后，还差一个“大脑”，也就是负责读上下文、做决策、输出 Thought 和 Action 的大语言模型。

这里我们使用一个兼容 OpenAI 接口的客户端封装类。这样做的好处是，只要不同服务商遵循相似的 API 规范，我们就能比较平滑地切换底层模型，而不用把业务逻辑重写一遍。

```python
from openai import OpenAI

class OpenAICompatibleClient:
    """
    一个用于调用任何兼容OpenAI接口的LLM服务的客户端。
    """
    def __init__(self, model: str, api_key: str, base_url: str):
        self.model = model
        self.client = OpenAI(api_key=api_key, base_url=base_url)

    def generate(self, prompt: str, system_prompt: str) -> str:
        """调用LLM API来生成回应。"""
        print("正在调用大语言模型...")
        try:
            messages = [
                {'role': 'system', 'content': system_prompt},
                {'role': 'user', 'content': prompt}
            ]
            response = self.client.chat.completions.create(
                model=self.model,
                messages=messages,
                stream=False
            )
            answer = response.choices[0].message.content
            print("大语言模型响应成功。")
            return answer
        except Exception as e:
            print(f"调用LLM API时发生错误: {e}")
            return "错误:调用语言模型服务时出错。"
```

你可以把这个类理解成“模型适配层”。后面的 Agent 主循环不需要关心你到底在用 OpenAI、Azure、Ollama 还是别的兼容服务，它只关心一件事：给你提示词，你能不能返回模型输出。

这种封装思路在真实工程里非常常见。因为一旦业务逻辑和模型调用逻辑耦合得太死，后面换模型、换平台、做 AB 测试、接本地部署，都会很痛苦。

要实例化这个类，你需要准备：

- `API_KEY`
- `BASE_URL`
- `MODEL_ID`

如果你暂时没有相应服务，也可以先把这部分当成“接口层结构”来理解，后面再接真实模型。

### 1.3.3 执行行动循环

#### 主循环逐行导读（抓住五件事）

1. **`prompt_history`**：短期记忆。每一轮的模型输出和 Observation 都追加进去，下一轮模型才能「接着想」。  
2. **`for i in range(5)`**：最大轮次护栏，防止死循环烧钱。  
3. **正则截断多余 Thought-Action**：模型有时会一次写两步，先只执行第一步更稳。  
4. **解析 `Action:`**：`Finish[...]` 则结束；否则解析 `tool(arg="...")` 并查 `available_tools`。  
5. **把结果写成 `Observation:` 再 append**：闭环的关键一环。

**自己调试时优先看**：是不是解析失败？是不是工具名拼错？是不是 Observation 没写回 history？这三类问题占新手坑的大多数。


前面的东西现在终于可以串起来了。下面这段主循环，是整个案例最值得你认真读懂的部分，因为它展示了一个最小 Agent 是怎么跑起来的。

读代码时建议你一直问自己四个问题：

1. 当前上下文是怎么累计的？
2. 模型输出后，系统怎么解析？
3. 工具怎么被真正执行？
4. 结果又是怎么回流给模型的？

```python
import re

# --- 1. 配置LLM客户端 ---
# 请根据您使用的服务，将这里替换成对应的凭证和地址
API_KEY = "YOUR_API_KEY"
BASE_URL = "YOUR_BASE_URL"
MODEL_ID = "YOUR_MODEL_ID"
TAVILY_API_KEY="YOUR_Tavily_KEY"
os.environ['TAVILY_API_KEY'] = "YOUR_TAVILY_API_KEY"

llm = OpenAICompatibleClient(
    model=MODEL_ID,
    api_key=API_KEY,
    base_url=BASE_URL
)

# --- 2. 初始化 ---
user_prompt = "你好，请帮我查询一下今天北京的天气，然后根据天气推荐一个合适的旅游景点。"
prompt_history = [f"用户请求: {user_prompt}"]

print(f"用户输入: {user_prompt}\n" + "="*40)

# --- 3. 运行主循环 ---
for i in range(5): # 设置最大循环次数
    print(f"--- 循环 {i+1} ---\n")
    
    # 3.1. 构建Prompt
    full_prompt = "\n".join(prompt_history)
    
    # 3.2. 调用LLM进行思考
    llm_output = llm.generate(full_prompt, system_prompt=AGENT_SYSTEM_PROMPT)
    # 模型可能会输出多余的Thought-Action，需要截断
    match = re.search(r'(Thought:.*?Action:.*?)(?=\n\s*(?:Thought:|Action:|Observation:)|\Z)', llm_output, re.DOTALL)
    if match:
        truncated = match.group(1).strip()
        if truncated != llm_output.strip():
            llm_output = truncated
            print("已截断多余的 Thought-Action 对")
    print(f"模型输出:\n{llm_output}\n")
    prompt_history.append(llm_output)
    
    # 3.3. 解析并执行行动
    action_match = re.search(r"Action: (.*)", llm_output, re.DOTALL)
    if not action_match:
        observation = "错误: 未能解析到 Action 字段。请确保你的回复严格遵循 'Thought: ... Action: ...' 的格式。"
        observation_str = f"Observation: {observation}"
        print(f"{observation_str}\n" + "="*40)
        prompt_history.append(observation_str)
        continue
    action_str = action_match.group(1).strip()

    if action_str.startswith("Finish"):
        final_answer = re.match(r"Finish\[(.*)\]", action_str).group(1)
        print(f"任务完成，最终答案: {final_answer}")
        break
    
    tool_name = re.search(r"(\w+)\(", action_str).group(1)
    args_str = re.search(r"\((.*)\)", action_str).group(1)
    kwargs = dict(re.findall(r'(\w+)="([^"]*)"', args_str))

    if tool_name in available_tools:
        observation = available_tools[tool_name](**kwargs)
    else:
        observation = f"错误:未定义的工具 '{tool_name}'"

    # 3.4. 记录观察结果
    observation_str = f"Observation: {observation}"
    print(f"{observation_str}\n" + "="*40)
    prompt_history.append(observation_str)
```

这段代码值得你慢一点看，我把它拆给你：

- `prompt_history` 是智能体的短期工作记忆。它把用户请求、模型输出、工具结果按时间顺序存起来。
- 每一轮开始时，系统把历史拼起来形成 `full_prompt`，这相当于告诉模型“我们已经走到哪一步了”。
- 模型输出后，程序用正则从里面截出结构化的 `Thought + Action`。
- 如果 `Action` 是 `Finish[...]`，说明任务结束。
- 如果 `Action` 是工具调用，就解析工具名和参数，去 `available_tools` 里真正执行。
- 工具返回的结果被包装成 `Observation`，再追加回历史中，供下一轮继续思考。

这就是一个最小闭环。

这里还有两个特别值得你注意的工程细节。

第一，为什么要设置最大循环次数 `for i in range(5)`？因为真实模型有可能跑偏，或者一直重复尝试，或者在某个状态里兜圈子。不给上限，系统就可能无限循环。

第二，为什么还要专门做输出截断和格式校验？因为模型再聪明，也不保证每次都老老实实按格式输出。Agent 工程里一个重要现实就是：<strong>你不能假设模型永远听话，必须给它加护栏。</strong>

所以，如果你以后看各种 Agent 框架发现里面有很多“解析器”“校验器”“重试机制”“fallback 分支”，不要觉得那是多余代码。恰恰相反，那些才是让原型变成可用系统的关键部分。

### 1.3.4 运行案例分析

#### 把三轮日志映射回理论

| 循环 | Thought 在干什么 | Action | Observation 提供了什么 |
|------|------------------|--------|------------------------|
| 1 | 任务分解：先天气后景点 | `get_weather` | 晴、26℃ |
| 2 | 用天气作约束推景点 | `get_attraction` | 颐和园/长城等建议 |
| 3 | 信息够了，合成答复 | `Finish[...]` | （任务结束）|

这正是：**任务分解 → 工具调用 → 上下文理解 → 结果合成**。若第 1 轮天气失败，合格 Agent 应在 Thought 里改策略（换城市名/报错给用户），而不是假装成功。


下面来看一个完整运行过程。它只跑了三轮，但这三轮已经足够把 Agent 的基本工作方式展示清楚。

```bash
用户输入: 你好，请帮我查询一下今天北京的天气，然后根据天气推荐一个合适的旅游景点。
========================================
--- 循环 1 ---

正在调用大语言模型...
大语言模型响应成功。
模型输出:
Thought: 首先需要获取北京今天的天气情况，之后再根据天气情况来推荐旅游景点。
Action: get_weather(city="北京")

Observation: 北京当前天气:Sunny，气温26摄氏度
========================================      
--- 循环 2 ---

正在调用大语言模型...
大语言模型响应成功。
模型输出:
Thought: 现在已经知道了北京今天的天气是晴朗且温度适中，接下来可以基于这个信息来推荐一个适合的旅游景点了。
Action: get_attraction(city="北京", weather="Sunny")

Observation: 北京在晴天最值得去的旅游景点是颐和园，因其美丽的湖景和古建筑。另一个推荐是长城，因其壮观的景观和历史意义。
========================================
--- 循环 3 ---

正在调用大语言模型...
大语言模型响应成功。
模型输出:
Thought: 已经获得了两个适合晴天游览的景点建议，现在可以根据这些信息给用户提供满意的答复。
Action: Finish[今天北京的天气是晴朗的，气温26摄氏度，非常适合外出游玩。我推荐您去颐和园欣赏美丽的湖景和古建筑，或者前往长城体验其壮观的景观和深厚的历史意义。希望您有一个愉快的旅行！]

任务完成，最终答案: 今天北京的天气是晴朗的，气温26摄氏度，非常适合外出游玩。我推荐您去颐和园欣赏美丽的湖景和古建筑，或者前往长城体验其壮观的景观和深厚的历史意义。希望您有一个愉快的旅行！
```

这三轮可以非常清楚地拆开来看。

第一轮，智能体并没有急着直接给答案，而是先意识到自己缺少关键信息。这说明它具备了最基础的任务分解意识。

第二轮，它没有重新从头乱想，而是把上一轮得到的天气结果作为条件，继续执行下一步。这说明它在利用上下文推进任务。

第三轮，它不再调用工具，而是判断“信息已经够了”，于是收束成最终回答。这说明它不只是会用工具，还会决定何时停止。

所以，这个小案例虽然简单，却已经包含了 Agent 的四个核心能力：

- <strong>任务分解</strong>
- <strong>工具调用</strong>
- <strong>上下文承接</strong>
- <strong>结果合成与结束判断</strong>

如果你能真正读懂这一节，后面再学 LangChain、LlamaIndex、LangGraph、AutoGen 等框架时，你会更容易透过框架表面看到本质：这些框架大多是在帮你把这套循环写得更稳、更大、更可控。

## 1.4 智能体应用的协作模式

学到这里，很多人会自然冒出一个问题：那以后是不是所有软件都该做成 Agent？

答案是：<strong>不是。</strong>

这是初学者特别容易踩的一个坑。因为智能体概念很吸引人，看上去很“高级”，于是容易产生一种错觉，好像系统越自主越先进。但真实工程世界讲究的不是“听起来先进”，而是“是不是稳定、是不是合适、是不是划算”。

所以这一节的重点，就是帮你建立一种更成熟的判断：智能体在实际应用里，常见的协作位置到底是什么？什么时候它更像工具？什么时候它更像协作者？它和传统 Workflow 的边界又在哪里？

### 1.4.1 作为开发者工具的智能体

#### 对照表：工具型 Agent 的共同点

GitHub Copilot、Claude Code、Trae、Cursor 差异很大，但共享一个协作模式：

- **人仍在回路**：最终合并代码、上线责任在开发者。  
- **上下文是编辑器/仓库**：智能体感知的是文件、终端、诊断信息。  
- **目标是加速而非完全托管**：适合高频、可验证的局部任务。

**选型直觉**：要「补全顺手」看插件型；要「整库对话/多文件改」看 AI 原生编辑器或 CLI Agent。


在第一种模式下，智能体并不是来替代人的，而是来增强人的。它更像一个能力很强、反应很快、上下文记忆不错的搭档。

比如在软件开发里，它可以：

- 帮你补全代码
- 帮你解释报错
- 帮你查 API 文档
- 帮你生成测试样例
- 帮你重构重复逻辑
- 帮你在大型代码库里定位问题

这时候，主导权仍然主要在人手里。人负责定义目标、判断质量、做最后决策；Agent 负责把很多繁琐、重复、搜索型、草稿型工作接过去。

市场上已经有很多典型产品：

- <strong>GitHub Copilot</strong>：强在编辑器内代码补全和即时建议，后续也扩展到对话式编程。
- <strong>Claude Code</strong>：更强调终端里的自然语言驱动开发，擅长在代码库上下文中执行编辑、测试、调试。
- <strong>Trae</strong>：主打智能代码生成与优化，适合快速迭代和原型开发。
- <strong>Cursor</strong>：作为 AI 原生编辑器，更强调让 AI 深度理解整个代码库，从而支持问答、重构、调试、修改等更完整的开发动作。

你不必把所有产品的区别死记下来，更值得记住的是它们共同说明了一件事：<strong>AI 进入软件开发，第一站往往不是“完全替代开发者”，而是“先成为一个极强的开发工具”。</strong>

这条路线为什么现实？因为它风险更低、可控性更强、落地门槛更小。就像一个实习生刚加入团队时，先从辅助工作做起，通常比一上来独立接管整个项目更靠谱。

### 1.4.2 作为自主协作者的智能体

#### 三种架构方向，用「项目组」类比

1. **单智能体自主循环**（如早期 AgentGPT）：一个全能同事从早忙到晚，简单目标够用，复杂目标易失控。  
2. **多智能体协作**：产品经理/工程师/测试各扮演角色（CAMEL、MetaGPT、CrewAI、AutoGen…）——像真正的小团队。  
3. **状态图控制流**（如 LangGraph）：把循环、分支、人工审批画成图，工程可控性更强。

后面章节会具体碰框架；第一章只需建立地图：**自主性升高 → 需要更强的角色分工、协议与状态管理。**


另一种模式就更进一步了。在这种模式下，我们不再告诉智能体每一步要做什么，而是直接给一个比较高层的目标，让它自己拆、自己排、自己执行、自己反思。

比如你不再说“先查天气，再查酒店，再给我一个行程表”，而是直接说：“帮我做一个适合亲子家庭的三天厦门旅行方案，预算控制在 5000 元以内。”

这时，智能体就更像一个被委托任务的协作者，而不只是一个会响应指令的工具。

近几年出现了很多朝这个方向探索的框架和产品，比如：

- BabyAGI
- AutoGPT
- CrewAI
- AutoGen
- MetaGPT
- LangGraph

虽然这些系统的实现方式差别很大，但大致可以归成几条路线：

1. <strong>单智能体自主循环</strong>

一个智能体围绕目标不断自我迭代，进行“思考-规划-执行-反思”。这种模式结构相对直接，适合展示 Agent 的自主闭环能力。

2. <strong>多智能体协作</strong>

这类系统会模拟团队分工。比如一个负责规划，一个负责编码，一个负责测试，一个负责写文档。它们像一个虚拟项目组，通过角色分工和对话协作完成复杂任务。

3. <strong>高级控制流架构</strong>

像 LangGraph 这样的框架，更强调底层执行图、状态流转、循环分支和人工介入点。它不是简单把多个 Agent 拼起来，而是给你一套更稳的工程控制结构。

这条路线听起来很诱人，因为它让我们看到“数字协作者”的可能性。但你一定要同时看到它的另一面：自主性越高，系统越难调、越难控、越难保证稳定。

一个能自主调用十个工具、运行多轮计划的 Agent，听起来很强，但也更可能：

- 误解任务
- 调错工具
- 在错误分支里越走越远
- 成本失控
- 结果不可复现

所以，“作为协作者”的模式虽然很吸引人，但它绝不是“更高级所以一定更好”，而是“能力更强，但工程要求也更高”。

### 1.4.3 Workflow 和 Agent 的差异

#### 一张决策表：什么时候用 Workflow，什么时候用 Agent？

| 问题 | 偏 Workflow | 偏 Agent |
|------|-------------|----------|
| 步骤能否事先写死？ | 能 | 不能，要边做边定 |
| 失败是否可接受探索？ | 否，要可审计 | 可，允许试错 |
| 输入是否高度结构化？ | 是 | 常是自然语言/开放任务 |
| 成本与延迟敏感？ | 更可控 | 可能多轮调用更贵 |

**方案 C（常见生产形态）**：外层 Workflow 管合规与阶段门禁，内层局部 Agent 处理开放子任务（例如「理解用户投诉原因」），争议单再转人工。


最后，这一章里还有一个必须讲透的概念：<strong>Workflow 和 Agent 到底有什么区别？</strong>

这两个词在很多文章里经常混着用，所以特别容易把初学者搞晕。你可以先记一句最简洁的话：

<strong>Workflow 是把路径提前写好；Agent 是把目标给出来，再让系统动态决定路径。</strong>

Workflow 像什么？像流程图。你提前定义好：

- 第一步做什么
- 第二步做什么
- 满足什么条件走左边
- 不满足什么条件走右边

比如企业报销流程就是典型 Workflow：

- 员工提交报销单
- 小于 500 元，经理审批
- 大于 500 元，再转财务总监
- 审批通过后触发打款

这类流程的优点非常明显：

- 稳定
- 可审计
- 结果可预测
- 易于控制风险

但它的前提是：你对流程已经很清楚，场景变化也相对有限。

Agent 则不一样。它不是所有步骤都提前写死，而是只给目标和边界，让系统边执行边判断。还是用旅行助手举例：

1. 它先把任务拆成“查天气”和“推荐景点”。
2. 它自主选择先调用天气工具。
3. 拿到“晴天”结果后，它再推理出“适合户外活动”。
4. 然后再选择合适景点并组织最终回答。

这里最关键的一点是：没有人提前写死“如果晴天就一定推荐某景点”。它是根据实时信息动态决定的。

这也是 Agent 最核心的魅力所在：它能在不确定环境中继续推进任务，而不是一旦脱离预设路径就立刻卡住。

但这并不意味着 Agent 一定比 Workflow 高级。很多场景里，Workflow 反而更合适。比如规则明确、流程固定、合规要求高、出错代价大的业务，往往更适合 Workflow。智能体更适合那些目标明确但路径难以完全预定义、需要灵活判断和多步探索的任务。

真实系统里，一个越来越常见的做法是：<strong>让 Workflow 负责兜底和护栏，让 Agent 负责局部灵活决策。</strong>

比如：

- 大流程由 Workflow 控制
- 某几个需要理解文本、判断意图、生成方案的节点交给 Agent
- 关键节点保留人工审核

这通常比“全 Workflow”更灵活，也比“全 Agent”更稳。

## 1.4 本章小结

读到这里，你应该已经能把“智能体”从一个流行词，慢慢还原成一个更扎实的概念了。

这一章最值得带走的，不是某个术语定义，而是下面这几个核心判断。

第一，<strong>智能体的核心不在“会聊天”，而在“会围绕目标形成闭环”。</strong> 它会感知环境、做判断、采取行动、接收反馈，再根据反馈继续往前走。

第二，<strong>现代 Agent 很新，但它的很多思想并不新。</strong> 从反射式智能体到基于模型、基于目标、基于效用，再到学习型智能体，今天的大模型 Agent 其实是站在这些历史积累上的。

第三，<strong>LLM 给智能体带来的最大变化，不只是“更会说”，而是“更能接住模糊任务”。</strong> 它让系统开始有能力处理高层目标、自然语言需求和动态上下文。

第四，<strong>Agent 的运转本质上是一个循环。</strong> 感知、思考、行动、观察，再进入下一轮。后面你学到的大多数框架，本质上都在增强这个循环，而不是推翻它。

第五，<strong>不是所有自动化都该做成 Agent。</strong> Workflow 和 Agent 各有适用边界。真正成熟的系统设计，不是盲目追求“更自主”，而是找到“刚刚好的自主性”。

如果你现在愿意回头看一眼生活里的系统，比如导航软件、外卖派单、智能客服、代码助手，你已经可以用这一章的框架去分析它们了：

- 它的环境是什么？
- 它能看到什么？
- 它能做什么？
- 它是按固定流程执行，还是会动态决策？
- 它到底更像 Workflow，还是更像 Agent？

当你开始能这样分析时，就说明你不是只「看过」这一章，而是真的开始理解它了。

## 深度加厚：把第一章「串成一条可执行故事」

下面不引入新知识点编号，只把原版已有知识用一条连续故事再讲一遍。若你读正文仍觉得散，先读这一节。

### 故事设定

你要做一个「周末北京半日游助手」。用户只说一句：「明天去北京玩，别太累，预算别太高。」

### 第一步：先当系统设计者，填 PEAS（对应 1.2.1）

- **P**：给出可执行半日行程；强度中低；预估花费可接受；说明天气依据。  
- **E**：天气 API、景点检索、用户聊天窗口；票价与人流会变。  
- **A**：查天气函数、搜景点函数、最终自然语言答复；**没有**下单权限。  
- **S**：用户原话、工具返回文本。

环境特性：部分可观察（搜不到全部景点）、随机（临时闭园）、动态（天气变）、序贯（先天气后景点）。

### 第二步：选架构类型（对应 1.1.1 / 1.1.3）

- 只做「温度>35 就劝室内」→ 简单反射够用。  
- 要记住用户说「别太累」并影响后续推荐 → 需要状态（基于模型的雏形）。  
- 要规划「上午–中午–下午」 → 目标/规划。  
- 要在「少走路」和「必看代表作」之间权衡 → 效用。  
- 要根据用户连续拒绝调整策略 → 学习/反思（后面章节会展开）。

时间维度上：紧急「暴雨预警」要反应式；行程编排要审议式；LLM Agent 用小循环混合二者。

知识表示上：LLM 提供亚符号直觉；`Action: get_weather(city="北京")` 是符号接口；合在一起就是神经符号实践。

### 第三步：跑 Agent Loop（对应 1.2.2–1.3）

1. 感知：用户请求进入 `prompt_history`。  
2. 思考：模型输出 Thought「先查天气」。  
3. 行动：解析器调用 `get_weather`。  
4. 观察：`Observation: …晴…`。  
5. 再思考：基于晴天与「别太累」选颐和园而非爬长城。  
6. Finish：合成最终答案。

若解析失败，不要假装成功：把错误写成 Observation，让模型自我纠正——这是工程闭环，不是「模型不够聪明」一句话能概括的。

### 第四步：决定产品形态（对应 1.4）

- 做 VS Code 插件帮写旅行爬虫 → 开发者工具模式。  
- 交给一队角色 Agent 自动出攻略 PDF → 自主协作者模式。  
- 公司报销审批仍用 Workflow；「理解用户投诉原因」可用 Agent 子模块。

### 第五步：对照 Workflow vs Agent（对应 1.4.3）

若产品经理要求「任何推荐必须经过人工审核才能发出」，外层应是 Workflow 门禁；内层 Agent 只生成候选。自主性不是越高越好。

### 术语速查（加厚版）

| 术语 | 你应用自己的话能解释成 |
|------|------------------------|
| 传感器 | 智能体「读世界」的通道 |
| 执行器 | 智能体「改世界」的通道 |
| 自主性 | 在边界内自己决定下一步 |
| 世界模型 | 对不可见部分也保持的内部估计 |
| PEAS | 成功标准/环境/执行器/传感器 |

## 习题

下面这些习题不是让你机械复述概念，而是希望你开始像系统设计者一样思考。真正学会 Agent，往往不是靠背定义，而是靠不断问自己：“如果是我来设计，这里应该怎么做？”

> <strong>提示</strong>：以下的部分习题没有标准答案，重点在于培养学习者对智能体系统批判性的深入思考和动手实践能力。

1. 请分析以下四个 `case` 中的<strong>主体</strong>是否属于智能体，如果是，那么属于哪种类型的智能体（可以从多个分类维度进行分析），并说明理由：

   `case A`：<strong>一台符合冯·诺依曼结构的超级计算机</strong>，拥有高达每秒 2EFlop 的峰值算力

   `case B`：<strong>特斯拉自动驾驶系统</strong>在高速公路上行驶时，突然检测到前方有障碍物，需要在毫秒级做出刹车或变道决策

   `case C`：<strong>AlphaGo</strong>在与人类棋手对弈时，需要评估当前局面并规划未来数十步的最优策略

   `case D`：<strong>ChatGPT 扮演的智能客服</strong>在处理用户投诉时，需要查询订单信息、分析问题原因、提供解决方案并安抚用户情绪

2. 假设你需要为一个"智能健身教练"设计任务环境。这个智能体能够：
   - 通过可穿戴设备监测用户的心率、运动强度等生理数据
   - 根据用户的健身目标（减脂/增肌/提升耐力）动态调整训练计划
   - 在用户运动过程中提供实时语音指导和动作纠正
   - 评估训练效果并给出饮食建议

   请使用 PEAS 模型完整描述这个智能体的任务环境，并分析该环境具有哪些特性（如部分可观察、随机性、动态性等）。

3. 某电商公司正在考虑两种方案来处理售后退款申请：
   
   方案 A（`Workflow`）：设计一套固定流程，例如：

   A.1 对于一般商品且在 7 天之内，金额 `< 100RMB` 自动通过；`100-500RMB `由客服审核；`>500RMB` 需主管审批；而特殊商品（如定制品）一律拒绝退款
   
   A.2 对于超过 7 天的商品，无论金额，只能由客服审核或主管审批；
   
   方案 B（`Agent`）：搭建一个智能体系统，让它理解退款政策、分析用户历史行为、评估商品状况，并自主决策是否批准退款
   
   请分析：
   - 这两种方案各自的优缺点是什么？
   - 在什么情况下 `Workflow` 更合适？什么情况下 `Agent` 更有优势？如果你是该电商公司的负责人，你更倾向于采用哪种方案？
   - 是否存在一个方案 C，能够结合两种方案，达到扬长避短的效果？
   
4. 在 1.3 节的智能旅行助手基础上，请思考如何添加以下功能（可以只描述设计思路，也可以进一步尝试代码实现）：

   > <strong>提示</strong>：思考如何修改 `Thought-Action-Observation` 循环来实现这些功能。

   - 添加一个"记忆"功能，让智能体记住用户的偏好（如喜欢历史文化景点、预算范围等）
   - 当推荐的景点门票已售罄时，智能体能够自动推荐备选方案
   - 如果用户连续拒绝了 3 个推荐，智能体能够反思并调整推荐策略

5. 卡尼曼的"系统 1"（快速直觉）和"系统 2"（慢速推理）理论<sup>[2]</sup>为神经符号主义 AI 提供了很好的类比。请首先构思一个具体的智能体的落地应用场景，然后说明场景中的：

   > <strong>提示</strong>：医疗诊断助手、法律咨询机器人、金融风控系统等都是常见的应用场景

   - 哪些任务应该由"系统 1"处理？
   - 哪些任务应该由"系统 2"处理？
   - 这两个系统如何协同工作以达成最终目标？

6. 尽管大语言模型驱动的智能体系统展现出了强大的能力，但它们仍然存在诸多局限。请分析以下问题：
   - 为什么智能体或智能体系统有时会产生"幻觉"（生成看似合理但实际错误的信息）？
   - 在 1.3 节的案例中，我们设置了最大循环次数为 5 次。如果没有这个限制，智能体可能会陷入什么问题？
   - 如何评估一个智能体的"智能"程度？仅使用准确率指标是否足够？
