# 第九章 上下文工程

第八章我们给智能体装上了「短期便签 + 长期笔记本 + 外部图书馆」（Memory + RAG）。但真实长任务里很快会撞到另一堵墙：

- 检索回来的材料、对话历史、工具输出、系统指令……**全想塞进一次模型调用**，窗口装不下；
- 就算窗口很大，材料堆太多，模型也会「走神」——关键信息被淹没；
- 跨天、跨会话的重构/研究，不能只靠「把聊天记录越攒越长」。

这一章要补上的，就是：**在每一次调用模型之前，如何以可复用、可度量、可演进的方式，拼装并优化输入上下文**。这就是**上下文工程（Context Engineering）**。

你可以把本章理解成：给 Agent 配上「议程整理员 + 项目记事本 + 安全探查终端」——不只是「找得到」，还要「这一轮该看见什么、看见多少、怎么摆、超了怎么办」。

> **互动教程**：浏览器版约 41 页，含 GSSC 步进、窗口预算滑块、闪卡与自测，路径见  
> `docs/chapter9/interactive-tutorial/index.html`（与本学习版互补：HTML 适合刷概念，本文适合细读与复盘）。

## 读这一章之前，先建立心智模型

### 一个生活比喻

想象你在给同事开项目会，桌上只能摊开一叠材料：

| 人类动作 | Agent 对应 | 本章组件 |
|---------|-----------|---------|
| 先从柜子、邮箱、聊天里**收材料** | Gather | ContextBuilder |
| 按「相关 + 新鲜」**挑进议程包** | Select | ContextBuilder |
| 按固定栏目**装订**（角色/任务/证据…） | Structure | ContextBuilder |
| 桌面满了就**浓缩旧页**再继续 | Compress / Compaction | ContextBuilder + 长程策略 |
| 把进度写到**窗外的项目笔记** | Write（外存） | NoteTool |
| 需要时再去仓库**现场翻文件** | JIT 探索 | TerminalTool |
| 脏活交给助理，只拿回摘要 | Isolate（隔离） | 子代理架构（理念） |

LLM 像一位**注意力有限的顾问**：你塞给他的每一页，都会占用「注意力预算」。上下文工程不是「提示怎么写得更漂亮」这么简单，而是**整包材料怎么策划**。

### 几个关键词，先抓牢

- **上下文（Context）**：对 LLM **采样时包含的那一组 tokens**——系统指令、工具描述、消息历史、检索结果、笔记片段等，凡是模型「看得见」的都算。
- **上下文窗口（Context Window）**：一次调用里模型能看见的容量上限。像办公桌面积，不是无限大。
- **上下文腐蚀（Context Rot）**：窗口里 tokens 越多，模型从中**准确回忆/利用**信息的能力反而可能下降（边际收益递减）。
- **注意力预算**：每多一个 token 都要占一点「注意力」；因此要追求**高信号密度**，而不是「能塞尽塞」。
- **GSSC**：Gather → Select → Structure → Compress，HelloAgents `ContextBuilder` 的四步流水线。
- **JIT（Just-in-time）上下文**：不预加载整库，只维护轻量**引用**（路径、查询、URL），运行时用工具按需加载。
- **写入 / 选择 / 隔离（Write / Select / Isolate）**：把状态写到窗外；把高信号选进窗；把探索脏活隔离到子代理干净窗口，只回摘要。
- **MVTS（最小可行工具集）**：工具要职责清晰、低重叠；人类都说不准用哪个，别指望智能体选对。

### 第八章 vs 第九章（新手易混）

| 维度 | 第八章 · 记忆与检索 | 第九章 · 上下文工程 |
|-----|-------------------|-------------------|

## 9.1 什么是上下文工程

### 9.1.1 从「写好一句话」到「管好一整包」

经历数年之后，**提示工程（Prompt Engineering）**已经深入人心：怎么写系统提示、怎么加示例、怎么约束输出格式。但当智能体要**跨多轮、长时间、反复调工具**工作时，真正决定成败的，往往不再是某一句措辞，而是：

> **什么样的上下文配置，最有可能让模型产出我们期望的行为？**

所谓「上下文」，就是采样时那组 tokens。工程问题是：在 LLM 的固有约束下，**优化这些 tokens 的效用**。有效驾驭 LLM，常常需要「在上下文中思考」——审视模型**可见的整体状态**，并预判这种状态会诱发什么行为。

### 9.1.2 提示工程 vs 上下文工程

| | 提示工程 | 上下文工程 |
|--|---------|-----------|
| 焦点 | 指令措辞与结构化 | 推理期维护「最优信息集合」 |
| 范围 | 主要是系统/用户提示写法 | 提示 + 工具 + MCP + 外部数据 + 消息历史… |
| 典型场景 | 单轮分类、短文本生成 | 长时程、多轮、循环智能体 |
| 演进关系 | 基础功 | 提示工程的自然演进与上位集合 |

循环运行的智能体，每轮都会产生下一轮可能相关的数据，这些信息必须被**周期性地提炼**。上下文工程的「艺与术」，就是从不断扩张的**候选信息宇宙**中，甄别哪些进入**有限窗口**。

**新手自检**：若你只改「请」→「务必」，那是提示措辞；若你决定「本轮注入哪三条检索证据、丢掉哪段工具噪声」，那是上下文工程。

## 9.2 为什么上下文工程重要

### 9.2.1 上下文腐蚀与注意力预算

尽管模型更快、窗口更大，经验与「针堆找针」类基准仍显示：**上下文腐蚀（context rot）**——随着窗口中 tokens 增加，模型从上下文中准确回忆信息的能力反而可能下降。

因此：

1. **上下文是有限资源**，且具有**边际收益递减**；
2. LLM 像人类一样有「工作记忆 / 注意力预算」；
3. 每新增一个 token，都在消耗这笔预算。

**为何架构上会这样（理解即可，不必推导公式）**：

- Transformer 中，token 之间可形成约 \(n^2\) 级两两注意力关系；上下文越长，关系被「拉薄」；
- 训练分布往往更偏向短序列，模型对「全上下文依赖」的经验相对更少；
- 位置编码插值等技术可适配更长序列，但可能牺牲部分位置精度；
- 表现通常是**性能梯度下降**，而不是瞬间「悬崖式崩溃」。

**结论**：不能指望「窗口越大越好」自动解决问题；**有意识的上下文工程**是构建强健智能体的必需品。

> 比喻：桌面堆满发票时，反而找不到那张关键收据——不是桌子变小了，是注意力被稀释了。

### 9.2.2 有效上下文的「解剖学」

在有限注意力预算下，目标是：

> **用尽可能少、但高信号密度的 tokens，最大化获得期望结果的概率。**

围绕三类组件做工程：

#### （1）系统提示（System Prompt）

- 语言清晰、直白；信息层级「刚刚好」。
- **两极误区**：
  - **过度硬编码**：把脆弱的 if-else 逻辑写进提示，难维护；
  - **过于空泛**：只有宏观目标，缺少对期望输出的具体信号。
- **建议**：分区组织（如 `<background_information>`、`<instructions>`、工具指引、输出描述），用 XML/Markdown 分隔；追求能勾勒期望行为的**最小必要信息集**（「最小」≠「最短」）。
- **校准路径**：先用最强模型 + 最小提示试跑 → 按失败模式增补指令与示例。

#### （2）工具（Tools）与 MVTS

工具定义了智能体与信息/行动空间的契约，应：

- 职责单一、相互低重叠，接口语义清晰；
- 对错误鲁棒；返回 **token 友好** 的信息；
- 入参描述明确、无歧义。

常见失败：**臃肿工具集**——边界模糊，导致「选哪个工具」本身就含混。

> **如果人类工程师都说不准用哪个工具，别指望智能体做得更好。**  
> 精选 **最小可行工具集（MVTS）** 往往比「工具越多越好」更稳。

#### （3）示例（Few-shot）

- 始终推荐提供示例；
- **不要**把所有边界条件一股脑塞进提示；
- 精选**多样且典型**的示例，直接画像期望行为——对 LLM 而言，好的示例胜过千言万语。

总指导思想：**信息充分但紧致**，再配合运行时动态检索（见图 9.2 右侧思路）。

### 9.2.3 上下文检索与智能体式搜索（JIT）

一个简洁定义：

> **智能体 ≈ 在循环中自主调用工具的 LLM。**

工程趋势：从「推理前一次性 embedding 检索、预加载」→ **及时（JIT）上下文**：

| 策略 | 做法 | 优点 | 风险 |
|-----|------|------|------|
| 预加载 | 一次性塞入大量相关文本 | 首轮快 | 易过时、易撑爆窗口、噪声大 |
| JIT | 维护路径/URL/查询等引用，运行时 `head`/`grep`/`glob` 加载 | 实时、省窗、渐进理解 | 更慢；缺引导易走死胡同 |
| 混合（常用） | 前置少量高价值材料（如 README）+ 工具继续探索 | 速度与灵活兼顾 | 要设计好边界与工具启发式 |

**渐进式披露（progressive disclosure）**：每一步交互产生新上下文，反过来指导下一步——文件大小暗示复杂度、命名暗示用途、时间戳暗示相关性。智能体按层构建理解，工作记忆只保留**当前必要子集**，并用「记笔记」做补充持久化。

引用本身的**元数据**也有信号：例如 `tests/test_utils.py` 与 `src/core/test_utils.py` 语义暗示不同。

### 9.2.4 面向长时程任务的三大策略

长时程任务（大型迁移、跨小时研究等）要求在超出窗口的行动序列中仍保持连贯。无限加大窗口不能根治污染与相关性退化。三大手段：

| 策略 | 定义（白话） | 适合 |
|-----|-------------|------|
| **压缩整合（Compaction）** | 接近上限时高保真总结，用摘要 + 少量近期工件**重启新窗口** | 要对话连续性、上下文「接力」 |
| **结构化笔记（Structured note-taking）** | 把关键状态写到**窗外**持久存储，之后按需拉回 | 有里程碑的迭代开发/研究 |
| **子代理架构（Sub-agent）** | 主代理规划综合；子代理在干净窗口深挖，只回 **1k–2k tokens** 摘要 | 复杂研究、可并行探索 |

压缩调参经验：先保证**召回**（别漏关键决策/缺陷），再提高**精确度**（剔冗余）；一种「轻触式」做法是清理深历史中的工具调用与结果噪声。

映射到 Write / Select / Isolate：

- **Write**：笔记、文件、记忆——写到窗外；
- **Select**：GSSC 的 Select——高信号进窗；
- **Isolate**：子代理——脏上下文隔离，只回摘要。

## 9.3 在 Hello-Agents 中的实践：ContextBuilder

ContextBuilder 的设计理念是「简单高效」：统一以**相关性 + 新近性**分数做选择，避免过早引入复杂的来源优先级体系。

### 9.3.1 设计动机与目标

| 目标 | 含义 |
|-----|------|
| **统一入口** | Gather-Select-Structure-Compress 可复用，减少每个 Agent 里重复的模板代码 |
| **稳定形态** | 固定分区骨架，便于调试、A/B、评估 |
| **预算守护** | 在 token 预算内尽量保留高价值信息；超限有兜底压缩 |
| **最小规则** | 不引入繁杂来源/优先级分类，降低复杂度 |

设计骨架中常提到的分区（便于心智建模）：

- `[Role & Policies]`：角色与行为准则  
- `[Task]`：当前任务  
- `[State]`：状态（设计意图；实现里常并入 Context/自定义包）  
- `[Evidence]`：RAG/外部证据  
- `[Context]`：历史与记忆等  
- `[Output]`：输出要求  

> **实现提示**：教程/框架示例中 `_structure` 常见落地为 Role → Task → Evidence → Context → Output；`[State]` 可作为扩展分区，不必死记「代码里一定有这个标题」。

### 9.3.2 核心数据结构

#### ContextPacket：候选信息包

每个候选信息统一成一个包：

```python
@dataclass
class ContextPacket:
    content: str
    timestamp: datetime
    token_count: int
    relevance_score: float = 0.5   # 会 clamp 到 [0, 1]
    metadata: Optional[Dict[str, Any]] = None
    # 例：{"type": "system_instruction"} / "rag_result" / "note" ...
```

**新手理解**：Packet = 「可能进议程的一张材料卡片」，上面标了字数、新旧、相关分、类型。

#### ContextConfig：预算与权重

```python
@dataclass
class ContextConfig:
    max_tokens: int = 3000
    reserve_ratio: float = 0.2      # 为系统指令等预留比例
    min_relevance: float = 0.1
    enable_compression: bool = True
    recency_weight: float = 0.3
    relevance_weight: float = 0.7   # 与 recency_weight 之和必须为 1.0
```

要点：

- `reserve_ratio`：保证关键系统指令不被挤光；
- `__post_init__` 会断言权重之和为 1.0——调参时改一个就要改另一个。

### 9.3.3 GSSC 流水线详解

把四步记成餐厅比喻：**Gather=采购候选菜 · Select=按预算点菜 · Structure=摆盘分区 · Compress=桌满了就精简摆盘但不打乱菜单结构。**

#### （1）Gather：多源汇集

典型来源：

1. **系统指令**（最高优先级，relevance=1.0，标记 `system_instruction`）  
2. **MemoryTool.search**（如 limit=10, min_importance=0.3）  
3. **RAGTool.search**（如 limit=5, min_score=0.3）  
4. **对话历史**（常只留最近 N 条，如 5 条，基础 relevance≈0.6）  
5. **custom_packets**（笔记、终端预处理结果等）

伪代码节奏（帮助你读源码时不迷路）：

```python
packets = []
if system_instructions:
    packets.append(ContextPacket(..., relevance_score=1.0,
                   metadata={"type": "system_instruction"}))
if memory_tool:
    try:
        packets.extend(parse(memory_tool.run({"action": "search", ...})))
    except Exception as e:
        print("[WARNING] 记忆检索失败:", e)  # 不中断
# RAG、最近 5 条历史、custom_packets 同理…
```

关键设计：

- **容错**：每个外部源 `try/except`，单源失败告警后继续，不中断整条流水线；
- **历史限长**：避免窗口被旧聊天占满；
- **系统指令不参与「谁该被丢掉」的竞争**——后面 Select 会单独预留。

#### （2）Select：评分 + 贪心装填

步骤概览：

1. 分离系统指令包与其他包；  
2. 先扣掉系统指令占用的 token，得到剩余预算（若系统指令已占满 → 警告并只返回系统包）；  
3. 对其他包算综合分：

\[
\text{combined} = w_{\text{rel}}\cdot \text{relevance} + w_{\text{rec}}\cdot \text{recency}
\]

4. 过滤 `relevance < min_relevance` 的包；  
5. 按分数降序，**贪心**装入直到预算用尽（装不下就 `break`，不拆包硬塞——教学实现如此）。

相关性教学实现常用 **Jaccard（词集合交并比）**：

\[
\text{Jaccard}(C,Q)=\frac{|W_C \cap W_Q|}{|W_C \cup W_Q|}
\]

生产可换成向量余弦相似度。新近性常用**指数衰减**（约 24 小时内高分，之后衰减），并夹在如 `[0.1, 1.0]`：

```text
age_hours = now - timestamp
recency ≈ exp(-decay * age_hours / 24)   # decay 如 0.1
```

**务必记住**：系统指令**先占坑**，再谈其他材料的「竞选」。

#### （3）Structure：结构化装配

按 `metadata.type` 分组：`system_instruction` → Role；`rag_result`/`knowledge` → Evidence；其余 → Context。再拼成稳定模板：

```text
[Role & Policies]
你是一位资深的Python数据工程顾问。…

[Task]
如何优化Pandas的内存占用?

[Evidence]
Pandas内存优化的核心策略包括: …
---
数据类型优化可以显著减少内存占用。…

[Context]
user: 我正在开发一个数据分析工具
…
记忆: 用户正在开发数据分析工具,使用Python和Pandas

[Output]
请基于以上信息,提供准确、有据的回答。
```

优势：可读、可调试（出问题先看哪个区）、可扩展（新来源新分区）。调试 Agent「答非所问」时，先把这份结构化上下文打印出来，比猜模型脾气有效得多。

#### （4）Compress：兜底压缩

若结构化后仍超 `max_tokens`：

1. 按 `\n\n` 切开各 section；  
2. 能完整放下的分区先保留；  
3. 放不下的分区：若剩余预算 > 50 tokens，则截断并追加 `[... 内容已压缩 ...]`，然后停止；  
4. **尽量保持骨架完整**，而不是从中间乱砍导致 Role/Task 消失。

教学实现偏截断；生产可用 LLM 摘要。混合策略常见做法：深历史工具输出截断，架构决策/未决缺陷用摘要。

Token 计数教学上常做启发式估算（中文约 1 字≈1 token，英文词≈1.3）；生产应用真实 tokenizer。

### 9.3.4 完整使用与 Agent 集成

#### 基础调用

```python
from hello_agents.context import ContextBuilder, ContextConfig
from hello_agents.tools import MemoryTool, RAGTool

builder = ContextBuilder(
    memory_tool=MemoryTool(user_id="user123"),
    rag_tool=RAGTool(knowledge_base_path="./knowledge_base"),
    config=ContextConfig(max_tokens=3000, reserve_ratio=0.2, min_relevance=0.2),
)

context = builder.build(
    user_query="如何优化Pandas的内存占用?",
    conversation_history=history,  # List[Message]
    system_instructions="你是资深Python数据工程顾问...",
)
# 得到 Role/Task/Evidence/Context/Output 骨架字符串
```

#### ContextAwareAgent 思路

1. `run()` 内用 builder 生成 `optimized_context`；  
2. 作为 system（或等价位置）调用 LLM；  
3. 追加对话历史；  
4. 把交互摘要 `add` 进 MemoryTool。  

ContextBuilder 成为 Agent 的「上下文管理大脑」。

### 9.3.5 最佳实践

1. **动态预算**：简单任务缩小 `max_tokens`，复杂任务加大；  
2. **相关性升级**：生产用向量相似度替代 Jaccard；  
3. **缓存**：不变的系统指令/静态知识可缓存；  
4. **监控日志**：记录选中包数、token 使用率；  
5. **A/B**：调 `relevance_weight` / `recency_weight`。

**动手建议**：打开互动教程「窗口预算实验室」，拖动 `max_tokens`、`reserve_ratio`、Evidence/Context 占用，观察何时触发 Compress 提示——比只看公式更直观。

## 9.4 NoteTool：结构化笔记

NoteTool 是为**长时程任务**准备的结构化外部记忆：Markdown 正文 + YAML 前置元数据，人类可读、Git 友好、易回注 ContextBuilder。

### 9.4.1 为什么还要 NoteTool？（vs MemoryTool）

| | MemoryTool（第八章） | NoteTool（本章） |
|--|---------------------|-----------------|
| 定位 | 对话式记忆（工作/情景/语义等） | 项目式任务追踪与状态外存 |
| 载体 | 向量库、图谱等 | `.md` + `notes_index.json` |
| 典型内容 | 「聊过什么、知道什么」 | task_state / blocker / action… |
| 协作 | 可被 Gather 检索 | 常经 `custom_packets` 注入 Builder |

NoteTool 特点：结构化、版本友好、低开销、用 `type`/`tags` 多维组织。

**典型场景**：

1. **长期重构**：阶段进度、结论、阻塞、下一步；  
2. **文献综述**：论文结论、待调研、参考文献；  
3. **每轮对话前** `search`/`list` 相关笔记 → 转 `ContextPacket` → `build(..., custom_packets=...)`。

### 9.4.2 存储格式

单个笔记示例：

```markdown
---
id: note_20250119_153000_0
title: 项目进展 - 第一阶段
type: task_state
tags: [refactoring, phase1, backend]
created_at: 2025-01-19T15:30:00
updated_at: 2025-01-19T15:30:00
---

# 正文 Markdown …
```

另有 **`notes_index.json`**：集中元数据，加速检索、完整性校验；**文件名即 ID**。

### 9.4.3 七大操作（生命周期）

| 操作 | 作用（记住「干什么」即可） |
|-----|--------------------------|
| `create` | 生成 `note_id`，写 YAML+正文，更新索引 |
| `read` | 按 id 读出元数据 + 正文 |
| `update` | 改标题/正文/类型/标签，刷新 `updated_at` |
| `search` | 关键词搜标题/正文，可按 type/tags 过滤 |
| `list` | 按更新时间列出，可过滤 |
| `summary` | 总数、类型分布、最近笔记 |
| `delete` | 删文件 + 索引条目 |

笔记类型建议：

| type | 用途 | 注入 Builder 时相关性（经验） |
|------|------|------------------------------|
| `blocker` | 阻塞问题 | 最高（如 0.9） |
| `action` | 下一步行动 | 高 |
| `task_state` | 阶段状态 | 较高 |
| `conclusion` | 结论发现 | 中高 |
| `reference` | 参考资料 | 按需 |
| `general` | 其他 | 默认 |

**最小可跑示例**（体会 create → search → summary）：

```python
from hello_agents.tools import NoteTool

notes = NoteTool(workspace="./project_notes")

note_id = notes.run({
    "action": "create",
    "title": "重构项目 - 第一阶段",
    "content": "## 完成情况\n已完成数据模型层重构，覆盖率 85%。\n\n## 下一步\n重构业务逻辑层",
    "note_type": "task_state",
    "tags": ["refactoring", "phase1"],
})

notes.run({
    "action": "create",
    "title": "依赖冲突问题",
    "content": "第三方库版本不兼容，影响业务逻辑层 3 个模块。",
    "note_type": "blocker",
    "tags": ["dependency", "urgent"],
})

hits = notes.run({"action": "search", "query": "依赖", "limit": 3})
print(hits)
print(notes.run({"action": "summary"}))
```

`create` 内部节奏：时间戳生成 id → 写 YAML 头 → 落盘 `.md` → 更新 `notes_index.json`。  
`search` 可按 `note_type`/`tags` 预过滤，再在标题/正文里做关键词匹配，按 `updated_at` 倒序截断。

### 9.4.4 与 ContextBuilder 集成

```python
relevant = note_tool.run({"action": "search", "query": user_input, "limit": 3})
note_packets = [
    ContextPacket(
        content=note["content"],
        timestamp=...,  # 用 updated_at
        token_count=...,
        relevance_score=0.7,  # 或按 note_type 区分
        metadata={"type": "note", "note_type": note["type"]},
    )
    for note in relevant
]
context = builder.build(user_query=user_input, custom_packets=note_packets, ...)
```

案例里常见增强：优先 `list` blocker，再与 search 结果合并去重。

### 9.4.5 最佳实践

1. 合理分类；解决后的 blocker **升格**为 conclusion；  
2. 过时 action 清理；用 tags 做版本/完成标记；  
3. 限制注入条数，防止笔记反客为主撑爆窗口；  
4. 人可直接改 Markdown；Git 追踪；关键节点人工审核；  
5. 可定期 summary、生成进度文档、同步到 Notion 等（扩展）。

## 9.5 TerminalTool：即时文件系统访问

落地 9.2.2 的 JIT：代码库探索、日志分析、数据预览——需要**实时轻量**访问，而不是先向量化整个仓库。

### 9.5.1 为何需要 / 与 RAG 的分工

```python
# 预索引：成本高、易过时
# rag_tool.add_document("./project/**/*.py")

# JIT：
terminal.run({"command": "find . -name '*.py' -type f"})
terminal.run({"command": "grep -r 'class UserService' ."})
terminal.run({"command": "head -n 50 src/services/user.py"})
```

适合：结构探查、日志 `tail|grep`、CSV `head/wc/cut` 等。不适合：把 Terminal 当「万能写库工具」——默认偏向**安全只读探索**。

### 9.5.2 四层安全机制（必背）

| 层 | 机制 | 作用 |
|----|------|------|
| 1 | **命令白名单** | 只允许 ls/cat/grep/find/head… 等；拒绝 `rm` 等破坏性命令 |
| 2 | **工作目录沙箱** | 只能访问 `workspace` 内；`cd ..` 逃逸会被拒 |
| 3 | **超时** | 防止卡死/资源耗尽（如 timeout=30） |
| 4 | **输出大小上限** | 防止巨型输出撑爆内存/上下文 |

白名单常见类别（记类别即可）：

- 列表/信息：`ls`、`dir`、`tree`、`pwd`、`file`、`stat`、`du`、`df`  
- 查看：`cat`、`head`、`tail`、`less`、`more`  
- 搜索：`find`、`grep`、`egrep`、`fgrep`  
- 文本处理：`wc`、`sort`、`uniq`、`cut`、`awk`、`sed`  
- 导航：`cd`（可关）  
- 其他：`echo`、`which`、`whereis`  

```python
terminal = TerminalTool(workspace="./project", timeout=30, max_output_size=10*1024*1024)
terminal.run({"command": "rm -rf /"})
# ❌ 不允许的命令: rm

terminal.run({"command": "cat /etc/passwd"})   # ❌ 工作区外
terminal.run({"command": "cd ../../../etc"})   # ❌ 沙箱逃逸
```

### 9.5.3 核心功能要点

- `_execute_command`：在 `current_dir` 下 `subprocess.run(..., shell=True, capture_output=True)`，合并 stderr，检查返回码与输出大小；超时 → 可读错误字符串，避免拖垮 Agent。  
- `cd`：解析目标路径，resolve 后必须仍落在 workspace 根之下；无参数时返回当前目录。  
- 非零返回码不会抛崩，而是前缀警告，方便模型继续推理。  

### 9.5.4 典型模式与协同

| 模式 | 例子 |
|-----|------|
| 探索导航 | `ls` → `cd` → `tree` → `grep` |
| 数据预览 | `head -n 5 data/sales.csv`、`wc -l`、`cut` |
| 日志分析 | `tail -n 100 app.log \| grep ERROR` 再 `uniq -c` |
| 代码定位 | `find` + `grep -rn 'TODO\|FIXME'` + `head` 读片段 |

与其他工具协同（本章套路）：

```text
Terminal 探查 → 发现慢查询/缺陷
    → NoteTool 记 blocker（窗外持久）
    → 下轮 ContextBuilder 优先注入
    → （可选）结构结论写入 MemoryTool 语义记忆
```

这就是「JIT 探查 + 结构化外存 + 回注窗口」的标准闭环。

## 9.6 长程智能体实战：代码库维护助手

把 Builder + Note + Terminal（+ Memory）整合成 **CodebaseMaintainer**。

### 9.6.1 场景与三大挑战

中型 Flask 应用（约 50 个 py 文件）有技术债务。助手要：探索结构、识别问题、追踪进度、给连贯重构建议。

| 挑战 | 手段 |
|-----|------|
| 代码量超窗口 | Terminal 按需查看 |
| 跨天会话丢进度 | NoteTool 记状态/阻塞/计划 |
| 信息噪声 | ContextBuilder 筛选装配 |

### 9.6.2 三层架构（图 9.3）

<div align="center">
  <img src="https://raw.githubusercontent.com/datawhalechina/Hello-Agents/main/docs/images/9-figures/9-3.png" alt="图9.3 代码库维护助手三层架构" width="85%"/>
  <p>图 9.3 代码库维护助手三层架构</p>
</div>

| 层 | 职责 |
|----|------|
| **交互层** | `run(mode=explore/analyze/plan/auto)` 模式化入口 |
| **上下文层** | ContextBuilder + Packets 装配 |
| **工具层** | Terminal + Note + Memory |

### 9.6.3 主循环五步（建议背流程）

`CodebaseMaintainer.run(user_input, mode)` 内部可以记成：

```text
预处理(mode) → 检索笔记 → GSSC.build → LLM → 后处理/记笔记 → 更新历史
```

1. **预处理**：按 mode 用 Terminal/Note 收集 `pre_context` packets；  
2. **笔记**：检索相关笔记（优先 `list(blocker)`，再 `search` 合并去重）→ packets；  
3. **GSSC**：`context_builder.build(system_instructions=按 mode 定制, custom_packets=笔记+预处理)`；  
4. **LLM**：基于优化上下文生成回答；  
5. **后处理**：从回答中识别问题/计划 → 自动 `create` blocker/action；摘要进 Memory；更新 `conversation_history` 与 stats。  

模式差异（直觉）：

| mode | 预处理多做什么 |
|------|----------------|
| `explore` / `auto` | `find … '*.py' \| head` 等结构扫描 → `code_structure` 包 |
| `analyze` | `wc -l`、搜 TODO/FIXME → `code_analysis` 包 |
| `plan` | `list(task_state)` → `task_plan` 包 |

笔记转 Packet 时按类型设 relevance：**blocker(0.9) > action(0.8) > task_state(0.75) > conclusion(0.7)**。  
初始化时常见配置：`max_tokens=4000`、`reserve_ratio=0.15`、本案例可不挂 RAG（靠 Terminal JIT）。

### 9.6.4 使用节奏（跨天故事）

```python
maintainer = CodebaseMaintainer("my_flask_app", "./my_flask_app", llm)

# Day1 探索
maintainer.run("帮我看看项目结构", mode="explore")
maintainer.run("请分析 app/models/ 的数据模型设计")

# Day2 分析
maintainer.run("有哪些 TODO/复杂度问题？", mode="analyze")
maintainer.run("查看 order_service.process_order，给重构建议")

# Day3 规划
maintainer.run("下周重构计划？", mode="plan")
# 可手动 create_note 写详细周计划（人机协作）
```

### 9.6.5 运行效果：你应看到的能力

1. **跨会话连贯**：Day1 的 blocker 在 Day3 规划仍在；  
2. **智能上下文**：优先 blocker，按模式动态预处理；  
3. **即时文件访问**：无需预索引整库；  
4. **自动知识管理**：问题→blocker，计划→action；  
5. **人机协作**：人可直接改 Markdown 干预。  

可扩展：加 RAG、拆多代理、接测试/git、Gradio 界面等。

## 习题导读（5 大题要点）

> 原书习题偏开放与动手；下列是**导读要点**，不是标准答案全文。建议先自己答，再对照。

### 习题 1：腐蚀、JIT、系统提示平衡

**子题 A — context rot**

- 定义：tokens↑ → 准确利用上下文的能力可能↓。  
- 即便 100K/200K：注意力被摊薄、训练偏短序列、位置精度可能受损 → 仍需筛选与压缩。  

**子题 B — 整库塞窗 vs JIT（代码审查助手，50 文件）**

| | 整库塞窗 | JIT |
|--|---------|-----|
| 优点 | 首轮信息全、少工具轮次 | 省窗、实时、可渐进 |
| 缺点 | 噪声、贵、易腐蚀、易过时 | 慢、需好工具与引导 |
| 适用 | 极小库、强实时问答 | 中大型库、探索式审查 |

实践常 **混合**：README/约定预置 + grep/head 深挖。

**子题 C — 系统提示两极**

- 过硬编码例：把每个框架版本的 if-else 全写进 system；  
- 过空泛例：只写「你是有帮助的助手」无输出契约；  
- 平衡：最小必要分区 + 失败驱动增补 + 少量典型 few-shot。  

### 习题 2：GSSC 失效影响与压缩策略

**子题 A — 某阶段失效**

| 阶段失效 | 可能后果 |
|---------|---------|
| Gather 漏源/全挂 | 缺证据、缺记忆，回答空或幻觉↑ |
| Select 选错 | 高噪声进窗，关键包落选 |
| Structure 乱 | 模型难定位角色/证据，调试困难 |
| Compress 过猛 | 丢决策/缺陷细节，长程断裂 |

**子题 B — 质量评估（动手方向）**

在 `build` 后统计：包数量、平均 relevance、Evidence 是否为空、token 使用率、是否触发压缩；输出「建议加大/减小预算、提高 min_relevance」等。  

**子题 C — 截断 vs LLM 摘要**

- 截断/滑窗：便宜、确定、适合工具原始输出噪声；  
- LLM 摘要：适合保留架构决策与未决缺陷；  
- 混合：深历史工具结果截断，决策区摘要，骨架分区不打乱。  
（注：教材 Compress 示例偏截断；习题要求你思考何时上摘要。）

### 习题 3：Note / Terminal 扩展

**子题 A — 笔记自动整理**

临时笔记达阈值 → 聚类/LLM 归并 → 升格 task/conclusion → 删冗余；可用 `summary` + 定时任务。  

**子题 B — 人机审批**

白名单不够时：敏感路径/危险意图 → 生成「待审批操作」笔记或 UI 确认 → 人类批准后再执行（或换只读替代）。  

**子题 C — 重构助手流程（画图要点）**

探索(Terminal) → 记 blocker/action(Note) → Builder 装配 → 建议重构 → 人审 → 小步修改 → 测/记 conclusion → 循环。  

### 习题 4：三层信息、断点续传、任务依赖

**子题 A — 三层分工**

| 层 | 放什么 |
|----|--------|
| Terminal | 当前需要看的文件/命令结果（易变、勿长期堆窗） |
| Memory | 用户偏好、跨会话语义/情景摘要 |
| Note | 里程碑、阻塞、计划、可 Git 审的状态 |

避免：同一结论三处全文复制——窗内用摘要/引用，权威状态以笔记为准。  

**子题 B — 断点续传**

笔记记录：当前阶段、已完成勾选、打开的文件路径、未决 blocker、下一步 action；恢复时 `list/search` + 校验工作区路径仍存在。  

**子题 C — 任务依赖**

在 note 元数据或正文维护 `depends_on: [note_id…]`；调度时只拉「依赖已 conclusion」的 action；与 NoteTool 的 type/tags 集成。  

### 习题 5：渐进式披露

**子题 A — 场景设计**

例：论文写作——先扫目录与摘要 → 深读相关节 → 记结论笔记 → 再决定下一章；调试同理：复现 → 定位模块 → 读关键函数 → 记假设。  

**子题 B — 探索引导**

启发式：优先 README/入口文件；限制连续 `cat` 大文件次数；强制「先 grep 再 head」；对低信息增益路径降权。  

**子题 C — 何时预加载 vs 渐进**

| 更适合渐进披露 | 更适合一次性加载 |
|--------------|----------------|
| 大库探索、未知结构调研 | 短文档 QA、固定表单填空 |
| 长程重构 | 单轮分类/抽取 |
| 日志定位根因 | 已精选的小证据包问答 |
