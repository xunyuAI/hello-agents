9.1 · Context Engineering

什么是上下文工程

上下文 = 对 LLM 采样时包含的那组 tokens。工程问题是：在模型固有约束下，优化这些 tokens 的效用。

核心问题从「提示怎么写」升级为：什么样的上下文配置，最有可能让模型产出期望行为？

图 9.1（离线要点）
提示工程 ⊂ 上下文工程：后者覆盖系统指令、工具、MCP、外部数据、消息历史等进入窗口的一切。

9.1 · 对比卡

演进关系

提示工程

  • 焦点：指令措辞与结构化
  • 典型：系统提示精调
  • 适合：单轮分类 / 生成

从不断扩张的「候选信息宇宙」中，甄别哪些进入有限窗口——这就是上下文工程的核心技艺。

9.2 · Context Rot

上下文是稀缺资源

上下文腐蚀（context rot）：窗口里 tokens 越多，模型从中准确回忆信息的能力反而可能下降。

  • 像人类工作记忆：有容量与「注意力预算」
  • Transformer 两两注意力 ~ n²，关系被「拉薄」
  • 训练分布偏短序列；位置插值可换长度但牺牲位置精度
  • 表现是性能梯度，不是瞬间悬崖崩溃
桌面堆满发票时，反而找不到那张关键收据——不是桌子变小了，是注意力被稀释了。

9.2.1 · 高信号密度

有效上下文的「解剖学」

目标：用尽可能少、但高信号密度的 tokens，最大化期望结果概率。

系统提示 System Prompt

避免两极：过度硬编码 if-else；或过于空泛缺具体信号。分区组织（background / instructions / 工具指引 / 输出描述），追求「最小必要信息集」——最小 ≠ 最短。

工具 Tools · MVTS

职责单一、低重叠、错误鲁棒、入参清晰。臃肿工具集让「选哪个」本身含混——人类说不准，别指望智能体更好。精选最小可行工具集（MVTS）。

9.2.2 · Just-in-time Context

即时上下文与渐进式披露

智能体 ≈ 在循环中自主调用工具的 LLM。 工程趋势：从「推理前一次性 embedding 检索」→「维护轻量引用，运行时按需加载」。

预加载

  • 快，但易过时、易撑爆窗口
  • 适合少量高价值静态材料（README）

JIT

  • 路径/URL/查询作引用；head/tail/grep 探查
  • 元数据（目录名、时间戳）也携带语义
每一步交互产生新上下文，指导下一步——只在工作记忆保留当前必要子集；用笔记做补充持久化。

实践常用混合策略：前置少量高价值上下文 + 提供 glob/grep 继续探索。

9.2.3 · Compaction / Notes / Sub-agent

面向长时程任务

无限加大窗口不能根治污染与相关性退化。点击步进查看三大策略：

选压缩

要对话连续性、上下文接力

选笔记

有里程碑的迭代开发/研究

选子代理

复杂研究、可并行探索

9.2.3 · Write / Select / Isolate

三动作心智模型

把长程策略收成三个可操作动词——与 Anthropic 等语境中的 Write / Select / Isolate 对齐。

Write 写入

把状态写到窗外：NoteTool、文件、Memory。窗口只留引用或摘要。

Select 选择

从候选宇宙挑高信号进窗：GSSC 的 Select（相关+新近）+ 预算守护。

Isolate 隔离

脏活放到子代理干净窗口，主代理只收 1k–2k tokens 摘要。

对照：压缩整合偏「接力式 Select+摘要」；结构化笔记偏 Write；子代理偏 Isolate。三者可组合。

9.3.1 · 设计目标

为何需要 ContextBuilder

统一入口Gather → Select → Structure → Compress，减少每个 Agent 重复模板代码
稳定形态固定分区骨架，便于调试、A/B、评估
预算守护token 内保高价值；超限兜底压缩
最小规则以相关性+新近性评分，不引入复杂来源优先级体系
[Role & Policies] 角色与行为准则
[Task] 当前任务
[State] 状态信息（设计骨架中提及）
[Evidence] RAG/外部证据
[Context] 历史与记忆
[Output] 输出要求

9.3.2 · Packet & Config

ContextPacket 与 ContextConfig

ContextPacket · 候选信息包
@dataclass class ContextPacket: content: str timestamp: datetime token_count: int relevance_score: float = 0.5 # clamp 到 [0,1] metadata: Optional[Dict] = None

信息的基本单元：内容、时间、token、相关性、元数据（如 type=system_instruction）。

ContextConfig · 预算与权重
max_tokens=3000 reserve_ratio=0.2 # 为系统指令预留 min_relevance=0.1 enable_compression=True recency_weight=0.3 relevance_weight=0.7 # 二者之和须为 1.0

reserve_ratio 保证关键系统指令不被挤占。

9.3.3 · 点击步进

GSSC 流水线可视化

Select 公式：综合分 = relevance_weight × 相关性 + recency_weight × 新近性；新近性用指数衰减（约 24h 内高分）。相关性可用 Jaccard，生产可换向量相似度。
Gather=采购候选菜 · Select=按预算点菜 · Structure=摆盘分区 · Compress=桌满了就精简摆盘但不打乱菜单结构。

互动 · Token Budget

窗口预算步进可视化

拖动滑块，观察系统预留、证据、上下文如何争夺有限窗口；超限时触发 Compress 提示。

9.3.4 · 关键片段

构建上下文并接入 Agent

builder = ContextBuilder(memory_tool=..., rag_tool=..., config=ContextConfig(max_tokens=3000)) context = builder.build( user_query="如何优化Pandas的内存占用?", conversation_history=history, system_instructions="你是资深Python数据工程顾问..." )

输出骨架示例：Role → Task → Evidence（RAG）→ Context（历史+记忆）→ Output。

ContextAwareAgent 思路

run()：用 builder 生成 optimized_context → 作为 system 调 LLM → 追加历史 → 摘要写入 MemoryTool。ContextBuilder 成为 Agent 的「上下文管理大脑」。

9.3.5

ContextBuilder 优化建议

  1. 动态预算：简单任务缩小 max_tokens，复杂任务加大
  2. 相关性升级：生产用向量相似度替代关键词 Jaccard
  3. 缓存：不变的系统指令/知识可缓存
  4. 监控日志：记录选中包数、token 使用率
  5. A/B：调 relevance/recency 权重找最优

9.4.1 · vs MemoryTool

为何还要结构化笔记？

MemoryTool（第八章）

  • 对话式记忆：工作/情景/语义
  • 向量与图谱等后端
  • 偏「聊过什么、知道什么」

NoteTool（本章）

  • 项目式任务追踪
  • Markdown + YAML，Git 友好
  • 低开销状态：task_state / blocker / action…

场景：长期重构、文献综述、每轮对话前 search/list 笔记注入 ContextBuilder。

9.4.2 · YAML + Markdown

笔记文件与索引

--- id: note_20250119_153000_0 title: 项目进展 - 第一阶段 type: task_state tags: [refactoring, phase1] created_at: ... updated_at: ... --- # 正文 Markdown …

另有 notes_index.json 集中元数据，加速检索与完整性校验。文件名即 ID。

NoteTool 核心操作

类型建议：task_state · conclusion · blocker · action · reference · general；与 ContextBuilder 配合时 blocker 相关性可设更高。

9.5.1 · JIT 文件系统

即时探索，而非预索引一切

代码库探索、日志分析、数据预览——需要实时轻量访问，而不是先向量化整个仓库。

# 预索引：成本高、易过时 # JIT： terminal.run({"command": "find . -name '*.py' -type f"}) terminal.run({"command": "grep -r 'class UserService' ."}) terminal.run({"command": "head -n 50 src/services/user.py"})

落地 9.2.2 的 JIT 理念。

9.5.1 · 安全第一

强大但危险 → 多层防护

terminal.run({"command": "rm -rf /"}) → ❌ 不允许的命令: rm

9.5.2–9.5.4

导航、分析、与其他工具协作

核心能力

_execute_command：在 current_dir 下 subprocess，合并 stderr，检查返回码与输出大小。cd 特殊处理并校验仍在 workspace 内。

典型模式

探索式导航（ls → cd → tree → grep）；CSV head/wc/cut；日志 tail|grep；代码库 sed/awk 片段提取。

协同

结构写入 MemoryTool 语义记忆；慢查询写入 NoteTool blocker；输出转 ContextPacket 交给 ContextBuilder。
