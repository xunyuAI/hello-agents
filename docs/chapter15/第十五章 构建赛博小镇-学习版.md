# 第十五章 构建赛博小镇

> **学习版说明**：在原书正文基础上，沿 **NPC 智能体 → 好感度 → FastAPI 后端 → Godot 前端** 主线补齐新手讲解、对照表、代码拆解与易混点；架构与接口与原书 / `code/chapter15/Helloagents-AI-Town` 一致。互动翻页教程见 `interactive-tutorial/index.html`。

前面章节里，HelloAgents 多半待在「终端 / API」世界里：Agent 会思考、会调工具、会记记忆。这一章把舞台换成**可走动的 2D 像素办公室**——把智能体焊进 Godot 游戏引擎，做出真正「活着」的 NPC。

你可以把本章理解成一次**全栈综合实战**：

- **大脑**：HelloAgents `SimpleAgent` + 记忆 + 好感度  
- **中枢**：FastAPI 编排状态、对话、日志  
- **身体**：Godot 场景、玩家控制、对话 UI  

目标不是背完每一行 GDScript，而是建立一张清晰的**心智地图**：一次按 `E` 之后，请求怎么走、记忆怎么取、好感怎么变、画面怎么回。

本章赛博小镇包含五块产品能力：

1. **智能 NPC 对话**：自然语言，而不是死对话树  
2. **记忆系统**：短期连贯 + 长期语义回忆  
3. **好感度系统**：态度从陌生到挚友  
4. **游戏化交互**：2D 办公室自由走动  
5. **实时日志**：对话与好感变化可观测

## 15.1 项目概述与架构设计

> **本节目标**：搞清「为什么做 AI 小镇」、四层怎么叠、一次按 `E` 的数据流，并先把 Demo 跑起来。

### 15.1.1 为什么要构建 AI 小镇

传统 RPG 的 NPC 多半是**对话树**：编剧写死分支，可控但难有生命力。AI NPC 的跃迁在于：

1. 任意自然语言，而不是三个按钮选项；  
2. 记得历史与关系；  
3. 每人有职业、性格、说话风格；  
4. 态度随互动变化。

**新手可以这样记：** 对话树像自动贩卖机；AI NPC 像真同事——你随便说，他按人设与记忆接话。

应用面：教育角色扮演、虚拟办公室导师、陪伴场景、传统游戏增强。教学项目里，Datawhale 办公室是一个足够小、又足够完整的沙盘。

## 15.2 NPC 智能体系统

> **本节目标**：搞清「一个 NPC = 一个 SimpleAgent」、三角色 Prompt 差异、记忆五步、批量 vs 即时混合模式。

### 15.2.1 基于 HelloAgents 的 SimpleAgent

每个 NPC = 一个独立的 `SimpleAgent`（第七章那套对话循环）。创建时做四件事：

1. 用姓名 / 职业 / 性格拼 `system_prompt`  
2. `HelloAgentsLLM()`  
3. `MemoryManager(WorkingMemory, EpisodicMemory)`  
4. 返回 Agent  

教学示例（与原书一致，便于对照）：

```python
from hello_agents import SimpleAgent, HelloAgentsLLM
from hello_agents.memory import MemoryManager, WorkingMemory, EpisodicMemory

def create_npc_agent(npc_id: str, name: str, role: str, personality: str):
    """创建 NPC Agent"""
    system_prompt = f"""你是{name},一位{role}。
你的性格特点:{personality}

你在Datawhale办公室工作,与同事们一起推动开源社区的发展。
请根据你的角色和性格,自然地与玩家对话。
记住你们之前的对话内容,保持对话的连贯性。
"""

    llm = HelloAgentsLLM()

    memory_manager = MemoryManager(
        working_memory=WorkingMemory(capacity=10, ttl_minutes=120),
        episodic_memory=EpisodicMemory(
            db_path=f"memory_data/{npc_id}_episodic.db",
            collection_name=f"{npc_id}_memories"
        )
    )

    agent = SimpleAgent(
        name=name,
        llm=llm,
        system_prompt=system_prompt,
        memory_manager=memory_manager
    )
    return agent
```

**参数直觉（新手必记）：**

| 组件 | 示例参数 | 管什么 |
|------|----------|--------|
| WorkingMemory | `capacity=10`, `ttl_minutes=120` | 「刚才几句」、指代消解 |
| EpisodicMemory | 按 `npc_id` 分库 / collection | 「很久以前相关话题」语义检索 |

工作流程见图 15.5：收消息 → 检索记忆 → LLM → 回写记忆。

### 15.2.3 记忆系统集成

记忆是 NPC「像真人」的关键。架构见图 15.6。

<div align="center">
  <img src="https://raw.githubusercontent.com/datawhalechina/Hello-Agents/main/docs/images/15-figures/15-6.png" alt="" width="85%"/>
  <p>图 15.6 记忆系统架构</p>
</div>

- **短期（Working）**：容量有限、会过期。解决「它是什么颜色？」这类指代。  
- **长期（Episodic）**：向量语义检索。解决「还记得上次那个项目吗？」  

对话处理推荐心智顺序（与第八章一致，本章装进游戏循环）：

```
近期 Working → 语义检索 Episodic → 拼 context → agent.run → add_interaction
```

伪代码拆解：

```python
def process_dialogue(agent, player_message):
    # 1. 短期：最近几轮，保连贯
    recent = agent.memory_manager.working_memory.get_recent_messages(5)

    # 2. 长期：按当前问题语义搜往事
    relevant = agent.memory_manager.episodic_memory.search(
        query=player_message, top_k=3
    )

    # 3. 拼上下文
    context = {"recent": recent, "relevant": relevant}

    # 4. 生成
    reply = agent.run(player_message, context=context)

    # 5. 落盘，供下次检索
    agent.memory_manager.add_interaction(player_message, reply)
    return reply
```

**口诀：** 先近后远，先连贯后回忆，最后一定要写回。

### 15.2.4 批量对话生成：轻负载模式

**问题：** 多 NPC / 多玩家时，每人每次都打 LLM，贵且易撞限流。  

**解法：** `NPCBatchGenerator` 一次调用生成所有 NPC 的一句话，强制 JSON（见图 15.7）：

```json
{"张三":"...","李四":"...","王五":"..."}
```

<div align="center">
  <img src="https://raw.githubusercontent.com/datawhalechina/Hello-Agents/main/docs/images/15-figures/15-7.png" alt="" width="85%"/>
  <p>图 15.7 批量生成 vs 传统模式</p>
</div>

提示词要点（新手调试时最容易翻车的地方）：

1. 写明场景上下文（上午工作 / 午餐等）  
2. 列出每人职位、位置、活动、性格  
3. **强制只返回 JSON**，并给示例输出  
4. 每句 20–40 字，像真实办公室自言自语  

额外好处：三人在同一上下文里生成，台词会彼此「有关联」（张三在调 Bug，李四可能说要帮看看）。

适合：进入场景时的自言自语、定时氛围更新、降本。  
**不适合：** 替代玩家一对一认真对话。

**混合模式（本章高分设计）：**

| 模式 | 时机 | 目的 |
|------|------|------|
| 批量 | 后台约每 5 分钟 | 背景台词，NPC「看起来在活」 |
| 即时 | `POST /dialogue` | 个性化、带记忆与好感 |

示意代码：

```python
@app.post("/dialogue")
async def dialogue(request: DialogueRequest):
    agent = npc_agents.get(request.npc_id)
    reply = agent.run(request.player_message)  # 即时，不用批量缓存当最终回复
    # ... 更新好感、返回 ...

async def background_dialogue_update():
    while True:
        dialogues = batch_generator.generate_batch_dialogues()
        for name, text in dialogues.items():
            state_manager.update_npc_background_dialogue(name, text)
        await asyncio.sleep(300)  # 约 5 分钟
```

口诀：**远看用批量，近聊用即时。**

## 15.3 好感度系统设计

> **本节目标**：记住五级分数带；理解「LLM 判态度 → Δ分 → clamp」；明白好感如何改 Prompt 语气。

### 15.3.1 好感度等级划分

分数是账本；玩家感受到的是**信息密度与语气**。五级划分见图 15.8。

| 等级 | 分数 | 行为倾向 |
|------|------|----------|
| 陌生 | 0–20 | 礼貌疏远、回复短、少谈私事 |
| 熟悉 | 21–40 | 自然交流、偶提工作 |
| 友好 | 41–60 | 更详细、会主动问你 |
| 亲密 | 61–80 | 私人话题、热情建议 |
| 挚友 | 81–100 | 无话不谈、分享感受 |

后续可把高等级做成任务锁（例如好感 ≥ 60 才分享特殊情报）。

### 15.3.2 好感度计算逻辑

不要「每句话 +1」。本章用 LLM 做情感分析（见图 15.9）：

- 友好 → +5  
- 中立 → +2  
- 不友好 → −3  
- 解析失败 → 默认 +2  
- Δ分再限制在 `[-3, 5]`，总分 clamp 到 `[0, 100]`

<div align="center">
  <img src="https://raw.githubusercontent.com/datawhalechina/Hello-Agents/main/docs/images/15-figures/15-9.png" alt="" width="85%"/>
  <p>图 15.9 好感度计算流程</p>
</div>

教学版核心逻辑：

```python
class RelationshipManager:
    def analyze_sentiment(self, player_message: str, npc_reply: str) -> int:
        prompt = f"""分析以下对话中玩家的态度:
玩家: {player_message}
NPC: {npc_reply}

请判断玩家的态度是:
1. 友好(+5分): 礼貌、热情、表示感谢或赞同
2. 中立(+2分): 普通的询问或陈述
3. 不友好(-3分): 粗鲁、冷漠、批评或否定

只返回数字,不要其他内容。"""
        response = self.llm.think([{"role": "user", "content": prompt}])
        try:
            score_change = int(response.strip())
            return max(-3, min(5, score_change))
        except:
            return 2  # 默认中立，避免坏响应毁掉曲线

```

**新手易混点：**

1. **关系键是 `npc_id + player_name`**：张三对 Alice 与张三对 Bob 是两本账。  
2. **仓库实装更细**：`relationship_manager.py` 里用 JSON（`change_amount` / `sentiment` / `reason`），规则区间更宽；学习时先掌握「友好 / 中立 / 不友好」三档即可。  
3. **好感变化发生在回复生成之后**：先聊天，再根据本轮态度改分。

### 15.3.3 好感度影响对话

把等级映射成一段附加系统提示，例如陌生要求「简短专业」，挚友要求「亲切真诚」：

```python
affinity_prompts = {
    "陌生": "你刚认识这位玩家,保持礼貌但不要过于热情。回复简短专业。",
    "熟悉": "你已经认识这位玩家,可以进行正常的交流。回复自然友好。",
    "友好": "你把这位玩家当作朋友,愿意分享更多信息。回复详细热情。",
    "亲密": "你非常信任这位玩家,可以分享私人话题。回复充满关心。",
    "挚友": "你把这位玩家当作最好的朋友,无话不谈。回复亲切真诚。"
}

system_prompt = f"""你是{name},一位{role}。
你的性格特点:{personality}

当前与玩家的关系:{affinity_level}
{affinity_prompts[affinity_level]}
...
"""
```

**工程含义：** 同一 Agent 骨架，**Prompt 随关系动态变**，比单独训练多个模型便宜得多。

调用顺序口诀：**先查等级 → 再拼 Prompt / 取 Agent → 再生成 → 最后更新分数。**

```python
app = FastAPI(title="赛博小镇后端服务", version="1.0.0")
```

### 15.4.2 API 路由设计

**`/dialogue` 九步（建议能默写）：**

1. 校验 NPC 存在 → 否则 **404**  
2. busy → **409**（冲突：正在跟别人聊）  
3. 标记 busy  
4. 取当前好感等级  
5. 按等级取 / 配置 Agent，生成回复  
6. 更新好感  
7. 写日志  
8. 返回 `DialogueResponse`（回复 + 等级 + 分数）  
9. `finally` 释放 busy  

对应代码骨架：

```python
@app.post("/dialogue", response_model=DialogueResponse)
async def dialogue(request: DialogueRequest):
    if not agent_manager.has_npc(request.npc_id):
        raise HTTPException(404, detail="NPC 不存在")
    if state_manager.is_npc_busy(request.npc_id):
        raise HTTPException(409, detail="NPC 正在与其他玩家对话")

    state_manager.set_npc_busy(request.npc_id, True)
    try:
        affinity = relationship_manager.get_affinity(request.npc_id, request.player_name)
        agent = agent_manager.get_agent(request.npc_id, affinity["level"])
        reply = agent.run(request.player_message)
        new_affinity = relationship_manager.update_affinity(
            request.npc_id, request.player_name,
            request.player_message, reply
        )
        dialogue_logger.log_dialogue(...)
        return DialogueResponse(
            npc_reply=reply,
            affinity_level=new_affinity["level"],
            affinity_score=new_affinity["score"]
        )
    finally:
        state_manager.set_npc_busy(request.npc_id, False)
```

busy 像厕所门锁：占着就 409，说完（或报错）`finally` 开门。**漏写 finally 是新手最常见事故**——一次异常后 NPC 永远 busy。

### 15.4.3 状态管理与日志系统

**StateManager** 跟踪：位置、`is_busy`、`current_action`、背景台词、上次互动时间等。初始化时写入张三 / 李四 / 王五的默认坐标与 idle。

**DialogueLogger** 双输出：控制台实时看 + 按日文件归档。至少记录：NPC、玩家、双方文本、好感等级/分数、互动次数。没有日志，好感与 Prompt 调参会变成玄学。

### 15.4.4 理解 Godot 的场景系统

（本节在原书放在后端章末，作为前端预习。）

- **节点（Node）**：乐高块（Sprite2D、CharacterBody2D、AudioStreamPlayer…）  
- **场景（Scene）**：保存为 `.tscn` 的节点树，可嵌套实例化  

玩家场景示例：

```
Player (CharacterBody2D)
├─ AnimatedSprite2D
├─ CollisionShape2D
└─ Camera2D
```

三 NPC 共用一个 `NPC.tscn`：改气泡一次，全员生效；差异用导出变量（名字、id、职称）。这就是后面 15.5 的地基。

## 15.5 Godot 游戏场景构建

> **本节目标**：选型理由；四个核心场景怎么搭；玩家移动与 NPC 交互信号。

### 为什么选 Godot（选型速记）

1. **2D 成熟**：TileMap / AnimatedSprite2D / CharacterBody2D  
2. **MIT 开源**：教学友好  
3. **GDScript ≈ Python**：学习曲线平缓  
4. **HTTPRequest**：天然对接 FastAPI  

局限：重度 3D 另议；本项目像素办公室足够。

### 15.5.1 场景设计与资源组织

四个核心场景（见图 15.12）：

| 场景 | 角色 |
|------|------|
| Main | 组合背景、Player、三 NPC、UI、墙、BGM |
| Player | 移动、动画、相机、音效 |
| NPC | 碰撞、动画、InteractionArea、名牌/气泡 |
| DialogueUI | CanvasLayer 对话框 |

**推荐创建顺序（新手按这个做不容易乱）：**

1. **Player.tscn**：`CharacterBody2D` + AnimatedSprite2D + CollisionShape2D + Camera2D + 音效  
2. **NPC.tscn**：碰撞 + 动画 + `InteractionArea(Area2D)` + NameLabel + DialogueLabel  
3. **DialogueUI.tscn**：CanvasLayer → Panel → 名字/职称/文本/输入/发送/关闭  
4. **Main.tscn**：背景 → 实例化 Player → 三次实例化 NPC → DialogueUI → Walls → BGM  

**场景实例化直觉：** 编辑器里「实例化」= 复制整棵节点树。改 `NPC.tscn` 加一个气泡节点，张三李四王五自动都有。

### 15.5.2 玩家控制实现

`player.gd` 关注点：

| 点 | 做什么 |
|----|--------|
| `add_to_group("player")` | NPC 靠组识别「这是玩家」 |
| `_physics_process` | 读输入向量 → `velocity` → `move_and_slide` |
| `is_interacting` | 对话中锁移动、播 idle、停走路音 |
| 四向动画 / `flip_h` | 缺专用动画时用翻转兜底 |
| 按 `E` | 若有 `nearby_npc`，通知对话系统 |

核心片段（GDScript，读起来很像 Python）：

```gdscript
func _ready():
    add_to_group("player")  # 重要！NPC 靠这个组识别玩家
    camera.enabled = true

func _physics_process(_delta):
    if is_interacting:
        velocity = Vector2.ZERO
        move_and_slide()
        animated_sprite.play("idle")
        stop_running_sound()
        return

    var input_direction = Input.get_vector("ui_left", "ui_right", "ui_up", "ui_down")
    velocity = input_direction * speed
    move_and_slide()
    update_animation(input_direction)
```

**新手易混：** `_process` 每帧逻辑；**移动物理**放 `_physics_process` 更稳。对话锁移动用标志位，不要删掉 Player 节点。

### 15.5.3 NPC 行为与交互

- `InteractionArea` 的 `body_entered` / `body_exited` 维护「附近玩家」  
- 提示「按 E 键交互」  
- 按 E → 信号 / `call_group` 通知 Main / UI，带上 `npc_id` 或名字  
- 可展示批量背景台词气泡  

**信号思维：** NPC 不直接 `get_node("../../DialogueUI")` 乱改 UI，而是发事件；Main 负责接线。这样 NPC.tscn 可单独测交互范围。

伪流程：

```
玩家进入 Area → NPC 记下 player → 显示提示
玩家按 E → 发「开始对话(npc)」 → Main 开 UI + 锁移动
对话结束 → 解锁移动 → 清提示
```

## 15.6 前后端通信实现

> **本节目标**：弄懂异步 HTTP 客户端、对话 UI 职责、Main 如何把信号焊成闭环。

### 15.6.1 API 客户端封装

`api_client.gd`（常作 AutoLoad 单例）把 HTTP 细节藏起来：

- 基址、超时、JSON 编解码（URL 多来自 `config.gd`）  
- `send_chat` / `request_dialogue`、`get_npc_status`、可选好感查询  
- 信号：`chat_response_received` / `dialogue_received`、`request_failed` / `chat_error`  

**为什么异步？** `HTTPRequest` 发请求不阻塞游戏帧；回包用信号通知。多个 API 用**多个 HTTPRequest 子节点**，避免互相抢同一个连接状态。

**异步原则：** 请求发出后游戏继续跑；回包再刷 UI，避免卡死。

### 15.6.2 对话 UI 实现

职责清单：

1. 显示 NPC 名与职称  
2. RichTextLabel 展示回复  
3. LineEdit 收输入 + 发送 / 关闭  
4. 发送中禁用按钮，防连点打爆后端  

UI = 听筒；思考在后端。不要在 UI 脚本里拼 Prompt。

### 15.6.3 主场景整合

推荐接线闭环：

```
E 交互 → 开 UI → ApiClient POST → 回写回复 → 关 UI 解锁移动
         ↘ 定时 GET /npcs/status → 刷新背景气泡
```

Main 像「总调度」：

- 听 NPC / Player 的交互信号  
- 调 ApiClient  
- 把回复交给 DialogueUI  
- 定时拉状态，更新三个气泡  

做到这一步，整章「可玩 Demo」闭环完成。

## 15.7 总结与展望

### 15.7.1 本章回顾

你带走的五块积木：

1. **分层架构**：渲染 / API / Agent / 外部服务  
2. **NPC 智能**：SimpleAgent + Prompt + 记忆  
3. **关系系统**：五级好感驱动语气

### 15.7.2 扩展方向（选题菜单）

1. 多人在线（WebSocket + 每玩家好感）  
2. 任务系统（好感门槛解锁）

5. 动态事件（会议 / 派对）

### 15.7.3 思考与展望

AI NPC 的三座山：**成本、延迟、内容可控**。对策方向包括批量/缓存、打字机动画与预生成、端侧小模型、Prompt 与过滤护栏。

## 新手易混速查

| 易混 | 正确理解 |
|------|----------|
| 批量 vs 即时 | 批量=氛围气泡；按 E 认真聊=即时 Agent |
| 好感分数 vs 语气 | 分数在后端账本；玩家感到的是 Prompt 改过的语气 |
| 404 vs 409 | 404=NPC 不存在；409=NPC 正忙 |
| 节点 vs 场景 | 节点是积木；场景是可复用的积木树 |
| GDScript 与 Python | 语法像，但是跑在 Godot；调 AI 必须走 HTTP |
