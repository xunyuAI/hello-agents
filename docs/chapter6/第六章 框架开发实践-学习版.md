# 第六章 框架开发实践

上一章我们站在「使用者」视角，用低代码平台快速搭智能体。这一章换到「框架开发者」视角：当你既想保留代码可控性，又不想每次从零重写 Agent Loop、状态管理、工具调用和日志时，业界主流的智能体框架就是下一步。

你可以这样理解整章主线：

- **第四章**：手搓 ReAct / Plan-and-Solve / Reflection，看懂内脏。
- **第五章**：低代码平台，快验与业务编排。
- **第六章**：用框架把「共性苦活」标准化，专注业务逻辑与可靠性。

很多人一上来会问：「框架和第四章自己写的类有什么本质区别？」答案不是「框架更高级」，而是：框架提供一套**经过验证的规范**——通用主循环、组件解耦、状态与可观测能力，让你在多个项目之间复用，而不是复制粘贴债务。

读本章时，建议每遇到一个框架就抓三条：**设计哲学**（它把协作抽象成什么）、**核心积木**（你真正要配置什么）、**代表案例**（适合哪类任务）。学完还要会做选型：没有唯一赢家，只有场景匹配。

如果先记关键词：

| 框架 | 一句话 | 核心抽象 |
|------|--------|----------|
| AutoGen | 对话驱动协作 | Assistant / UserProxy / Team |
| AgentScope | 工程化消息平台 | Msg / MsgHub / Pipeline |
| CAMEL | 角色扮演自主协作 | RolePlaying / Inception Prompt |
| LangGraph | 图状态机精确控流 | State / Node / Edge |

完整可运行项目在仓库 `code/` 目录；正文与本文以原理与关键片段为主。

## 6.1 从手动实现到框架开发

从编写一次性脚本到使用成熟框架，是软件工程里一次重要的思维跃迁。第四章的代码很适合教学：任务能跑通、逻辑看得见。但如果你要构建**多个、类型不同、逻辑复杂**的智能体应用，很快会撞墙——每个项目都重写循环、记忆、工具注册和调试日志，维护成本会指数上升。

框架的本质，是把智能体共有、重复的工作抽象封装起来，让你在构建新应用时，把精力留给**独特业务逻辑**。

### 6.1.1 为何需要智能体框架

相对直接写独立脚本，使用框架的价值主要体现在四个方面。建议你把它们当成选型与验收清单，而不是营销话术。

#### ① 提升代码复用与开发效率

这是最直接的价值。好框架会提供通用的 `Agent` 基类或执行器，封装 Agent Loop。无论是 ReAct 还是 Plan-and-Solve，都可以基于标准组件快速搭建，避免重复劳动。

新手可以这样自检：如果换一个业务，你是否还要重写「调模型 → 解析动作 → 调工具 → 写记忆」整条链？若答案是「是」，说明你还在脚本阶段。

#### ② 实现核心组件的解耦与可扩展性

健壮系统应由松散耦合模块组成。框架通常强制你分离：

- **模型层 (Model Layer)**：与大语言模型交互，可替换 OpenAI、Anthropic、本地模型等。
- **工具层 (Tool Layer)**：标准化工具定义、注册与执行；加新工具不应牵一发动全身。
- **记忆层 (Memory Layer)**：短期/长期记忆，可切换滑动窗口、摘要等策略。

这种模块化让更换或升级任一组件变得简单——这就是工程上的可扩展性。

#### ③ 标准化复杂的状态管理

第四章 ReflectionAgent 里的 `Memory` 只是起点。真实长时运行应用里，状态管理是巨大挑战：上下文窗口限制、历史持久化、多轮对话状态跟踪……框架提供通用机制，你不必每次从零处理。

经验之谈：「状态乱」往往比「Prompt 不够好」更早让多智能体项目翻车。

#### ④ 简化可观测性与调试

行为复杂时，理解决策过程至关重要。精心设计的框架会内置可观测能力，例如 Callbacks：在 `on_llm_start`、`on_tool_end`、`on_agent_finish` 等生命周期节点自动记日志或上报。这比到处 `print` 更系统。

因此，从手动实现走向框架开发，不仅是代码组织方式的改变，更是构建复杂、可靠、可维护智能体应用的必由之路。

### 6.1.2 主流框架的选型与对比

如果说 LangChain、LlamaIndex 定义了第一代通用 LLM 应用框架范式，那么新一代框架更聚焦：**多智能体协作**与**复杂工作流控制**。

本章聚焦四个代表，它们设计理念不同，分别代表不同技术路径（对应原书表 6.1）：

#### AutoGen：通过对话实现协作

把多智能体系统抽象为由多个「可对话」智能体组成的群聊。你定义角色（如 Coder、ProductManager、Tester）和交互规则（例如 Coder 写完由 Tester 接管）。任务解决过程，就是这些智能体在群聊中通过自动化消息传递，不断对话、协作、迭代直至目标达成。

#### AgentScope：易用性 + 工程化

阿里达摩院出品的多智能体开发平台。强调友好接口、消息传递机制与分布式部署，适合构建和运维复杂、大规模系统。你可以把它想象成「智能体操作系统」，而不只是对话脚本库。

#### CAMEL：角色扮演（Role-Playing）

只需为两个智能体设定角色与共同任务（例如 AI 研究员 × Python 程序员），它们就能在**初始提示（Inception Prompting）**引导下自主多轮对话，相互启发配合。极大降低设计多智能体对话流程的复杂度——轻架构、重提示。

#### LangGraph：把流程建成图

LangChain 生态扩展。将执行流程建模为图：节点是步骤（调 LLM、执行工具），边是跳转逻辑。天然支持循环，使 Reflection 这类迭代修正工作流变得直观。强项是可控、可审计。

> **学习提示**：先不要问「哪个最强」，先问「我的任务更像圆桌会、消息总线、双人对手戏，还是流程图？」

## 6.2 框架一：AutoGen

AutoGen 的设计哲学根植于「以对话驱动协作」：把复杂任务解决流程，映射为不同角色智能体之间的一系列自动化对话。教材以 `0.7.4` 为例——这是一次重要架构重构：从类继承转向更灵活的**组合式架构**。

### 6.2.1 AutoGen 的核心机制

#### （1）框架结构的演进：分层 + 异步优先

新架构引入清晰分层：

- **`autogen-core`**：底层基础，封装与语言模型交互、消息传递等，保证稳定性与扩展性。
- **`autogen-agentchat`**：构建于 core 之上，提供对话式多智能体应用的高级接口。

同时全面转向异步（`async/await`）。多智能体场景里，等 LLM API 是主要耗时；异步让系统在等待一个智能体响应时处理其他任务，避免线程干等，提升并发与资源利用率。

#### （2）两大核心智能体组件

- **AssistantAgent（助理智能体）**：任务主要解决者，核心是封装 LLM。靠 System Message 变成不同「专家」，负责写计划、写代码、写文章等。
- **UserProxyAgent（用户代理智能体）**：双重角色——既是人类用户的「代言人」（发起任务、传达意图），又是可靠的「执行器」（可执行代码或调用工具并把结果反馈）。设计意图是清晰拆分「思考」与「行动/人在环」。

#### （3）从 GroupChatManager 到 Team

多 Agent 协作需要协调机制。新架构常用更灵活的 Team，例如 **RoundRobinGroupChat（轮询群聊）**：按预设顺序依次发言，适合流程固定的任务（产品经理 → 工程师 → 审查员）。

工作流可记为五步：组队 → 按序激活 → 被点名者响应 → 写入历史并传下一人 → 终止（出现 `TERMINATE` 或达到 `max_turns`）。

### 6.2.2 软件开发团队

案例目标：开发一个**实时显示比特币当前价格**的 Web 应用。任务虽小，却覆盖需求→选型→编码→审查→测试全链路。

四个角色：

| 角色 | 职责 |
|------|------|
| ProductManager | 模糊需求 → 可执行计划 |
| Engineer | 按计划写代码（如 Streamlit） |
| CodeReviewer | 质量、安全、规范审查 |
| UserProxy | 发起任务、执行验证，最终发 TERMINATE |

角色划分本身就是多智能体设计的关键一步：把大任务切成领域专家子任务。

### 6.2.3 核心代码实现（学习版精讲）

#### 模型客户端

用 `OpenAIChatCompletionClient` 对接兼容 OpenAI 规范的服务（含 Azure、Ollama 等），并用环境变量管理密钥——这是良好工程实践。

```python
from autogen_ext.models.openai import OpenAIChatCompletionClient

def create_openai_model_client():
    return OpenAIChatCompletionClient(
        model=os.getenv("LLM_MODEL_ID", "gpt-4o"),
        api_key=os.getenv("LLM_API_KEY"),
        base_url=os.getenv("LLM_BASE_URL", "https://api.openai.com/v1")
    )
```

#### System Message = 行为准则 + 交接协议

定义智能体的核心在于高质量系统消息：职责、输出结构，以及**显式引导下一棒**（如「请工程师开始实现」「请代码审查员检查」）。提示工程是多智能体高效协作的关键。

产品经理示例（结构示意）：

```python
def create_product_manager(model_client):
    system_message = """你是一位经验丰富的产品经理...
当接到开发任务时，请按以下结构分析：
1. 需求理解与分析
2. 功能模块划分
3. 技术选型建议
4. 实现优先级排序
5. 验收标准定义
请简洁明了地回应，并在分析完成后说"请工程师开始实现"。"""
    return AssistantAgent(
        name="ProductManager",
        model_client=model_client,
        system_message=system_message,
    )
```

工程师、审查员同理：各自专长清单 + 行动步骤 + 交接话术。UserProxy 则用 `description` 说明职责，并约定完成后回复 `TERMINATE`。

#### 定义团队

```python
team_chat = RoundRobinGroupChat(
    participants=[product_manager, engineer, code_reviewer, user_proxy],
    termination_condition=TextMentionTermination("TERMINATE"),
    max_turns=20,
)
```

记住三点：`participants` 顺序=发言次序；`TERMINATE` 常由 UserProxy 发出；`max_turns` 是防死循环安全阀。

#### 异步启动

```python
result = await Console(team_chat.run_stream(task=task))
# 入口：asyncio.run(...)
```

`task` 作为初始消息传入后，PM 先接球，整条自动化协作开始。预期流水线：User → PM → Engineer → Reviewer → UserProxy → TERMINATE。可能还有礼貌收尾轮次。

### 6.2.4 AutoGen 的优势与局限性

**优势**：不必先画复杂状态机，流程自然映射为对话；System Message 专业化可复用；RoundRobin 清晰；UserProxy 天然支持 Human-in-the-loop。

**局限**：LLM 对话不确定，可能偏题或循环；调试常面对长对话历史，缺乏传统堆栈——「对话式调试」难题。

**非 OpenAI 模型**：在 0.7.4 中需传入 `model_info` 字典（如 DeepSeek），告知框架能力边界（function_calling、context_length、vision 等）。

## 6.3 框架二：AgentScope

如果说 AutoGen 是灵活的「对话工作室」，AgentScope 更像完整的「智能体操作系统」：开发→测试→部署全生命周期，内置分布式、容错、可观测等企业级特性。它选择**组合式架构**与**消息驱动模式**。

### 6.3.1 AgentScope 的设计

#### （1）分层架构

自下而上可记为四层：

1. **基础组件层**：Message、Memory、Model API、Tool
2. **智能体基础设施层**：预置 Agent、ReAct、钩子、并行工具、异步实时控制
3. **多智能体协作层**：MsgHub（路由）+ Pipeline（顺序/并发编排）
4. **开发与部署层**：Runtime（生产运行时）+ Studio（可视化工具链）

#### （2）消息驱动

交互单位是 `Msg`，不是硬函数调用：

```python
from agentscope.message import Msg

message = Msg(
    name="Alice",
    content="Hello, Bob!",
    role="user",
    metadata={"timestamp": "...", "message_type": "text", "priority": "normal"}
)
```

收益要记牢四条：**异步解耦**、**位置透明**（本地/远程无所谓）、**可观测**（条条可追踪）、**可靠性**（持久化与重试）。

#### （3）智能体生命周期

统一基类 `AgentBase`。开发者通常主要写 `reply`；可选 `observe` 写入记忆。框架管初始化/运行/暂停/销毁等生命周期。

#### （4）MsgHub

消息中枢：点对点/广播/组播路由；消息可持久化到 SQLite、MongoDB 等；原生分布式，经 RPC 透明跨节点通信。代价是：你需要适应异步与消息驱动范式。

### 6.3.2 三国狼人杀游戏

案例把刘备、关羽、诸葛亮等经典角色引入狼人杀：既完成阵营任务，又体现人物性格——适合观察**实时协作、角色扮演、策略博弈**与**多层次角色建模**。

#### 三层架构

- **游戏控制层**：`ThreeKingdomsWerewolfGame` 维护全局状态、推进昼夜、裁定胜负
- **智能体交互层**：全靠 MsgHub（狼人密谈、白天辩论）
- **角色建模层**：`DialogAgent` + 提示词，「游戏角色 + 三国人格」

传统实现爱用中心状态机硬切阶段；这里用「在什么频道、用什么模式交换消息」描述流程。

#### 狼人阶段示例思路

通过 MsgHub 为狼人创建临时私密频道 → 讨论轮次 → 关闭自动广播 → `fanout_pipeline` + 结构化模型并行收集击杀投票。

#### 结构化输出 = 规则硬约束

例如 `DiscussionModelCN`（是否达成一致、信心 1–10、关键证据）、`WitchActionModelCN`（解药/毒药/目标）。把规则写成字段校验，比纯 Prompt「请遵守规则」更稳：女巫不能乱用药、预言家每晚限一人。

#### 双重角色提示词

`get_role_prompt(role, character)`：你是{character}，扮演{role} + 阵营规则 + 以该人物性格说话。同一狼人位：曹操偏狡猾，张飞偏冲动——可观察风格差异。

#### 并发与容错

`fanout_pipeline` 并行收集全员投票，模拟「同时投票」。单 Agent 异常时 try/except 给默认结构化响应，保证整局不崩——局部失败 ≠ 全局崩溃。

### 6.3.3 优势与局限性

**优势**：复杂流程映射为并发异步消息事件；结构化输出提升稳定可预测；原生并发与容错。

**局限**：学习曲线（异步、分布式）；简单对话场景可能过度工程化；生态仍在成长。

选型直觉：要生产级、大规模、高可靠 → 认真看 AgentScope；快速原型/轻量对话 → 可先选更轻框架。

## 6.4 框架三：CAMEL

CAMEL 最初目标不是功能大全，而是：在最少人类干预下，让两个智能体通过「角色扮演」自主协作。关键词是**轻架构、重提示**。

### 6.4.1 CAMEL 的自主协作

#### （1）角色扮演（Role-Playing）

典型双角色：

- **AI User**：提出需求、下达指令、构思步骤（推动者）
- **AI Assistant**：执行操作、提供方案（执行者）

例：资深股票交易员 × 优秀 Python 程序员，协作开发策略分析工具——跨领域专家对话，完成单方难独立完成的任务。

#### （2）引导性提示（Inception Prompting）

开局分别注入结构化 System Prompt，作为「行动纲领」，通常包含：

1. 明确自身角色
2. 告知协作者角色
3. 定义共同目标
4. 设定行为约束与沟通协议（一次一步、完成前不追问、用特定标志标识完成等）

这些约束让对话以高度结构化、任务驱动的方式推进，而不是闲聊跑偏。

### 6.4.2 AI 科普电子书案例

场景：心理学家 × 作家，共同创作面向大众的《拖延症心理学》短篇电子书——既要科学严谨，又要可读。

#### 关键步骤

1. **写清 `task_prompt`**：目标读者、字数、结构、风格要求。它既是任务说明书，也会被用来生成引导性提示。
2. **`RolePlaying(...)`**：作家作 `user_role`（推动结构与指令），心理学家作 `assistant_role`（提供专业知识）。
3. **`init_chat()` + `while step()`**：自动开场；每轮双方各发言；下一轮输入取助理上一轮输出；直到 `<CAMEL_TASK_DONE>` 或轮次上限。

#### 四阶段协作（观察日志时对照）

| 阶段 | 大约轮次 | 在做什么 |
|------|----------|----------|
| ① 框架对齐 | 1–5 | 作家提结构，心理学家补学术模块 |
| ② 知识转译 | 6–20 | 硬核概念 ↔ 比喻与生活案例 |
| ③ 迭代打磨 | 21–25 | 流畅性 vs 事实核查 |
| ④ 总结收束 | 收尾 | 实用建议与回顾，出现完成标志 |

对话片段常见模式：作家 `Instruction` → 心理学家 `Solution` → `Next request`。

### 6.4.3 优势与局限性

**优势**：少代码激发深度协作；自然涌现常比硬编码流灵活；生态在扩展（多模态、工具、多模型、与 LangChain/CrewAI/AutoGen 互操作）。

**局限**：高度依赖提示质量与调试直觉；大规模多智能体弱于 AutoGen 路由 / AgentScope 分布式；严流程/高并发/复杂决策树可能不如 LangGraph / AgentScope / AutoGen。

## 6.5 框架四：LangGraph

LangGraph 作为 LangChain 生态扩展，把智能体执行流程建模为**状态机**，并表示为**有向图**。与「靠聊」的框架不同：节点做计算，边决定下一步；**天然支持循环**，使迭代、反思、自我修正更直观。

### 6.5.1 LangGraph 的结构梳理

三块积木：

#### State（全局状态）

通常是 `TypedDict`，含 messages、current_task、final_answer 等。所有节点读写同一中心状态。

#### Node（节点）

Python 函数：接收状态，返回更新后的状态。例如 planner_node、executor_node。

#### Edge（边）

- **常规边**：A 的输出总是流向固定的 B
- **条件边**：用函数看状态，动态决定下一跳——实现循环与分支的关键

组装示意：`StateGraph` → `add_node` → `set_entry_point` / `add_edge` / `add_conditional_edges` → `compile()` → `stream()`。

心智模型：先定状态图式，再挂节点函数，最后把跳转说清楚，然后编译运行。

### 6.5.2 三步问答助手

固定流程：**Understand → Search → Answer**。

#### SearchState 设计要点

同时保留 `user_query`（理解后的需求）与 `search_query`（优化后的检索词）——自然语言问题 ≠ 最佳搜索关键词。另有 `search_results`、`final_answer`、`step` 等字段。

#### 三节点职责

1. **理解节点**：读用户消息，让 LLM 输出「理解 + 搜索词」，写入状态，`step=understood`
2. **搜索节点**：用 Tavily 真实搜索；失败则 `step=search_failed`
3. **回答节点**：若失败则 LLM 知识回退；否则综合搜索结果生成答案，`step=completed`

#### 构建与运行

线性边：`START → understand → search → answer → END`，可用 `InMemorySaver` 作 checkpointer。运行时可问「明天去北京，天气怎么样？有合适景点吗」，终端会展示理解→搜索→回答过程，并支持多轮交互。

### 6.5.3 优势与局限性

**优势**：高度可控、可预测、可审计；原生循环支持反思修正与容错路径；节点模块化，易插人类审核节点。

**局限**：前期样板多，要想 how 而不只是 what；缺少开放式社会性涌现；调试需全局理解节点/状态/边条件。

## 6.6 本章小结

四个框架，四种哲学：

- **AutoGen**：群聊抽象，「以对话驱动协作」
- **AgentScope**：工业健壮与扩展，从「能运行」到「能稳定服务」
- **CAMEL**：轻量角色扮演 + 引导提示，少码深协作
- **LangGraph**：显式图结构，循环与精确控制

提炼两条设计权衡轴：

1. **涌现式协作 vs 显式控制**  
   - 涌现（AutoGen / CAMEL）：定角色与目标，复杂行为从对话规则中涌现——贴近人际，但难预测调试。  
   - 显式（LangGraph）：逐步定义跳转——牺牲部分惊喜，换来可靠与可观测。

2. **工程化维度（AgentScope 特别强调）**  
   无论选哪种协作范式，走向生产都要面对并发、容错、分布式等挑战。

没有唯一赢家。选型前先问：要涌现还是可控？要原型还是生产？要几人协作还是严流程？

下一章：从零构建属于你自己的智能体框架。

## 附录 A · AutoGen 代码精读（新手加厚）

下面把原书关键片段按「读代码四问」再走一遍：这段在定义能力还是组织流程？操作的是模型、角色还是控流？删掉会丢什么？更像业务逻辑还是工程护栏？

### A.1 工程师与审查员的系统消息在守什么

工程师要交付「完整可运行代码」，并主动把球传给审查员；审查员要覆盖质量/安全/规范，再把球传给用户代理。你会发现：**交接话术写进 System Message**，比指望模型自己「记得下一棒是谁」可靠得多。

```python
def create_engineer(model_client):
    system_message = """你是一位资深的软件工程师，擅长 Python 开发和 Web 应用构建。
当收到开发任务时，请：
1. 仔细分析技术需求
2. 选择合适的技术方案
3. 编写完整的代码实现
4. 添加必要的注释和说明
5. 考虑边界情况和异常处理
请提供完整的可运行代码，并在完成后说"请代码审查员检查"。"""
    return AssistantAgent(name="Engineer", model_client=model_client, system_message=system_message)

def create_code_reviewer(model_client):
    system_message = """你是一位经验丰富的代码审查专家...
审查流程：1.读懂逻辑 2.查规范 3.找问题 4.给具体修改建议 5.评估整体质量
请提供具体的审查意见，完成后说"代码审查完成，请用户代理测试"。"""
    return AssistantAgent(name="CodeReviewer", model_client=model_client, system_message=system_message)
```

### A.2 任务描述要写到什么粒度

比特币案例的 `task` 同时写了**核心功能**与**技术要求**。对多智能体团队来说，初始任务太模糊，产品经理会花很多轮「猜需求」；太细又剥夺 PM 发挥空间。教材粒度是一个很好的中间点：功能清单 + Streamlit + 错误处理/加载态。

### A.3 运行日志怎么读

看到 `TextMessage (ProductManager)` 后是需求分析结构化输出，再出现「请工程师开始实现」——说明交接话术生效。审查完成后 UserProxy 可能先说「已经完成需求」，真正结束往往要等到输入 `TERMINATE`。若出现礼貌收尾轮次，那是轮询还在转，直到终止条件命中。

### A.4 DeepSeek 等模型为何要 model_info

兼容 OpenAI 协议 ≠ 能力画像相同。`model_info` 声明 function_calling、vision、json_output、context_length 等，避免框架按「默认 GPT 能力」误用。

## 附录 B · AgentScope 消息驱动对照表

| 游戏阶段 | 通信模式 | 框架手段 | 你在学什么 |
|----------|----------|----------|------------|
| 狼人密谈 | 组内广播 | MsgHub(werewolves, auto_broadcast=True) | 临时私密上下文 |
| 击杀投票 | 并行收集 | fanout_pipeline + 结构化模型 | 同时决策 |
| 预言家查验 | 点对点 | 主持人与预言家消息 | 路由多样性 |
| 白天讨论 | 全员广播 | MsgHub(alive_players...) | 公开信息场 |
| 白天投票 | 并行收集 | fanout_pipeline | 与夜晚投票同构 |

把「状态机硬切阶段」翻译成「频道 + 交换模式」，是 AgentScope 案例最值得带走的思维。

### B.1 结构化模型字段练习

试着为习题中的「猎人」角色草拟字段，例如：

- `shoot: bool` — 是否开枪
- `target_name: Optional[str]` — 目标
- `reason: str` — 公开陈述理由

再问自己：哪些约束必须靠 Field 校验（不能对已死玩家开枪），哪些可以靠提示词软约束？

### B.2 容错为什么重要

狼人杀里某个智能体 JSON 解析失败，不应拖垮整局。`try/except` + 默认 `DiscussionModelCN(...)` 是生产思维的微缩版：降级、可观测、继续前进。

## 附录 D · LangGraph 从「玩具图」到「助手图」

### D.1 最小循环图（教材规划者-执行者）

条件边返回值必须是路由表里的键：`continue_to_planner` / `end_workflow`。这是新手最易踩的坑——返回了中文「继续」却对不上映射。

### D.2 三步助手里的「失败路径」

案例用 `step == "search_failed"` 在回答节点内分支。习题要求你升级成「反思环」时，更地道的 LangGraph 做法是：增加 `reflect` 节点 + 条件边，例如答案过短则回到 `search` 或 `answer`。

### D.3 checkpointer 的意义

`InMemorySaver` 让多轮对话能记住图状态。生产可换持久化 checkpointer。这与第六章「状态管理是框架价值」形成呼应。

### D.4 和第四章 Reflection 的关系

第四章手写反思循环；LangGraph 用图原生表达「绕回」。学完应能画：生成 → 评价 →（不通过）→ 再生成。

## 附录 F · 常见问题 FAQ

**Q1：必须把四个框架都装一遍吗？**  
不必。先跟做一两个案例建立直觉，其余精读原理 + 对照表。以「会选型」为验收，而不是「会背 API」。

**Q2：框架会不会过时很快？**  
会变。但「对话 / 消息 / 角色戏 / 图控流」四种抽象更稳。抓住抽象，换版本时迁移成本更低。

**Q3：和 LangChain 什么关系？**  
LangGraph 属于 LangChain 生态扩展；其它框架相对独立。不必把「生态绑定」当成唯一选型理由。

**Q4：中文模型效果差怎么办？**  
先检查：System Message 语言与任务语言一致；温度与 max_turns；结构化输出是否开启；模型是否真支持工具/JSON。AutoGen 的 `model_info`、AgentScope 的结构化模型、CAMEL 的引导提示，都是调参抓手。

**Q5：下一章为什么还要自建框架？**  
因为只用框架会停在「使用者」；自建才能把规范内化，并在标准组件不够用时具备创造能力——这与第四章「为何造轮子」一脉相承。

## 对照原书精读 · 把日志当成教材

原书花了大量篇幅展示真实运行日志。新手容易跳过日志，只抄 API。反过来：日志才是「框架在干什么」的录像带。下面按框架告诉你日志里该盯什么。

### AutoGen 日志盯这四件事

1. **谁在说话**：`TextMessage (ProductManager)` 等角色标签是否按 participants 顺序出现。
2. **交接词有没有出现**：「请工程师开始实现」「请代码审查员检查」「请用户代理测试」。
3. **TERMINATE 从哪来**：是否由 UserProxy 侧发出；若迟迟不结束，检查终止条件与 max_turns。
4. **有没有偏题循环**：同一争论重复多轮且无进展——这是对话式调试的信号。

### AgentScope 日志盯这四件事

1. **主持人公告**：阶段切换是否清晰（天黑/睁眼/投票）。
2. **私密频道是否串台**：狼人发言是否出现在白天公开讨论前被「不该听到的人」引用（设计上应隔离）。
3. **结构化字段**：投票目标、是否用药等是否为合法字段值。
4. **异常降级**：是否出现警告但仍继续——说明容错生效。

### CAMEL 日志盯这四件事

1. **Instruction / Solution 节奏**是否稳定。
2. **角色有没有串戏**（作家是否开始写深层神经科学长文，心理学家是否开始改文风主导）。
3. **阶段迁移**：是否从搭框架自然进入转译与打磨。
4. **完成标志**：`<CAMEL_TASK_DONE>` 出现时机是否合理。

### LangGraph 终端盯这四件事

1. **搜索词**是否比原始问题更适合检索。
2. **搜索成功/失败**分支有没有走到。
3. **最终回答**是否引用了搜索结果（有时效信息时尤其明显）。
4. **多轮**时状态是否保持（同一会话继续追问）。
