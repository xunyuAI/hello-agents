开篇纠偏

先破除这些错觉

误解 1：有了框架就不用懂第四章范式

错。框架把范式封装起来；不懂循环与工具调用，调不通时只会玄学改 Prompt。

误解 2：四个框架有唯一赢家

错。群聊涌现、消息工程、双人角色戏、图控流——场景不同，最优解不同。

误解 3：框架 = 低代码平台

框架仍是代码库：要写 Python、管依赖、部署服务。介于手搓与纯拖拽之间。

§ 6.1

从手动实现到框架开发

教学脚本能跑通任务；多类型复杂应用很快撞墙。框架本质是一套经过验证的规范。

框架帮你省什么？

封装共有重复劳动：主循环、状态、工具、日志……你专注业务差异。

和「再抄第四章代码」有何不同？

抄代码=粘贴债务。框架=统一接口+可替换组件+工程实践。

6.1.1 · 价值①

提升代码复用与开发效率

好框架提供通用 Agent 基类/执行器，封装 Agent Loop。

  • ReAct、Plan-and-Solve 可基于标准组件快搭
  • 避免每个项目重写「调模型→解析动作→调工具→写记忆」
  • 团队共享约定，新人上手更快
不必每次开店都自己造收银系统——用成熟收银框架，你只设计菜单。

6.1.1 · 价值②

核心组件解耦与可扩展

模型层可换 OpenAI / Anthropic / 本地模型
工具层标准化定义、注册、执行；加新工具不影响别处
记忆层可换滑动窗口、摘要等策略
要点：模块化 → 更换或升级任一组件变得简单。

6.1.1 · 价值③

标准化复杂的状态管理

第四章 ReflectionAgent 的 Memory 只是开始；长时运行状态是巨大挑战。

  • 上下文窗口限制：裁剪、摘要、分段
  • 历史持久化：重启后恢复对话与任务进度
  • 多轮跟踪：子目标、待办、工具结果如何一致挂在状态上
  • 框架提供通用机制，不必每次重造

「状态乱」是多智能体项目最常见翻车点之一。

6.1.1 · 价值④

简化可观测性与调试

  • Callbacks 挂在生命周期关键节点
  • 典型：on_llm_start / on_tool_end / on_agent_finish
  • 自动日志/上报 → 追踪完整运行轨迹
  • 远比到处 print 更系统
像飞机黑匣子：框架帮你预埋探针位。

6.1.1 收束

从脚本到框架是思维跃迁

6.1.2 背景

从通用 LLM 应用框架到多智能体前沿

第一代重心

  • 链/检索/工具调用通用拼装
  • 单 Agent 或简单编排
  • 快速搭 LLM 应用

新一代重心

  • 多智能体协作
  • 复杂工作流控制
  • 对话群聊 / 消息 / 图控流等路径
要点：本章实战：AutoGen、AgentScope、CAMEL、LangGraph。

6.1.2 · AutoGen

核心思想：通过对话实现协作

  • 可对话智能体组成群聊
  • 定角色（Coder / PM / Tester）与交互规则
  • 任务解决=自动化消息传递直至目标达成
  • 适合多角色、流程感强、映射人类团队的场景

把软件工程例会自动化。

6.1.2 · AgentScope

易用性 + 工程化的多智能体平台

  • 友好接口：定义智能体、通信网络、生命周期
  • 内置消息传递机制
  • 支持分布式部署
  • 适合大规模、长期稳定的生产向系统

更像「智能体操作系统」。

6.1.2 · CAMEL

角色扮演（Role-Playing）协作

  • 为两个智能体设定角色与共同任务
  • 依赖 Inception Prompting 引导
  • 自主多轮、相互启发配合
  • 极大降低对话流程设计复杂度

轻架构、重提示。

6.1.2 · LangGraph

把执行流程建成图（Graph）

  • 节点=步骤（调 LLM、执行工具）
  • 边=跳转；条件边实现分支与循环
  • 链式大致单向；图原生可绕回
  • Reflection 类迭代修正更直观

§ 6.2

框架一：AutoGen —— 对话驱动协作

复杂任务 → 多角色智能体之间的自动化对话。教材以 0.7.4 为例：组合式架构。

像开圆桌会：定座位、发言顺序与散会口令；人设靠 System Message，Team 负责递话筒。

6.2 开篇

以对话驱动协作

  • 根植于「可对话」智能体组成的系统

演进方向

带来的收益

6.2.1 ·（1）异步

多智能体场景下的并发现实

  • 网络请求（调 LLM API）是主要耗时操作
  • 同步阻塞：等 A 时整条线程干等
  • 异步：等待 A 时可推进 B、C
  • 入口常见：asyncio.run(...) + await
result = await Console(team_chat.run_stream(task=task))
# asyncio.run(run_software_development_team())

6.2.1 ·（2）

助理智能体：任务的主要解决者

  • 核心封装 LLM
  • 根据对话历史生成计划、文章、代码
  • 通过不同 System Message 赋予不同「专家」角色
  • 同一组件类型，不同提示 = 不同专家

思考侧：推理、规划、生成——尽量由 Assistant 完成。

6.2.1 ·（2）

用户代理：代言人 + 执行器

作为代言人

  • 代表人类用户
  • 发起任务、传达意图
  • 可在关键节点介入

作为执行器

  • 可配置执行代码
  • 可调用工具
  • 把结果反馈给其它智能体
要点：区分「思考」（Assistant）与「行动/人在环」（UserProxy）。测完常发 TERMINATE。

6.2.1 ·（3）

  • 代表：RoundRobinGroupChat（轮询群聊）
  • 按预定义顺序依次发言——适合流程固定任务
产品经理 → 工程师 → 审查员：流水线站位，话筒按圈传递。

6.2.3 · System Message

ProductManager 的行为准则

  • 需求分析：核心功能与边界
  • 技术规划：清晰实现路径
  • 风险评估：技术风险与体验问题
  • 输出结构：需求理解→模块划分→选型→优先级→验收标准
  • 引导下一棒：「请工程师开始实现」
要点：系统消息定职责、输出结构与交接话术——多智能体提示工程关键。

6.2.3 · System Message

Engineer 聚焦技术实现

  • 专长：Python、Web（Streamlit/Flask/Django）、API、错误处理
  • 流程：分析→选方案→完整代码→注释→边界情况
  • 交付：完整可运行代码
  • 引导下一棒：「请代码审查员检查」
return AssistantAgent(
    name="Engineer",
    model_client=model_client,
    system_message=system_message,
)

6.2.3 · System Message

CodeReviewer 守质量关

  • 审查：可读性/可维护性/性能、安全性、最佳实践、异常处理
  • 流程：读懂→查规范→找问题→给建议→评估整体
  • 完成后：「代码审查完成，请用户代理测试」

交付前加质量关卡，避免「能跑但很脆」。

6.2.3 · UserProxy

不靠 LLM 聊天，靠代理职责收束流程

  • 代表用户提出需求
  • 执行最终代码 / 验证功能
  • 提供反馈
  • 完成后回复 TERMINATE，正常结束协作
UserProxyAgent(
  name="UserProxy",
  description="...完成测试后请回复 TERMINATE。"
)

6.2.3 ·（1）

OpenAIChatCompletionClient

可对接任何兼容 OpenAI API 规范的服务。

def create_openai_model_client():
    return OpenAIChatCompletionClient(
        model=os.getenv("LLM_MODEL_ID", "gpt-4o"),
        api_key=os.getenv("LLM_API_KEY"),
        base_url=os.getenv("LLM_BASE_URL", "https://api.openai.com/v1")
    )
要点：环境变量管密钥与地址：灵活、安全。含 Azure、Ollama 等。

6.2.3 ·（2）

行为准则 + 专业知识库 + 交接协议

  • 规定角色、职责、工作流程
  • 规定与其它智能体交互方式
  • 用独立函数封装每个角色——可维护、可复用
  • 精心设计的系统消息是高效协作的关键
没有好的岗位说明书，圆桌会就会变成各说各话。

6.2.3 ·（3）

RoundRobinGroupChat 关键参数

team_chat = RoundRobinGroupChat(
    participants=[product_manager, engineer, code_reviewer, user_proxy],
    termination_condition=TextMentionTermination("TERMINATE"),
    max_turns=20,
)
  • participants 顺序 = 发言次序
  • TERMINATE：通常由 UserProxy 测完后发出
  • max_turns：防死循环安全阀

run_stream + Console + asyncio

result = await Console(team_chat.run_stream(task=task))

从 User 到 TERMINATE 的完整闭环

6.2.4 ·（1）

客观看优势

  • 无需先画复杂状态机：流程自然映射为多角色对话
  • 更贴近人类团队协作，降低建模门槛
  • 精力聚焦「谁」与「做什么」
  • System Message 高度专业化、可复用
  • RoundRobin 清晰可预测；UserProxy 支持 Human-in-the-loop

6.2.4 ·（2）

客观看挑战

  • LLM 对话不确定 → 可能偏题、意外分支、循环
  • 调试棘手：没有清晰堆栈，只有长对话历史
  • 「对话式调试」难题
  • 缓解：质量监控、动态回退、超时与轮次硬限制
要点：顺序化流程能降低混乱，但不能消灭生成不确定性。

6.2.4 ·（3）

DeepSeek 等需传入 model_info

model_client = OpenAIChatCompletionClient(
    model="deepseek-chat",
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com/v1",
    model_info={
        "function_calling": True, "max_tokens": 4096,
        "context_length": 32768, "vision": False,
        "json_output": True, "family": "deepseek",
        "structured_output": True,
    }
)
要点：model_info 告诉框架该模型的能力边界。

  • 角色与群聊规则
  • 灵活协作

AgentScope 气质

§ 6.5

框架四：LangGraph —— 把 Agent 画成图

将执行流程建模为状态机并以有向图表示。

要点：节点=计算步骤；边=跳转；天然支持循环 → 迭代/反思/自我修正更直观。

6.5.1 开篇

革命点：链式单向 vs 图可绕回

对话式框架

  • 定角色与目标，行为从对话涌现
  • 灵活、贴近人际协作
  • 调试常面对长历史

LangGraph

  • 显式定义每步与跳转
  • 可控、可预测、可审计
  • 适合高可靠生产流程

6.5.1

全局状态：共享 TypedDict

class AgentState(TypedDict):
    messages: List[str]
    current_task: str
    final_answer: str
    # ... 任何需要追踪的字段
要点：可含对话历史、中间结果、迭代次数——状态是工作流的持久上下文。

6.5.1

节点：状态 → 更新后的状态

def planner_node(state: AgentState) -> AgentState:
    plan = f"为任务 '{state['current_task']}' 生成的计划..."
    state["messages"].append(plan)
    return state

def executor_node(state: AgentState) -> AgentState:
    result = f"执行计划 '{state['messages'][-1]}' 的结果..."
    state["messages"].append(result)
    return state
要点：节点是干活单元：规划者、执行者、搜索者……

6.5.1

常规边与条件边

最强能力在条件边。

def should_continue(state: AgentState) -> str:
    if len(state["messages"]) < 3:
        return "continue_to_planner"
    state["final_answer"] = state["messages"][-1]
    return "end_workflow"

workflow.add_conditional_edges(
    "executor", should_continue,
    {"continue_to_planner": "planner", "end_workflow": END},
)
要点：条件边用函数看状态再路由——实现循环与分支的关键。

6.5.1

StateGraph：搭积木 → compile → stream

workflow = StateGraph(AgentState)
workflow.add_node("planner", planner_node)
workflow.add_node("executor", executor_node)
workflow.set_entry_point("planner")
workflow.add_edge("planner", "executor")
# + conditional edges ...
app = workflow.compile()
for event in app.stream({"current_task": "...", "messages": []}):
    print(event)

先定状态图式，再挂节点，最后用边说清跳转，然后编译运行。

6.5.2

Understand → Search → Answer

START→ understand→ search→ answer→ END
要点：四步：定义状态 → 创建节点 → 构建图 → 运行应用。

为何同时保留 user_query 与 search_query

容错要点

  • 终端可见：理解→搜索词→Tavily→最终回答
  • 可持续交互（quit 退出）

6.5.3 ·（1）

可控、可循环、可插人审

  • 显式流程图 → 高度可控、可预测、可审计
  • 对生产级可靠性与合规追溯至关重要
  • 条件边轻松构建反思-修正与失败回退
  • 节点即函数 → 模块化；插入人类审核节点很直接

6.5.3 ·（2）

样板更多，涌现更少

  • 前期样板代码多：要想 how，而不只是 what
  • 简单任务可能显得繁琐
  • 缺少开放式「社会性涌现」惊喜
  • 调试需全局理解：节点逻辑 / 状态异变 / 边条件
要点：与对话框架对比时，这是可控性换来的代价。

6.6 核心提炼

涌现协作 × 显式控制 × 工程化

框架协作隐喻控制感更适合
AutoGen圆桌群聊中多角色流程化协作
AgentScope消息总线 OS中高高并发、分布式生产
CAMEL双专家对手戏低码高提示深度创作/研究
LangGraph流程图/状态机高可审计、可循环、严流程

没有唯一赢家。先问：要涌现还是可控？要原型还是生产？要几人协作还是严流程？

6.6 深挖

两种设计哲学

涌现式协作

  • 定义角色与目标
  • 行为从简单规则中涌现
  • 贴近人类交互
  • 有时难预测调试
  • 代表：AutoGen、CAMEL

显式控制

  • 明确每步与跳转
  • 牺牲部分涌现惊喜
  • 换来可靠性与可观测
  • 代表：LangGraph
要点：AgentScope 揭示第二轴：工程化——从「能运行」到「能稳定服务」。

§ 6.6

四种哲学，同一光谱

  • AutoGen：群聊抽象，「以对话驱动协作」
  • AgentScope：工业健壮与扩展，「能稳定服务」
  • CAMEL：轻量角色扮演 + 引导提示，少码深协作
  • LangGraph：显式图结构，循环与精确控制
