关键词地图

三种做事风格，不是「谁更高级」

ReAct

边想边做（Yao, 2022）。路径不确定、需边查边改。Thought→Action→Observation。

Plan-and-Solve

先规划再执行（Wang, 2023）。步骤清晰、任务链长更稳。Plan→Solve。

Reflection

做完回头检查（Reflexion / Shinn, 2023）。易错、要质量。执行→反思→优化。

考试：ReAct≈边想边翻资料；P&S≈先列完整步骤再下笔；Reflection≈做完自己验算。风格/代价/适用面不同。

§ 4.1.3 · 导读

统一模型接口：后面三种范式都靠它

你可以把它想成「统一的模型接口」。ReAct / Plan-and-Solve / Reflection 工作方式不同，但都要向模型发请求、拿回结果。封装好像搭积木；封装乱则每种范式重复踩坑。

HelloAgentsLLM：为本书定制的 LLM 客户端；调用任何兼容 OpenAI 接口的服务，并默认使用流式响应。

§ 4.1.3 · 构造

参数优先，否则读环境变量

class HelloAgentsLLM: def __init__(self, model=None, apiKey=None, baseUrl=None, timeout=None): self.model = model or os.getenv("LLM_MODEL_ID") apiKey = apiKey or os.getenv("LLM_API_KEY") baseUrl = baseUrl or os.getenv("LLM_BASE_URL") timeout = timeout or int(os.getenv("LLM_TIMEOUT", 60)) if not all([self.model, apiKey, baseUrl]): raise ValueError("模型ID、API密钥和服务地址必须被提供或在.env中定义。") self.client = OpenAI(api_key=apiKey, base_url=baseUrl, timeout=timeout)
护栏：缺任一配置直接抛错，避免「默默用空密钥打到一半才失败」。
§ 4.1.3 · think

流式拼接 delta，得到完整字符串

def think(self, messages: List[Dict[str, str]], temperature: float = 0) -> str: print(f"🧠 正在调用 {self.model} 模型...") try: response = self.client.chat.completions.create( model=self.model, messages=messages, temperature=temperature, stream=True, ) collected = [] for chunk in response: content = chunk.choices[0].delta.content or "" print(content, end="", flush=True) collected.append(content) print() return "".join(collected) except Exception as e: print(f"❌ 调用LLM API时发生错误: {e}") return None

temperature=0 默认更稳，利于格式化输出与调试。

§ 4.2

最经典、最适合建立直觉的范式

ReAct（Reason + Act）由 Shunyu Yao 于 2022 提出。核心：模仿人类解决问题，把推理与行动显式结合，形成「思考-行动-观察」循环。

像认真做题：先想下一步 → 查资料/调工具 → 根据新结果再想。没有一开始规划整条路线，而是边走边修正。适合信息不完整、路径不确定的场景。
§ 4.2 · 出处

Reasoning and Acting · ICLR 2023

文献 [1]：Yao et al. ReAct: Synergizing reasoning and acting in language models。

让模型每一步输出都遵循固定轨迹：Thought → Action →（环境返回）Observation，再进入下一轮，直到 Finish。

§ 4.2.1 · 背景

ReAct 诞生前的两类主流

纯思考 · CoT

  • 能引导复杂逻辑推理
  • 无法与外部世界交互
  • 易产生事实幻觉

纯行动

  • 直接输出要执行的动作
  • 缺乏规划与纠错
  • 难根据中间结果改道
ReAct 的洞察

思考与行动相辅相成：思考指导行动，行动结果反过来修正思考。

§ 4.2.1 · 三拍之一

Thought：智能体的内心独白

分析当前情况、分解任务、制定下一步计划，或反思上一步结果。这是可解释性的关键来源——调试时先看 Thought 链。

Thought: 要回答这个问题，我需要查找华为最新发布的手机型号及其主要特点。 这些信息可能在我的现有知识库之外，因此需要使用搜索引擎来获取最新数据。
§ 4.2.1 · 三拍之二

Action：调用工具或宣布结束

具体动作通常是外部工具调用，格式固定为 工具名[输入]；任务完成时用 Finish[最终答案]。

Action: Search[华为最新款手机] # 或 Action: Finish[根据搜索结果，最新旗舰是……]
格式规约是机制基石：代码靠正则精确解析意图；模型若不守格式，整条流水线会断。
§ 4.2.1 · 三拍之三

Observation：工具返回的事实

执行 Action 后从外部工具回来的结果——搜索摘要、API 返回值、错误信息等。必须写回历史，下一轮 Thought 才能「看见」。

§ 4.2.1 · 公式

策略 π 与工具 T

时间步 \(t\)：根据问题 \(q\) 与历史行动-观察轨迹，生成思考与行动：

\[\left(th_t,a_t\right)=\pi\left(q,(a_1,o_1),\ldots,(a_{t-1},o_{t-1})\right)\]

环境工具执行行动并返回观察：

\[o_t = T(a_t)\]

新的 \((a_t,o_t)\) 追加到历史，直到 Thought 判定任务完成。

§ 4.2.2 · 管理器

统一注册与调度多种工具

class ToolExecutor: def __init__(self): self.tools: Dict[str, Dict[str, Any]] = {} def registerTool(self, name, description, func): if name in self.tools: print(f"警告:工具 '{name}' 已存在，将被覆盖。") self.tools[name] = {"description": description, "func": func} def getTool(self, name): return self.tools.get(name, {}).get("func") def getAvailableTools(self) -> str: return "\n".join([f"- {n}: {i['description']}" for n,i in self.tools.items()])

§ 4.2.3 · (3) 解析

正则抽出 Thought 与 Action

def _parse_output(self, text: str): thought_match = re.search(r"Thought:\s*(.*?)(?=\nAction:|$)", text, re.DOTALL) action_match = re.search(r"Action:\s*(.*?)$", text, re.DOTALL) thought = thought_match.group(1).strip() if thought_match else None action = action_match.group(1).strip() if action_match else None return thought, action def _parse_action(self, action_text: str): match = re.match(r"(\w+)\[(.*)\]", action_text, re.DOTALL) if match: return match.group(1), match.group(2) return None, None

例：Search[华为最新手机] → 名 Search，输入 华为最新手机。

§ 4.3

先画完整蓝图，再按图施工

Plan-and-Solve：先规划 (Plan)，后执行 (Solve)。与 ReAct「边走边看」风格迥异。

ReAct 像经验丰富的侦探，根据现场蛛丝马迹随时改调查方向；Plan-and-Solve 像建筑师，动工前必须绘完整蓝图，再严格按图施工。许多现代大模型 Agent 模式都融入了这种设计。
§ 4.3.1 · 背景

缓解 CoT 多步「偏离轨道」

Plan-and-Solve Prompting 由 Lei Wang 于 2023 提出（文献 [2]）。核心动机：思维链处理多步骤复杂问题时容易偏离。

与 ReAct 每步融合思考与行动不同，P&S 将流程解耦为规划阶段与执行阶段。

§ 4.3.1

Planning → Solving

规划阶段

接收完整问题；不急着解题或调工具，而是分解问题并制定清晰分步计划（一次 LLM 调用产物）。

执行阶段

严格按计划逐步执行；每步可为独立 LLM 调用或对上步结果加工，直至得出答案。

处理需长远规划的复杂任务时，目标一致性更高，减少中间迷失。

§ 4.3.1 · 公式

π_plan 与 π_solve

规划模型生成含 \(n\) 步的计划 \(P=(p_1,\ldots,p_n)\)：

\[P = \pi_{\text{plan}}(q)\]

第 \(i\) 步解依赖问题、完整计划与历史结果；最终答案为 \(s_n\)：

\[s_i = \pi_{\text{solve}}(q, P, (s_1, \ldots, s_{i-1}))\]

§ 4.3.1 · 场景

结构性强、可清晰分解的任务

§ 4.3.2 · 代码

split 围栏 + ast.literal_eval

class Planner: def plan(self, question: str) -> list[str]: prompt = PLANNER_PROMPT_TEMPLATE.format(question=question) response_text = self.llm_client.think(messages=[...]) or "" try: plan_str = response_text.split("```python")[1].split("```")[0].strip() plan = ast.literal_eval(plan_str) return plan if isinstance(plan, list) else [] except (ValueError, SyntaxError, IndexError) as e: print(f"❌ 解析计划时出错: {e}") print(f"原始响应: {response_text}") return []
解析失败返回空列表——上层应终止，避免空计划硬跑。
§ 4.3.3 · 核心

执行器不仅解题，还要管状态

Executor 记录每步结果，作为后续步骤上下文，保证信息在任务链中顺畅流动——像仪表盘/进度条。

提示词需含四块：原始问题、完整计划、历史步骤与结果、当前步骤；并要求「仅输出该步答案，不要额外解释」。

§ 4.4.4 · 终稿

Sieve of Eratosthenes

def find_primes(n): """Finds all prime numbers between 1 and n using Sieve of Eratosthenes.""" if n < 2: return [] is_prime = [True] * (n + 1) is_prime[0] = is_prime[1] = False p = 2 while p * p <= n: if is_prime[p]: for i in range(p * p, n + 1, p): is_prime[i] = False p += 1 return [num for num in range(2, n + 1) if is_prime[num]]
§ 4.4.4 · 分析

批判前提 · 迭代改进 · 收敛终止

  1. 有效批判是优化前提：「极严格+效率」让模型不满于功能正确，指出复杂度瓶颈并建议筛法。
  2. 迭代式改进：按反馈实现 O(n log log n)。
  3. 收敛：知深仍能判断「一般无需改进」，触发终止条件。

不仅修错，更驱动质量/效率阶梯式提升。

§ 4.4.5 · 成本

调用 · 延迟 · 提示工程

  • 每轮至少 +2 次 LLM（反思+优化）；多轮成倍
  • 串行等待 → 总耗时显著，不适合强实时
  • 多角色 Prompt 设计与调试成本上升
§ 4.4.5 · 收益

以成本换质量

收益：合格→优秀的质量跃迁；内部纠错增强鲁棒性。

适合：关键业务代码/技术报告、科研推演、高可靠决策支持。

不适合：需快速响应，或「大致正确」已够 → 更轻量的 ReAct / P&S 更划算。

§ 4.5 · 向前看

生产里很少「只用一种」

更复杂 Agent 可否混合？例如：P&S 出高层计划，每步用 ReAct 调工具，低置信时触发 Reflection。

速度极高时牺牲规划还是反思？优先优化模型还是流程？——下一章将探索低代码平台与轻代码构建方案。

习题

范式对比 · 解析鲁棒性

1. 三种范式本质区别与组合

交织（ReAct）/ 解耦两阶段（P&S）/ 事后迭代（Reflection）。

智能家居：多设备+习惯调节——可 ReAct 做感知与工具调用，习惯策略用 Reflection 审慎，日程类用 P&S。

混合架构：规划器 + 工具循环 + 低置信反思。

2. 正则脆弱与更鲁棒方案

脆弱：格式偏离、多 Action、嵌套括号、语言混杂。

替代：JSON / structured output / function calling；对比可维护性与模型支持度。

习题

工具扩展 · 动态重规划

3. ToolExecutor 扩展

加 Calculator；错误调用多次时的引导（Observation 明示+Prompt 纠错）；50–100 工具时用检索/分层/embedding 组织描述。

4. 静态计划的局限

执行失败 → 触发重规划（保留已成功步骤）。北京→上海差旅：工具多、不确定性高，常偏 ReAct 或「粗计划+ReAct 子步骤」。分层规划：控复杂度、可复用子计划。

习题

双模型反思 · Prompt · 电商客服

5. Reflection 深入
强模型反思+快模型执行：质量/成本权衡。更智能终止：分数阈值、连续两轮无实质改动。论文助手：逻辑/创新/表达/引用多维反思。
6. 提示词工程
ReAct Prompt 服务交织循环与格式；P&S 服务列表计划。角色设定改变反馈焦点。Few-shot 提升格式遵循。
7. 电商客服综合
组合：查单/政策用工具 ReAct，争议决策 Reflection。工具≥3：订单查询、物流、退款政策、发信。风险：幻觉同意退款、越权——加规则引擎、人工阈值、审计日志。
