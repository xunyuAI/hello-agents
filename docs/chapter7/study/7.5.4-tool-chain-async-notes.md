## 2. 工具链（ToolChain）在干什么？

### 2.1 一句话

把「工具 A 的输出 → 工具 B 的输入」写成**可配置的步骤列表**，用 `context` 当黑板传递中间结果。

### 2.2 执行时序（顺序 = 有依赖）

```text
initial_input
    │
    ▼
context["input"] = initial_input
    │
    ├─ step1: template.format(**context) → registry.execute_tool(...)
    │         context[output_key1] = result
    │
    ├─ step2: 可用 {input} / {output_key1} ...
    │         context[output_key2] = result
    │
    └─ 返回最后一步的 output_key
```

核心机制只有三个：

1. **`input_template`**：`str.format(**context)`，如 `"{input}"`、`"{search_result}"`  
2. **`output_key`**：本步结果写入 context，供后续步骤引用  
3. **`ToolRegistry.execute_tool`**：真正干活的还是注册表，链只做编排

这对应「单一职责」：链不管搜索怎么实现，只管「先谁后谁、数据怎么流」。

### 2.3 和 Agent「自己选工具」的差别

| | ReAct / FunctionCall | ToolChain |
|--|----------------------|-----------|
| 谁决定下一步 | LLM 每轮选工具 | 开发者预先写死步骤 |
| 适合 | 开放式、路径不固定 | 固定流水线、可复现流程 |
| 风险 | 可能乱调工具 | 灵活度低，但可控 |

课程进度上：你刚学完 Agent 自主用工具；这里再补一条「**确定性流水线**」路径，生产里两者常并存（Agent 触发某条链，或链作为宏工具注册）。

### 2.4 教材 `create_research_chain` 的教学用意与落地注意

教材示例：

```text
search("{input}") → search_result
my_calculator("根据以下信息计算相关数值:{search_result}") → calculation_result
```

用意是展示：**模板里可以塞自然语言说明 + 变量**。  
但若计算器是 AST 白名单版（7.5.2 的 `my_calculator`），整段中文会算失败——这不是链坏了，是**下游工具契约**问题。

可运行做法（测试里的 `create_demo_three_step_chain`）：

```text
search → extract_expr → my_calculator
```

中间加「抽取表达式」工具，既满足习题「≥3 个工具」，也符合真实流水线（检索 → 结构化 → 计算）。

### 2.5 与当前 `hello_agents` 的一点兼容

现行 `ToolRegistry.execute_tool` 返回 **`ToolResponse`**，不是纯 `str`。  
教材按 `str` 写的 `len(result)` 会报错。实现里用 `_result_to_text` 取 `.text` 再写入 context——**协议升级下的最小适配**，不改变教材编排思想。

## 3. 异步执行（AsyncToolExecutor）在干什么？

### 3.1 一句话

工具本体仍是**同步阻塞**的；用 `ThreadPoolExecutor` + `run_in_executor` 丢进线程，再用 `asyncio.gather` 同时等多个结果。

### 3.2 为什么不是「真异步 API」？

课程阶段目标是：**在不改每个工具实现的前提下，给注册表加并行能力**。  
多数第三方 SDK（搜索、HTTP）仍是同步的，线程池包装是务实方案。  
真正的 `async def` HTTP 客户端是后续优化，不是本节必考点。

### 3.3 何时并行划算？（习题预热）

| 场景 | 是否划算 | 原因 |
|------|----------|------|
| 多个独立网络搜索 / API | ✅ | 等待时间可重叠 |
| 步骤有数据依赖（A 输出喂 B） | ❌ | 必须等 A，应用 ToolChain |
| 强 CPU + 争用 GIL 的纯计算 | ⚠️ 有限 | 线程提升小，可考虑多进程 |
| 共享可变全局状态的工具 | ❌/慎用 | 竞态与难调试 |

测试 `test_async_tool_executor.py` 用 `sleep` 模拟网络：并行耗时应明显短于串行——这就是「I/O 重叠」的可观测证据。

### 3.4 和工具链怎么选型？

```text
需要上一步结果吗？
  ├─ 是 → ToolChain（顺序 + context）
  └─ 否 → AsyncToolExecutor.gather（并行）
也可以：链的某一步内部再并行打多个独立查询
```

## 4. 设计原则回顾（教材段末总结）

教材收束的几条，对应你前面写过的代码：

1. **单一职责**：计算器只算、搜索只搜、链只编排  
2. **接口统一**：`run` / 函数工具最终都落到可执行、可注册的文本结果  
3. **异常与安全**：计算器用 AST 而非裸 `eval`；链对缺变量友好返回  
4. **异步提吞吐 + 管资源**：线程池 `max_workers`、显式 `shutdown`
